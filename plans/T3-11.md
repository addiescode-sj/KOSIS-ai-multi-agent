# T3-11 통합 서비스 UI — 디자인 프로토타입을 Next.js 컴포넌트로 이식

## Goal
- 완료 기준 (TASK.md 그대로): 통합 서비스 UI — 답변, 출처, Vega-Lite 차트, 멀티턴, 실행 가능한 데모 (산출물①)
- 입력: 디자인 프로토타입 `~/.pencil/documents/6ecfb2bb-…/kosis-ai` (Vite + React 18 + Tailwind 4, JSX 1,320줄,
  localhost:5173). 고객 화면 25개 상태(홈·대화·생성 중·답변 유형 9종·피드백·대화 목록·검색·로그인) + 관리자 3화면.
  모든 수치·대화·표가 하드코딩된 목업이다.
- 대상 스택(사용자 지정): Next.js App Router(레포는 16.4 — 14+ 조건 충족), TypeScript, zod, Vercel AI SDK, Radix UI primitive, Tailwind.
- Baseline (현재 `frontend/`, 실전 2 UI 그대로):
  - 화면 1개(`components/chat.tsx`), 회색 shadcn 기본 테마, 프로토타입 디자인 반영 0
  - `outcome` 4종(answered/refused/clarify/failed) 구분 표시 0 (`no_answer` 노란 카드 하나), 거절 사유별 안내 0
  - Vega-Lite 차트 렌더 0 (`result.chart`를 받지만 그리지 않음)
  - 멀티턴 0 (`meta.thread_id`를 버림 → 매 턴 새 대화, route.ts 주석 "multi-turn wiring is T3-11")
  - 핵심 수치(`stat_answer`) 별도 표시 0, `sub_results`(부분 답) 표시 0
  - 백엔드 응답 런타임 검증 0 (`as SearchResult` 캐스팅)

## Idea
프로토타입은 "보이는 모습"의 정답이고, 데이터는 백엔드 `ChatResult`(`src/kosis_agent/graph/state.py`)가 정답이다.
세 옵션 공통 핵심(= 실데이터 경로):
1. 디자인 토큰(brand 색·canvas·line·ink·sub·mute, Pretendard)을 `globals.css`의 shadcn 변수에 매핑한다. 테마 체계를 따로 두지 않는다.
2. 프로토타입 `ui.jsx`의 손으로 만든 Modal·Toggle·Radio·Select를 Radix primitive(`radix-ui` 패키지, 이미 의존성) 기반
   shadcn 컴포넌트로 바꾼다 (Dialog·Switch·RadioGroup·Select·Tabs). 접근성(포커스 트랩·ESC·aria)이 따라온다.
3. 해시 라우터는 App Router 경로로. 답변 "유형별 화면"은 경로가 아니라 **대화 화면 안에서 `outcome`·사유로 고르는 카드**가 된다.
4. `/api/chat` 프록시가 `meta.thread_id`를 클라이언트로 넘기고 다음 턴에 되돌려 보낸다(멀티턴). `result`는 zod로 파싱한다.
5. 답변 차트는 백엔드 Vega-Lite v5 spec을 `vega-embed`로 그대로 그린다(프런트가 숫자를 만들지 않음). 디자인 색은 Vega config로.
6. 대화 목록·복원: `GET /threads/{id}`는 글자(role·content)만 주고 메모리 checkpointer라 서버 재시작 시 404다.
   그래서 **스트림으로 받은 `ChatResult`를 턴마다 브라우저 localStorage에 저장**하고 복원은 그것으로 한다(차트·출처·수치 그대로).
   이어서 질문할 때 서버에 thread가 없으면(재시작) "이전 맥락은 이어지지 않음"을 표시하고 새 thread로 시작한다.

프로토타입 → 백엔드 매핑 (리뷰 반영, 코드로 확인):

| 프로토타입 화면 | 백엔드 근거 | 처리 |
|---|---|---|
| 숫자 답변 `number` | outcome=answered, `stat_answer`, `chart`, `picked[0]` | 핵심 수치·요약·Vega 차트·출처(`KOSIS / 조사명 / 표명 + url`) |
| 부분 답변 `partial` | answered + `sub_results[]`(question·table_key·outcome·reason·text·answer) 중 refused **또는 clarify** | 답한 것/못 한 것 분리 |
| 되묻기·조건 보완 `clarify`·`refine` | outcome=clarify | 하나의 카드로 합침 (백엔드 구분 없음) |
| 불일치·자료 없음·인과 거절 | outcome=refused + `no_answer_reason` 8종(no_period·no_item·class_mismatch·unit_mismatch·not_aggregatable·causal·missing_value·out_of_scope) + 실전 2 검색 거절 사유 | 사유 코드 → 아이콘·제목 사전(`lib/refusals.ts`), 모르는 코드는 일반 거절 카드 + 백엔드 문장 그대로 |
| 오류 `error` | outcome=failed, SSE `error` | `chart_note`가 있으면 "차트만 다시 그리지 못함" 안내(답은 유지), 그 외 다시 시도 |
| 일반 답변 `general` | 대응 outcome 없음 | 만들지 않음 (지어내지 않음) |
| 생성 중 `generating` | SSE: `meta` → 실전 2 검색 노드 이름(parse·retrieve·rerank1·rerank2·gate·guide·refuse) → `stat`(표마다) → `token` → `result` | 단계 표시를 "질문 해석·표 검색(노드들)·계산(stat)·답변 작성(token)"으로 묶음. 차트 단계는 이벤트가 없어 따로 표시하지 않음 |
| 원표 보기 `raw` | `picked[].url` (KOSIS 링크) | 외부 링크, 자체 표 화면 없음 |
| 대화 목록·복원 | localStorage의 저장 ChatResult (위 6) | 실데이터(이 기기에서 받은 답) |
| 검색 | 로컬 대화 + `POST /tools/search_tables`(실전 2) | 실데이터 |
| 로그인·피드백·관리자 | 백엔드 없음 | **옵션마다 다름 ↓** |

## Option A — 실데이터 화면만 이식 (최소안)
- 접근: 공통 핵심 + 백엔드 근거가 있는 화면만: 홈(빈 대화)·대화(outcome 카드 전부)·생성 중·대화 목록/복원(localStorage)·검색(대화 + 표).
  로그인·피드백·관리자는 이식하지 않는다(사이드바·헤더에서도 해당 버튼 제거).
- 예상 성능 향상 (UI 태스크라 하네스 계층 없음 → 기능 지표, 모두 수동 시나리오 + 단위 테스트로 확인):
  - outcome 구분 표시 0/4 → 4/4, 거절 사유별 안내 0 → 8종 + fallback, Vega 차트 0 → 1, 멀티턴 0 → 1, 부분 답 표시 0 → 1
  - 새로 고침 후 대화 복원(차트·출처 포함) 0 → 1
  - 다음 단계 영향: T3-14 기능 테스트·T3-15 시연에서 멀티턴 성공률·거절 시나리오를 화면으로 보일 수 있음(지금은 불가)
- 실질 반영 이점: 데이터 정확성(화면의 모든 숫자가 백엔드 출처)·예외 처리(사유별 거절)·기능 완성도. 목업 숫자 0.
  zod 스키마 `lib/schemas.ts`가 백엔드 Pydantic 미러로 T3-14에서 재사용.
- 비용·리스크: 공통 핵심이 작업의 대부분. 신규 의존성 zod·vega-embed(+vega, vega-lite). 프로토타입의 로그인·피드백·관리자 디자인은 반영 안 됨.

## Option B — A + 백엔드 없는 화면은 실서비스와 분리된 디자인 갤러리로 (균형안)
- 접근: A 전부 + 로그인·피드백 모달·관리자(메트릭·필터)를 같은 컴포넌트로 이식하되 **`/design/*` route group에만** 둔다.
  고정 픽스처(`design/fixtures.ts`)로 그리고, 레이아웃 상단에 "디자인 시안 — 실제 데이터 아님" 띠를 고정한다.
  실서비스 경로(`/`, `/c/*`, `/conversations`, `/search`)에서는 갤러리로 가는 링크·목업 숫자가 없다.
  Jaeger 화면은 실제 Jaeger UI 링크(`trace_id`)로 대체.
- 예상 성능 향상: A와 같은 기능 지표(실데이터 경로는 동일) + 프로토타입 디자인 반영 범위가 전부로 넓어짐.
  나중에 피드백·관리자 API가 생기면 픽스처만 실데이터로 바꾸면 됨(컴포넌트 재사용).
- 실질 반영 이점: 발표에서 기획 화면 전체를 보여 줄 수 있음. 목업 숫자는 실서비스 경로에 나오지 않아 "지어내지 않음" 원칙 유지.
- 비용·리스크: A 대비 화면 약 5개(로그인·로그인 실패·피드백 모달·관리자·필터) 추가. 리스크 — 갤러리 화면이 데모 중 실기능으로 오인될 수 있음(띠로 막음), 유지보수 대상 증가.

## Option C — A + 백엔드 API 신설로 해당 화면도 실데이터 (고성능안)
- 접근: A 전부 + FastAPI에 `POST /feedback`(SQLite), `GET /admin/metrics`(OTel span·피드백 집계: 질문 수·outcome 분포·거절 사유·
  노드별 p50/p95·토큰·비용), 카카오 OAuth(next-auth) 연동. checkpointer를 SQLite로 바꿔 서버 재시작 후에도 thread 유지.
- 예상 성능 향상: A의 지표 + 피드백 저장 0 → 1, 관리자 지표가 하네스와 같은 원천(0 → 1), 서버 재시작 후 멀티턴 유지 0 → 1.
- 실질 반영 이점: 운영 관측까지 보이는 완성형. 평가 핵심 지표(툴·수치 정확도, 멀티턴 성공률)는 A·B와 같음.
- 비용·리스크: 백엔드 Pydantic 계약 3개 신설 + checkpointer 교체(T3-23 계약 영향) + 카카오 앱 등록·비밀값·인증 보안 검토.
  작업량이 A의 몇 배이고 T3-12~15 산출물과 겹친다.

## Recommendation
**Option B.** 사용자가 원한 것은 프로토타입 화면의 이식이고, A는 로그인·피드백·관리자 디자인을 버린다. B는 실데이터 경로를 A와 똑같이 두고,
백엔드가 없는 화면은 실서비스 경로 밖(`/design`)에 시안으로 격리해 목업 숫자가 실답변과 섞이지 않게 한다.
C의 추가분은 평가 핵심 지표를 올리지 않으면서 백엔드 계약을 늘리므로 필요해질 때 별도 태스크로 뺀다.
(목업 숫자를 어디에도 두지 않는 것이 최우선이면 A.)
