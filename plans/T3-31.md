# T3-31 LLM 하위 span·토큰 메트릭

## Goal
- 완료 기준 (TASK.md 그대로): 노드 안 LLM 호출(실전 2 rerank2의 CLOVA/HCX 직접 호출, 실전 1 HCX 단계, 해석기·멀티쿼리
  chat model)을 모두 `gen_ai.operation.name=chat` span(`gen_ai.request.model`, `gen_ai.usage.input_tokens/output_tokens`)으로
  남기고, 토큰·지연은 OTel 메트릭(`gen_ai.client.token.usage`, `gen_ai.client.operation.duration`)으로 계측한다.
  평가 ops(토큰·LLM 호출 수)와 메트릭 합계가 같은지 대조, pytest.
- Baseline (코드 확인, 2026-11-12, T3-30 브랜치 위):

  | LLM 호출 | 어디서 | 지금 span | agent ops 토큰에 잡힘 |
  |---|---|---|---|
  | 해석기·멀티쿼리 (ChatOpenAI/ChatClovaX) | `graph/context.py`, `graph/multiquery.py` | `chat <model>` (LangChain 콜백) | 예 |
  | 실전 1 HCX 단계 (urllib) | `summarize_stat` 툴 안 | 툴 span 아래 단계 span(T3-30, 이름 `analyze.llm_plan` 등, gen_ai 토큰 속성 있음) | **아니오** (`CHAT_PREFIX` 이름만 셈) |
  | 실전 2 rerank2 (CLOVA reranker / HCX, urllib) | `search_tables` 툴 안 | **없음** (`SearchOutput.spans`의 `rerank2` 항목에 `stage2_calls`·토큰·`stage2_seconds`만) | **아니오** |

  - OTel 메트릭 계측기: **0개** (MeterProvider 없음)
  - 즉 agent 계층 ops의 `llm_calls`·`input_tokens`는 해석기 호출만 센다 → 요청당 비용이 실제보다 작게 나온다.
  - KOS-115 원문의 "guide 노드 ChatClovaX"는 실전 2 backend의 답 노드라 이 레포 워크플로에는 없다(search는 gate에서 끝남).
    범위에서 뺀다.

## Idea
1. **"LLM 호출 = `gen_ai.operation.name == "chat"` span" 하나의 규칙**으로 맞춘다. 실전 1·2는 고치지 않는다(submodule 금지).
   LangChain이 보지 못하는 두 곳(실전 1 HCX, 실전 2 rerank2)은 툴이 돌려준 기록에서 span을 만든다.
2. **메트릭은 span이 끝나는 한 곳에서 기록**한다. `LiveSpans`에 LLM span 종료 helper 하나(`_llm_done`)를 두고,
   LangChain chat · 실전 1 단계 · rerank2 세 경로가 모두 거기를 지난다 → span 합계와 메트릭 합계가 정의상 같다.
   - `gen_ai.client.token.usage` Histogram (unit `{token}`, 속성 `gen_ai.operation.name`, `gen_ai.request.model`,
     `gen_ai.token.type`=input|output) · `gen_ai.client.operation.duration` Histogram (unit `s`). OTel GenAI 규약 이름 그대로.
   - 서비스: `backend/app/telemetry.py`에 MeterProvider(service `kosis-agent`). Jaeger는 메트릭을 받지 않으므로 OTLP 메트릭은
     `OTEL_EXPORTER_OTLP_METRICS_ENDPOINT`가 있을 때만 보낸다(없으면 계측기는 no-op 비용). 전역 provider는 건드리지 않는다.
   - 평가: `evals/runners/agent.py`가 자기 MeterProvider + InMemoryMetricReader를 붙이고, run 끝에 메트릭 합계를 ops에
     `metric_input_tokens`/`metric_output_tokens`로 남겨 span 합계와 대조한다.
3. agent ops 집계를 이름(`CHAT_PREFIX`)이 아니라 `gen_ai.operation.name == "chat"` 속성으로 센다 → 실전 1·rerank2 토큰이
   비용에 들어간다. **기존 agent run과 ops 숫자가 달라진다(더 커짐, 원래 빠져 있던 호출)**. ops_history 비교 시 주의를 Result에 남긴다.

## Option A — 사후 변환 (툴 기록 → chat span) + 한 곳 메트릭
- 접근: `LiveSpans.on_tool_end`에서
  - 실전 1 `StatOutput.spans` 중 `gen_ai.request.model`이 있는 단계에 `gen_ai.operation.name=chat`을 붙인다(이름은 단계 이름 유지).
  - 실전 2 `SearchOutput.spans`의 `rerank2` 항목(`stage2_calls>0`)을 `chat <model>` span으로 만든다. 시작 시각은 앞 노드
    `seconds` 누적합(검색 그래프 노드는 순차 실행), 길이는 `stage2_seconds`. 모델 이름은 `stage2_llm.model`을 툴 생성 시
    받아 둔다(`search_tables` artifact는 이미 있음 → 모델만 span 속성에 필요).
  - 세 경로 모두 `_llm_done(span, model, tin, tout, seconds)`로 끝내며 메트릭 기록.
- 예상 성능 향상: LLM 호출 span 커버리지 1/3 경로 → 3/3; agent ops 토큰이 잡는 LLM 경로 1 → 3;
  메트릭 계측기 0 → 2; span 합계 = 메트릭 합계(오차 0, 같은 helper). 지연 영향 ≈ 0(사후, 요청 끝난 툴 기록만 읽음).
- 실질 반영 이점: 요청당 비용·지연(종합 핵심 지표)이 실제 호출을 다 센다. 서비스·평가 공용 콜백 하나라 재사용.
  submodule 수정 0.
- 비용·리스크: 반나절. rerank2 시작 시각은 근사(노드 seconds 누적, ms 단위 오차). 재시도 횟수는 `llm.attempts` 속성으로만
  남고 시도별 span은 없음. 실전 2가 `rerank2` trace 키 이름을 바꾸면 깨짐 → pytest로 고정.

## Option B — 호출 지점 실시간 계측 (stage 2 Select 래핑)
- 접근: A의 메트릭 helper는 같고, rerank2만 사후가 아니라 실시간으로 잡는다. backend `build_agent()`에서
  `selectors.LLM_RERANKERS`의 Select를 래퍼로 감싸, 호출 전후에 현재 LangChain run의 콜백 매니저로
  `on_chat_model_start`/`on_llm_end`를 직접 쏜다 → `LiveSpans`가 진짜 시작·종료 시각의 `chat <model>` span을 연다.
  실전 1은 urllib에 훅이 없어 A와 같이 사후 변환.
- 예상 성능 향상: A와 같은 커버리지·합계 + rerank2 span 시각이 실측(근사 오차 0), 실패 시 error span 실시간.
- 실질 반영 이점: Jaeger 워터폴이 정확. 같은 방식으로 다른 urllib 호출도 감쌀 수 있음.
- 비용·리스크: 1일. 실전 2 모듈 전역 dict를 바꾸는 monkeypatch(평가·서비스 모두 영향), 실전 2 내부 구조(selectors)에 결합.
  콜백 매니저를 노드 안에서 꺼내는 코드가 LangChain 내부 API에 의존. 이득은 수 ms 시각 정확도뿐.

## Option C — OTel 자동 계측 패키지
- 접근: `opentelemetry-instrumentation-urllib`(+ `-openai-v2`)를 붙여 모든 HTTP 호출을 자동 span으로. 토큰은 HCX·CLOVA 응답
  본문에 있어 자동 계측이 못 읽으므로, A의 사후 변환으로 토큰 속성·메트릭을 따로 채운다.
- 예상 성능 향상: HTTP 단위 span(재시도 시도별) 추가, 토큰 커버리지는 A와 같음.
- 실질 반영 이점: Chroma·KOSIS 등 비 LLM HTTP도 보임.
- 비용·리스크: 의존성 2개 추가, 전역 계측이라 평가 provider와 서비스 provider 분리(T3-30 원칙)가 깨지기 쉬움
  (자동 계측은 전역 provider를 씀). span 수 증가. 결국 토큰은 A가 필요 → A + 의존성.

## Recommendation
**옵션 A.** 지표(LLM 경로 커버리지 1 → 3, 메트릭 0 → 2, span=메트릭 합계)는 A만으로 다 오르고, B·C의 추가 이득은
rerank2 span 시각 수 ms 또는 HTTP 시도별 span뿐인데 비용은 monkeypatch·전역 계측이다. 실시간 정확도가 필요해지면 B로 올린다.

범위 추가 (사용자 선택 2026-11-12, "두 층 다"): 종료 이유 계측.
- LLM 층: chat span에 `gen_ai.response.finish_reasons`(LangChain 응답에 있을 때만). 실전 1·rerank2는 finish reason이 기록에
  없으므로 꾸미지 않고 실패만 `error.type`(실전 1 `llm.status`, rerank2 `stage2_error`의 예외 이름).

  `finish_reasons`를 턴에 쓰지 않는 이유: GenAI 규약상 LLM 응답 한 번의 속성이고, 이 워크플로의 턴 종료는 finalize 코드가 정한다.
