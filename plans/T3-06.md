## Idea
두 단계로 한다. 1단계가 끝나야 2단계의 숫자를 믿을 수 있다.

1. **리팩터 반영 (인계 문서 2부 그대로, 채점·지표 불변)**
   - import만 바뀐 7개 파일 + `tests/test_evals_ablation.py` (인계 §1).
   - 생성 방법이 바뀐 곳: L1 프리셋 → `(IndexSpec, SearchOptions, stage2 LLMConfig)`, `load_resources` → `build_search` / `build_graph`+`run_search`,
     `ChromaTableRetriever.connect(spec 넘김)` 3곳, `parse_query(sigungu=…)` 2곳, route `guide→found` 주석 (인계 §2).
   - **인계 문서와 다른 점**: 인계는 종합 레포 `backend/app/config.py`의 `agent_config()`를 쓰라고 하지만 main·원격 브랜치 어디에도 없다.
     실전 2 `backend/app/config.py`는 이름이 가려지고, 파일 경로 로드는 CLAUDE.md §3("실전 2는 `kosis_rag.*`만 import") 위반.
     → `evals/config.py`(작은 함수 하나)가 `kosis_rag.schemas.resources`의 `IndexSpec`·`SearchOptions`·`ChromaConfig`와 `kosis_rag.rerank.selectors.default_config`로
     셸 환경변수(실전 2 `search_config_from_shell`과 같은 이름·기본값)에서 직접 만든다. 데이터 경로는 `<KOSIS_WORKSPACE>/data`. `agent_config()`가 생기면 이 파일을 그 호출로 바꾼다.
   - `.env`는 읽지 않는다(인계 §0). 패리티 run은 셸에 `CHROMA_*`·`EMBED_CKPT`·`RERANK_CKPT`·`STAGE2`·키를 설정해야 하며, 없으면 기본값으로 조용히 돈다 → README와 Result에 명시.
   - `scripts/verify.sh`의 `vendor/phase2/src/kosis_rag/schemas.py` 존재 검사 → 패키지가 되어 항상 실패. 경로 한 줄 수정(범위 밖이지만 verify가 돌아야 측정 가능).
2. **멀티턴·멀티쿼리 채점 (새 layer `agent`)** — 아래 옵션.
   - 에이전트(T3-03·T3-04)가 아직 없으므로 **아키텍처와 무관한 계약**으로 채점한다: 시나리오(정답) × transcript(실행 기록) → 결정적 점수.
     transcript는 LangChain 메시지 관례(`AIMessage.tool_calls`)에서 뽑으므로 ReAct / Plan-and-Execute / 멀티에이전트(T3-07~10)를 같은 채점기로 비교할 수 있다.

옵션은 두 축으로 갈린다: **실행 기록을 어디서 얻나**(메시지 vs OTel span) × **멀티턴 실패를 얼마나 쪼개나**. 세 옵션 모두 채점기(결정적, LLM 0)는 같다:
`AgentScenario` 계약(`evals/schemas.py`) + `evals/evaluators/agent.py` — 툴 순서 일치 · 불필요 호출 수 · 빠진 호출 수 · 인자 필드별(`query.field_correct`) ·
턴별 표 키 상태 · 거절(`missed_refusal`/`false_refusal`) · 최종 수치(`summarize_stat` 결과 `StatAnswer`를 `calculation.grade`에 그대로 + **최종 답 문장의 숫자도**
`allowed_text_numbers`로 대조해 LLM이 지어낸 숫자 검출) · 턴 통과 · 대화 성공률 · pass^k · `--oracle` 자기검증.
transcript에는 `StatAnswer`를 Pydantic dump로 저장한다(텍스트만 저장하면 L3 채점 불가).

## Option A — 메시지 기반 얇은 실행기 (KOS-120 최소)
- 접근: 채점기 + `evals/runners/agent.py`: 컴파일된 LangGraph 그래프를 `thread_id`별 턴마다 `invoke` → LangChain 메시지 관례(`AIMessage.tool_calls`, `ToolMessage`)에서
  툴·인자·`StatAnswer`를 뽑는다. ReAct / P&E / 멀티에이전트 모두 이 관례라 아키텍처 무관. 비용·지연: 턴별 `latency_ms`·`llm_calls`·토큰 →
  `ops.summarize`(p50/p95·비용) · `ops_history.jsonl`. 토큰은 `ops.UsageCallback`(LangChain) + 실전 1 클라이언트는 `ops.usage_client`로 감싸 누락 방지.
  `--from-run`으로 저장된 transcript 재채점.
- 예상 성능 향상: 지표 값은 에이전트(T3-03·04)가 있어야 나오므로 이번엔 없다. 측정 가능해지는 것: pytest 수집 오류 6 → 1, L0~L4 실행 0 → 5계층(패리티 확인 대상),
  KOS-120 지표 실행 경로 0 → 1. T3-07 베이스라인 측정을 막는 요인 제거.
- 실질 반영 이점: 데이터 정확성(표 키 보존·지어낸 숫자 검출)·결과 검증. T3-07~10이 같은 채점기·실행기를 그대로 씀. KOS-120 완료 조건 3개 충족.
- 비용·리스크: 반나절~하루. LLM 비용 0. state 키 이름은 T3-04에서 정해지므로 표 키 추출 함수 한 곳만 맞추면 됨. 지금 그래프는 T3-01 전이라 실행 검증은 가짜 그래프로만.

## Option B — A + 턴 유형별 멀티턴 실패 집계 (추천)
- 접근: A 전부 + 시나리오 턴에 `kind`(`carry` 조건 이월 · `reference` "이거/그 표" · `correction` 정정 · `switch` 주제 전환 · `multi` 한 턴 여러 요청 · `refuse` 범위 밖)를 달고
  연구 문서 §3 실패 유형 ①~④를 심판 없이 결정적으로 판정: `reference`·`carry` 턴에 표 키가 바뀌면 `lost_reference`/`lost_condition`, `switch` 턴에 앞 턴 표 키를 그대로 쓰면
  `leaked_context`, `correction` 턴에 고친 인자가 반영되지 않으면 `ignored_correction`, `multi` 턴은 하위 요청별 툴 recall. report.md에 kind별 통과율·유형 표·대화별 첫 실패 턴.
- 예상 성능 향상: A와 같음(값은 T3-07). 차이는 해상도: 대화 성공률 하나 대신 유형 5개로 나와 T3-04·T3-07에서 무엇을 고칠지 바로 정해짐.
- 실질 반영 이점: A + 질의 이해·예외 처리(주제 전환·범위 밖). 사용자 요청(연구 문서의 멀티턴·멀티쿼리 유형)을 결정적 지표로 덮음. T3-10 비교 표의 행이 됨.
- 비용·리스크: A + 반나절. 유형 판정 규칙은 시나리오 정답(앞 턴 표 키)만 보므로 추가 데이터 불필요. 규칙이 틀릴 위험 → 유형별 pytest.

## Option C — span 기반 실행 기록 (KOS-114 선행)
- 접근: 채점기는 같고, transcript를 메시지가 아니라 실행 중 OTel span(KOS-114 NodeSpans 실시간 콜백)에서 만든다. 툴 호출·토큰·지연을 span 속성(`gen_ai.*`, `tool.name`)에서 읽어
  서비스와 평가가 같은 trace ID를 공유.
- 예상 성능 향상: A와 같음. 실패 턴에서 Jaeger trace로 바로 이동.
- 실질 반영 이점: 관측성·기술 설계(서비스·평가 공용 계측), KOS-114·115와 한 번에 정리.
- 비용·리스크: 2일+. KOS-114가 없어 span 이름·속성을 먼저 정해야 함(계약 충돌). 아키텍처마다 span을 심어야 해 T3-08·09 부담. KOS-120 기한(11/14) 위험.

구현 범위 (C를 이 레포 안에서 닫는 형태):
1. 리팩터 반영(Idea 1단계) — 인계 §1·§2 + `test_evals_ablation`의 `TableInfo` 사본 + `scripts/verify.sh` 경로 + `evals/config.py`(`kosis_rag.schemas.resources`로 구성, `.env` 안 읽음).
2. **span 계약 = OTel GenAI semantic conventions 이름 그대로** (새 이름을 만들지 않아 KOS-114·115와 충돌 없음):
   턴 root `invoke_agent`(`gen_ai.conversation.id`=thread_id, `kosis.turn.index`) · 툴 `execute_tool <name>`(`gen_ai.tool.name`, `gen_ai.tool.call.arguments`, `gen_ai.tool.call.result`)
   · LLM `chat <model>`(`gen_ai.request.model`, `gen_ai.usage.input_tokens/output_tokens`) · 그래프 노드는 `NodeSpans`와 같은 규칙(이름 하드코딩 없음).
3. `src/kosis_agent/tracing.py` `LiveSpans` 콜백: LangChain 콜백으로 **실행 중** 실제 OTel span을 연다(서비스·평가 공용). KOS-114의 "`src/kosis_rag`로 옮김"은 vendor 수정 금지라
   이 레포 `kosis_agent`에 둔다. backend 연결은 `backend/app/main.py`가 T3-01로 깨져 있어 이번엔 안 함(T3-01 뒤: `with agent_turn(tracer, thread_id, i) as (_, spans):` 안에서 `config={"callbacks": [spans]}`).
4. `evals/runners/agent.py`: 시나리오 턴마다 그래프를 `thread_id`로 `invoke` + `LiveSpans` → `InMemorySpanExporter`로 받은 span에서 transcript(툴 순서·인자·`StatAnswer`·지연·LLM 호출·토큰)를 만든다.
   `OTEL_EXPORTER_OTLP_ENDPOINT`가 있으면 같은 span이 Jaeger로도 간다. 채점 뒤 `eval.scenario` span이 턴 root들에 **OTel Link**로 verdict를 붙인다(KOS-114 할 일 3).
   턴 상태(표 키)는 span에서 결정: 그 턴 마지막 `summarize_stat`/`make_chart`의 `table_key` 인자, 없으면 `search_tables` 결과 1위 키 → state 키 이름(T3-04)에 의존 안 함.
