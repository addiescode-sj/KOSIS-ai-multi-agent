## 설계 (모든 옵션 공통)

**테이블** — alembic 마이그레이션 `0002_pgvector` (KOS-86 마이그레이션 체계에 맞춤, 임도유와 확인)

```sql
CREATE EXTENSION IF NOT EXISTS vector;
CREATE TABLE vector_collection (
  name        text PRIMARY KEY,          -- Chroma 컬렉션 이름 그대로
  metadata    jsonb NOT NULL,            -- embed_model, embed_ckpt, doc_format, dim ... (Chroma 메타데이터 그대로)
  created_at  timestamptz NOT NULL DEFAULT now()
);
CREATE TABLE vector_item (
  collection  text NOT NULL REFERENCES vector_collection(name) ON DELETE CASCADE,
  id          text NOT NULL,             -- 표 키, 질문 id, '표키|지역코드'
  key         text NOT NULL,             -- metadata->>'key' (표 키 조건용)
  document    text NOT NULL,
  metadata    jsonb NOT NULL,
  embedding   vector(1024) NOT NULL,
  PRIMARY KEY (collection, id)
);
CREATE INDEX ON vector_item (collection, key);
```

- **벡터 인덱스(HNSW)는 처음엔 만들지 않는다.** 표 색인 2,364행 · 청크 5,158행 규모는 전체 비교(정확 검색)가 수 ms이고,
  KOS-138의 "필터 후 결과가 줄어드는 문제"(HNSW가 후보를 먼저 자르고 조건을 나중에 거는 것)가 원천적으로 없다.
  행이 수만 건을 넘으면 HNSW + `hnsw.iterative_scan = relaxed_order`(pgvector 0.8)를 붙인다.
- 점수는 지금과 같게 `1 - (embedding <=> q)` (코사인 거리).
- 이미지: `postgres:17-alpine` → `pgvector/pgvector:0.8.1-pg17`. 같은 PostgreSQL 17이지만 alpine(musl) → debian(glibc)이라
  문자 정렬 규칙이 달라진다. 개발용 `postgres-data` 볼륨(대화 기록·평가 결과)은 새로 만드는 것을 기본으로 하고,
  남길 자료가 있으면 `pg_dump`로 옮긴다.
- 마이그레이션 주의(검토):
  - `tests/test_store.py:108-116`이 마이그레이션 결과와 ORM 모델이 같기를(`diff == []`) 요구한다 → 벡터 테이블을 ORM 모델에 넣는다
    (`pgvector` 파이썬 패키지의 `Vector(1024)` 형). `include_object`로 빼는 것보다 정직하다.
  - downgrade는 테이블 → extension 순으로 지운다. base까지 되돌려도 깨지지 않는지 테스트.
  - 실전 2만 단독으로 쓸 때(적재·테스트) 테이블이 없으면 어댑터가 같은 DDL을 `IF NOT EXISTS`로 만든다(`ensure_schema()`). 종합은 alembic이 먼저 만든다.
  - 배포 DB에서 `CREATE EXTENSION` 권한 필요 → M6 확인 항목.
  - 실전 2 `pyproject.toml`에 `psycopg[binary]`·`pgvector` 의존성 추가.

**옮기는 방법** — `scripts/chroma_to_pgvector.py` (새 파일, 1회용)
1. 받은 볼륨으로 로컬 Chroma를 띄운다(안내서 3번 받는 쪽).
2. 컬렉션마다 `get(include=["embeddings","documents","metadatas"])`을 나눠 읽어 `COPY`로 넣는다. **임베딩은 다시 하지 않는다.**
3. 확인: 컬렉션별 개수 일치(표 색인 2,364 · 청크 5,158), id 집합 일치, 무작위 100건 벡터 최대 오차 0(float32 그대로).
   컬렉션마다 메타데이터 `dim`과 실제 벡터 길이를 확인하고, 1024가 아니면 멈춘다(볼륨을 받아야 확인 가능).
   메타데이터의 리스트(`f_*`)·참거짓(`f_national`)·정수(`start`·`end`)는 jsonb에 그대로 담는다.

**확인 방법** — 실전 2 `scripts/parity_l1.py` (실전 2 저장소에서 실행: `search_config_from_shell`이 실전 2 `backend/app/config.py`에만 있음)
- L1 골든셋 질문 전체를 Chroma·pgvector로 한 번씩 `dump` → `compare`. 기대: 순위·표 키 동일.
- 지금 compare는 줄 텍스트가 완전히 같아야 통과한다(316행). pgvector `<=>`는 double, Chroma는 float32라 점수 끝자리가 다르므로
  실전 2 PR에 `--score-tol`(기본 0, 이번엔 1e-5) 옵션을 넣는다.
- fingerprint(111-126행)에 `store` 키를 추가해 두 덤프를 구분하고, compare에 `--ignore-config store`로 그 키만 빼고 비교한다.
- 조건 필터 질문만 따로 세어 "요청한 k개 중 받은 개수"를 Chroma → pgvector로 기록.
- 검색 지연: dense 한 번 호출 시간(중앙값·95%)을 같은 질문으로 Chroma → pgvector.



## Option A — 어댑터만 바꾸고 Chroma를 바로 뺀다
- 실전 2 `adapters/chroma.py` 자리에 `adapters/pgvector.py`를 두고, 지금 코드가 쓰는 메서드(`get_collection`, `.metadata`,
  `.count()`, `.query(...)`, 적재용 `upsert/get/delete`)를 같은 모양으로 제공한다. 검색 로직(dense.py·hq.py)은 거의 그대로.
- compose에서 `chroma` 서비스 삭제, 설정 `CHROMA_*` → `DATABASE_URL`(이미 있음) + `VECTOR_COLLECTION`.
- 예상 수치: L1 Hit@1/5/10 **변화 없음**(같은 벡터·정확 검색. Chroma는 근사 검색이라 오히려 같거나 아주 조금 나을 수 있음),
  조건 필터 결과 개수 지금과 같거나 많음, dense 지연 수 ms 수준(측정으로 확인). 서버 컨테이너 1개 감소, 메모리 약 0.3~0.5GB 절약.
- 이점: 구조가 가장 단순, M6 배포에서 서비스 하나 줄어듦(DB 백업·모니터링 한 곳).
- 비용·리스크: 전환 후 문제가 생기면 되돌리려면 커밋을 되돌려야 함. 전후 비교를 하려면 비교 시점에 옛 커밋을 따로 돌려야 함.

## Option B — 두 저장소를 설정으로 고르게 하고, 비교 후 기본값을 pgvector로 (추천)
- A의 어댑터 + 설정값 `VECTOR_STORE=chroma|pgvector` (기본 `pgvector`). 같은 코드에서 값만 바꿔 parity 비교를 바로 할 수 있다.
- compose: `chroma`를 `profiles: ["chroma"]`로 내려 평소엔 안 뜨게 하고, backend의 `depends_on: chroma`를 뺀다.
  기능 동결(11/22) 뒤 QA 기간에 문제 없으면 Chroma 코드·서비스를 지우는 후속 정리(2~3시간: 어댑터 분기, 실전 2 compose·config의
  `CHROMA_*`, 종합 `.env.example`·`evals/config.py`의 `CHROMA_*`, `chromadb-client` 의존성(`pyproject.toml:25`), `check_build.py`).
- 설정 위치: 종합 `backend/app/config.py`와 실전 2 `backend/app/config.py`(74행) 둘 다 `VECTOR_STORE`를 읽는다.
- 예상 수치: A와 같음.
- 이점: 동결 이틀 전 전환이라 되돌리기가 설정 한 줄. 같은 실행 환경에서 "몇 → 몇"을 남기기 쉬움(KOS-138 완료 기준).
- 비용·리스크: QA 기간 동안 저장소 두 종류 코드가 공존(분기 1곳). 지우는 정리를 잊으면 남음 → Linear에 후속 이슈로 남긴다.

## Option C — 검색을 SQL로 다시 짜서 필터·검색을 DB에서 한 번에
- 등록부 필터(`filter_with_relaxation`)까지 SQL로 옮기고, BM25도 PostgreSQL 전문 검색으로 바꾸는 큰 전환.
- 예상 수치: 측정 전에는 알 수 없음. 조건 완화 규칙이 바뀌면 L1 수치가 움직일 수 있음.
- 비용·리스크: 실전 2 검색 그래프를 고치지 않는다는 원칙(종합 CLAUDE.md)과 충돌, 동결 전 일정에 맞지 않음. **범위 밖으로 둔다.**
