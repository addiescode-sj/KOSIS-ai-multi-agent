# T3-23 AI 파이프라인 고도화 — 1단계: 검색 임베딩 방법 비교

## Goal
- 완료 기준 (TASK.md 그대로): 같은 검색 골든(v2, T3-22 재판정 라벨)에서 임베딩 방법별 Hit@1·Hit@5·Hit@10·MRR·Recall@50과 짝 비교 구간(지금 서비스 임베딩 대비)을 표로 남기고, 이긴 방법만 서비스 후보로 올린다. 비교 코드는 pytest로 검증한다 (Linear KOS-156)
- 이번 단계 범위: 검색의 임베딩(1단계 dense 목록)만 바꾼다. BM25·조건 필터·RRF·1차 리랭커·gate는 지금 설정 그대로 두고, 바뀐 임베딩이 그 뒤 단계까지 어떤 차이를 내는지 함께 잰다. KOS-156의 나머지 범위(노드 계약 고정·검색 API 고정 KOS-33·슬롯 추출 KOS-102)는 이 plan 뒤 단계로 남긴다.
- Baseline (골든 v2 test, 답할 수 있는 60문항, T3-22 Result): staged(임베딩 unseen-e1 + BM25 + 조건 + 1차 리랭커) Hit@1 0.600 · Hit@5 0.867 · MRR 0.711, hybrid+cond(리랭커 없음) Hit@1 0.417 · MRR 0.576. dense 단독 값과 dev 29문항 값은 이 레포에 run이 없다 → S0에서 같은 하네스로 다시 잰다.
- 지금 서비스 임베딩: `data/models/embedder/bge-m3-ft-unseen-e1.pt`(bge-m3 위 6층, v0 하드네거티브, n2-L60 문서 텍스트, sha aa412057). 1차 리랭커 `bge-reranker-v2-m3-ft-unseen-e2.pt`는 이 임베딩이 뽑은 후보로 학습됐다.

## 2단계 — 색인 텍스트 바꾸기: 역 HyDE vs 표 설명문 (사용자 지정, 2026-11-08, 초안)
배경: 1단계 결과 학습 리랭커가 가장 큰 개선이었고, 남은 오답은 "임베딩이 정답 표를 위로 못 올림"과 "형제 표 구분"이다. 강사 피드백(표마다 정확한 자연어 설명을 합성해 넣기)과 기존 역 HyDE(T2-39)를 같은 조건에서 비교한다.

| 방법 | 만드는 시점 | 만드는 것 | 검색 때 맞대는 것 |
| --- | --- | --- | --- |
| 역 HyDE (T2-39, 이미 있음) | 색인 | 표마다 예상 질문 여러 개(gpt-4o-mini, 9,757개) → 별도 질문 색인 | 질문 ↔ 예상 질문, 기존 목록과 RRF |
| 표 설명문 (새로) | 색인 | 표마다 자연어 설명 1개(고성능 모델) | 질문 ↔ 표 텍스트(n2 + 설명) |

- 기존 자산: `data/hq/hq-cb0b3c5b-a3c88540-gpt-4o-mini-f30-k2/` 에 질문 9,757개와 함께 **gpt-4o-mini 한 줄 설명 2,364개**(`descriptions.jsonl`, 예: "주요 인구지표를 지역별로 보여주는 통계입니다.")가 이미 있다. 짧고 두루뭉술해서 형제 표 구분에는 약하다 → "약한 설명" 비교군(D0)으로 쓴다.
- 고성능 설명문(D1): 이 프로젝트의 별도 Claude 스레드가 구독으로 생성(API 비용 없음). 입력은 표 메타데이터 카드(n2 텍스트 + 조사·기관·수록기간·주기·지역 수준)만, 골든 질문은 보지 않는다(누수 없음). 고정 프롬프트 파일로 25표씩 나눠 생성, 출력 `data/desc/<build_id>/descriptions.jsonl`(key, description) + `build.json`(프롬프트 sha, 모델, 표 sha, 표 수, 실패 수). 규칙: 한국어 2~4문장, 무엇을 세는지·어떤 분류로 나뉘는지·기간과 주기·지역 단위·같은 조사의 비슷한 표와 다른 점을 쓴다, 메타데이터에 없는 사실·숫자(연도 범위 제외)는 쓰지 않는다. 표 10개 샘플을 먼저 사용자가 확인한다.
- 설명문을 쓰는 곳: **dense 임베딩 텍스트에만** 덧붙인다(`n2 텍스트 + "설명: ..."`). BM25와 리랭커 문장은 지금 n2 그대로(리랭커가 n2로 학습됨). 학습 임베딩도 n2로 학습됐으므로 무학습 BGE에서도 함께 잰다.
- 필요한 코드(사용자 확인 후): 실전 2 `shared/tabletext.py`에 형식 `n2-L60+desc`(임베딩 텍스트만 설명 추가, BM25·리랭커는 `n2-L60`), 가중치 형식 검사(`check_format`)는 `+desc` 앞부분으로 비교, 설명 파일 경로는 적재 인자 `--desc <build_id>`, 컬렉션 meta에 desc build_id 기록. pytest: 형식 분리, 설명 없는 표는 n2와 같음, 형식 검사.

| # | 임베딩 | 색인 텍스트 | 질문 색인(역 HyDE) | 리랭커 | 비교 대상 |
| --- | --- | --- | --- | --- | --- |
| E1 | 학습 | n2 | f30-k2 켬 | 없음 / 학습 | R4 / R7 |
| E2 | 학습 | n2 + D0(4o-mini 설명) | 끔 | 없음 / 학습 | R4 / R7 |

- 2차 리랭커(GPT)는 이 단계에서 끈다(비용·변동 줄이기, 이긴 조합만 마지막에 붙여 본다).
- 판정: test 60에서 비교 대상 대비 1위 정답률 또는 5위 안 정답률이 +2문항 이상이고 다른 하나가 1문항 넘게 떨어지지 않으면 "효과 있음"으로 후보에 올림. 판정 없는 표 비율(Unjudged@10)도 함께 적는다(새로 올린 표가 판정 없는 표면 최소값이 과소평가됨).

## Option A — 기반 모델 바꾸기 (무학습 스크리닝)
- 접근: 문서 텍스트·나머지 단계는 그대로 두고 dense 모델만 바꾼다. 후보: bge-m3 무학습(기준점), KURE-v1(재확인용 1회), multilingual-e5-large-instruct, Qwen3-Embedding-0.6B, OpenAI text-embedding-3-large(API, 팀이 GPT 계열 사용 가능). 구현 전에 라이선스·GPU 메모리를 확인하고 안 맞는 후보는 뺀다.
- 예상 성능 향상: 무학습 후보가 지금 미세조정 임베딩을 바로 이길 가능성은 낮다(미세조정이 무학습 대비 Hit@5 +0.10). 기대하는 것은 "어느 기반이 무학습 상태에서 bge-m3보다 높은가"이고, 무학습 bge-m3보다 dense Hit@5가 0.05 이상 높으면 C의 미세조정 후보가 된다. 서비스 지표(staged) 변화는 예상 0~-0.05.
- 실질 반영 이점: 기술 설계 — "왜 bge-m3인가"에 처음으로 숫자 근거가 생긴다(발표·ADR). 하네스는 이후 모든 임베딩 실험에 재사용된다.
- 비용·리스크: 코드 0.5일, 인코딩은 사용자 PC GPU로 모델당 10~20분, OpenAI는 문서·질문 약 1M 토큰(1달러 미만 추정). 리스크: 1차 리랭커가 지금 임베딩 후보로 학습돼 있어 staged 층 비교는 지금 임베딩에 유리하게 기운다(dense·hybrid 층으로 판단).

## Option B — 같은 모델, 다른 표현 (bge-m3 출력·문서 쪼개기·지시문)
- 접근: 서비스 체크포인트 unseen-e1을 그대로 쓰고 표현 방식만 바꾼다.
  - B1 bge-m3 sparse(lexical weight) 출력을 네 번째 목록으로 RRF에 더함 (BM25와 다른 학습된 어휘 신호)
  - B2 bge-m3 multi-vector(ColBERT) 점수로 상위 50 재정렬 또는 목록 추가
  - B3 표 한 장 = 여러 벡터: 제목·조사명 / 항목·분류 / 기간·주기·지역 필드를 따로 임베딩해 max·가중합으로 점수 (형제표 혼동이 주 실패라 필드 분리가 효과 있을 수 있음, 10/29 후보 6번)
  - B4 질의 지시문 접두("수치를 찾을 통계표: …") 유무
  - 미세조정은 위 6층만 바꿨으므로 sparse·ColBERT 헤드는 기반 가중치 그대로 붙는다. 이 조합이 망가지지 않는지는 dev에서 먼저 확인하고, 망가지면 무학습 bge-m3로 같은 비교를 해 원인을 나눈다.
- 예상 성능 향상: hybrid+cond Hit@1 0.417 → 0.43~0.47, Recall@50 소폭 상승(근거: 실패 대부분이 정답이 후보 안에 있는데 순서가 틀린 형제표 혼동, 10/29 분석에서 후보 50 안 정답 90% 이상). staged는 리랭커가 순서를 다시 잡아 +0~+0.03. 크기는 측정 전 근거가 약하다.
- 실질 반영 이점: 데이터 정확성 — 형제표(기간·지역 수준만 다른 표) 혼동을 직접 겨냥. 지금 체크포인트·리랭커를 그대로 쓰므로 이기면 실전 2 PR이 작다(목록 하나 추가). 재학습이 필요 없다.
- 비용·리스크: 코드 1일(B3 필드 텍스트 만들기가 가장 큼), 인코딩 GPU 30분~1시간, API 비용 0. 리스크: B3는 문서 수가 3~4배라 서비스 색인·지연이 늘어난다(측정에 p95 지연 포함). sparse는 BM25와 겹쳐 이득이 작을 수 있다.

## Option C — A + B 비교 후 상위 기반 모델 미세조정
- 접근: A·B를 모두 돌리고, 무학습에서 bge-m3를 이긴 기반 모델 1~2개를 지금과 같은 레시피(v0 하드네거티브, 평가 표 제외 unseen, 위 6층 또는 그에 맞는 층, 1 epoch)로 Colab에서 미세조정한다. B에서 이긴 표현이 있으면 그 표현 위에서 비교한다. 리랭커는 새 임베딩 후보로 다시 학습할지 별도 판단(이번 범위 밖, 결과만 기록).
- 예상 성능 향상: 기반 모델이 무학습에서 bge-m3보다 Hit@5 +0.05 높았다면, 같은 미세조정 이득(+0.10)이 비슷하게 붙는다고 보고 hybrid Hit@5가 옛 검색 골든 89문항 기준 0.607 → ~0.65 수준(근거: 계획29의 미세조정 이득 크기). 이득이 겹치지 않을 수도 있어 불확실성이 크다.
- 실질 반영 이점: 서비스 검색 품질을 올릴 가능성이 가장 크고, "모델 고르기 → 같은 레시피로 학습 → 같은 골든으로 판정" 절차가 남는다.
- 비용·리스크: A·B 비용 + 학습 노트북 이식 0.5~1일 + Colab 학습 모델당 1~2시간(사용자 실행) + 새 임베딩이면 리랭커와 후보 분포가 어긋나 staged가 오히려 떨어질 수 있음. 11/15 마감 안에 KOS-156 나머지 범위(계약·API·슬롯)와 같이 하기 빠듯하다.

## Recommendation
