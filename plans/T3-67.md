# T3-67 운영자 화면 전부 React로 배포

## Goal
- 완료 기준: 배포판 `https://<사이트>/admin` 아래 화면이 모두 프론트(Next.js, T3-65·66 디자인)로 나온다. 홈·지표 대시보드·필터·질문 목록·질문 상세·👎 처리함.
  - 운영자 앱(`admin/`)은 화면을 그리지 않고 JSON API(`/admin/api/*`)만 맡는다.
  - 지금 지키는 것은 모두 그대로 둔다: 카카오 로그인 + 허용 목록(밖이면 404), 전용 DB 계정 `kosis_admin`(대화 내용 못 읽음), 질문 상세 접근 기록, 👎 처리 충돌 막기, 답 문장 없음(11/26).
- Baseline (main `6ece94c`):
  - 배포판 React 운영자 화면 0개. `/preview/admin`은 배포판에서 404.
  - 운영자 기능은 Jinja 화면 5개(홈·지표·질문 목록·질문 상세·👎 처리함)에만 있다.
  - JSON API 1개(`GET /admin/api/metrics`, T3-66).
- 의존: T3-66(#66) 병합됨. 운영자 앱 배포는 node-2(`deploy/k8s/32-admin.yaml`, T3-62).

## 배경 (조사)
- 입구(`deploy/k8s/40-ingress.yaml`): `/admin` Prefix → 운영자 앱 8100, `/` → 프론트 3000. Traefik은 긴 경로가 먼저 맞는다.
- 프론트 로그인 확인 방식: 서버 컴포넌트가 브라우저 쿠키를 그대로 실어 백엔드를 부른다(`lib/backend/server-read.ts` `loginCookie`·`backendGet`, 5초 제한). 운영자 확인도 같은 방식으로 운영자 앱을 부르면 된다.
- T3-66: 지표 대시보드는 브라우저가 같은 주소의 `/admin/api/metrics`를 부른다(쿠키는 브라우저 → 운영자 앱, 프론트 서버는 안 거침). 401 → 로그인 필요, 404 → 권한 없음 화면.
- **문제: 지금 React 화면은 틀(메뉴·제목)을 먼저 그리고 숫자만 막는다.** 배포판에 그대로 열면 운영자가 아닌 사람도 "Admin Console" 틀을 보게 되어 "운영자 아니면 404(화면이 있다는 것도 알리지 않음)" 원칙이 깨진다 → 서버에서 먼저 확인해야 한다.
- React에 없는 화면: 홈, 질문 목록, 질문 상세, 👎 처리함(+저장). 있는 것: 대시보드, 필터, Jaeger(예시 데이터).
- 👎 저장은 지금 HTML 폼 + form_token(쿠키 토큰의 HMAC) + Origin 검사.

## 공통으로 바꾸는 것 (세 옵션 모두)

### 운영자 앱 (`admin/`)
| 주소 | 내용 |
|---|---|
| `GET /admin/api/me` | 운영자 이름·ID, 👎 저장에 쓸 `form_token`. 프론트 서버의 확인용 |
| `GET /admin/api/home` | 홈 카드(오늘 질문·오류·이탈·p95·새 👎, 최근 7일 문제, 처리함 상위 5) |
| `GET /admin/api/metrics` | 그대로 (T3-66) |
| `GET /admin/api/questions` | 질문 목록 (start·end·outcome·user·internal·page_no) |
| `GET /admin/api/questions/{id}` | 질문 상세 + 고쳐 쓴 질문 + 피드백 + 처리 상태 + 같은 대화. **접근 기록 1행**(지금과 같음) |
| `GET /admin/api/feedback` | 👎 처리함 (status·start·end·category·assignee·page_no) + 담당자 목록 |
| `POST /admin/api/feedback/{id}` | JSON `{status, assignee, note, issue_key, seen}`. 200 저장된 값 · 409 먼저 바뀜 · 422 값 오류 · 404 피드백 없음 · 403 Origin/토큰 틀림 |
- 모든 `/admin/api/*`: 로그인 없음 401 JSON, 허용 목록 밖 404, **DB 장애 503 JSON**(#66 리뷰 1), `no-store`.
- POST 보호: `Origin == ADMIN_PUBLIC_ORIGIN` + `Content-Type: application/json` + 헤더 `X-Admin-Token`(= `/me`의 form_token). 다른 사이트에서는 세 가지를 다 맞출 수 없다.
- `first_token`도 5분 캐시에 넣는다(#66 리뷰 2).
- 숫자·SQL은 지금 `queries.py` 함수를 그대로 부른다. 새 SQL 없음.

### 프론트 (`frontend/`)
- `app/preview/admin/*` → `app/admin/*`로 옮긴다: `/admin`(홈), `/admin/metrics`(대시보드), `/admin/filters`, `/admin/questions`, `/admin/questions/[id]`, `/admin/feedback`.
- **`frontend/proxy.ts`(Next 16의 요청 앞단, matcher `/admin/:path*`, `/admin/api` 제외)** 가 화면을 그리기 전에 확인한다. layout에서 막으면 안 된다(리뷰 1·2: 루트 layout이 `<Suspense>` 뒤에서 흘려보내 200이 먼저 나가고, 화면 사이 이동·미리 읽기 요청에서는 layout이 다시 돌지 않으며, layout은 주소를 모른다).
  - 로그인 쿠키 없음 → 307 `/auth/kakao/login?next=<주소+쿼리>`
  - `ADMIN_URL/admin/api/me`(클러스터 안 `http://kosis-admin:8100`, 3초 제한)에 Cookie 헤더만 실어 부름 → 200이면 통과, 401이면 로그인으로, 404면 **빈 본문 404**, 그 밖(503·HTML·연결 안 됨)이면 **빈 본문 503**(운영자인지 모르는 사람에게 틀을 보이지 않음, 리뷰 7)
  - 미리 읽기·화면 사이 이동 요청에도 똑같이 돈다. 통과한 응답에도 `Cache-Control: no-store`·`X-Robots-Tag: noindex`·`X-Frame-Options: DENY`·`Referrer-Policy: no-referrer`를 여기서 붙인다(`next.config` headers는 페이지 응답에서 덮어써질 수 있음, 리뷰 3).
  - 뒷받침: 각 페이지 서버 컴포넌트도 `React.cache`로 묶은 `requireOperator()`를 한 번 부른다(proxy matcher가 바뀌어도 새지 않게).
  - `next build` 결과에서 `/admin` 경로가 미리 만든 화면(prerendered)으로 표시되지 않는지 확인한다.
- `lib/auth/login-href.ts`: 돌아올 곳에 `/admin`으로 시작하는 주소를 허용한다(카카오 로그인 실패 뒤 다시 시도할 때 `/admin`을 잃지 않게, 리뷰 2). 백엔드 `safe_return`은 이미 `/admin`을 받는다.
- 데이터는 브라우저가 같은 주소로 `/admin/api/*`를 부른다(T3-66 방식). 쿠키가 프론트 서버를 거치는 곳은 proxy의 `/me` 확인 하나뿐이고, 쿠키는 기록하지 않는다.
- 👎 저장 토큰: 브라우저가 `/admin/api/me`를 직접 읽어 `form_token`을 받고 `X-Admin-Token` 헤더로 보낸다(리뷰 8). 다른 사이트는 사용자 정의 헤더 때문에 사전 확인(CORS preflight)에서 막히고, 운영자 앱은 CORS를 열지 않는다.
- 질문 상세 쿼리는 `staleTime: Infinity`·`retry: false`·`refetchOnWindowFocus: false`. 창을 다시 볼 때마다 접근 기록이 늘지 않게 한다(리뷰 6).
- `next.config.ts`: `/admin/api/*` → `ADMIN_URL` 전달을 `ADMIN_URL`이 있으면 배포 빌드에서도 켠다(로컬 `next build && next start` 시험용. 배포에서는 입구가 먼저 받아 영향 없음, 리뷰 4). `/preview/admin/:path*`는 rewrite 대신 `/admin/:path*`로 redirect.
- 새 화면 4개(홈·질문 목록·질문 상세·👎 처리함)는 T3-65 부품(`AdminShell`·`Panel`·`DataTable`·`StatCard`)으로 만든다. 디자인 시안이 없는 화면이라 기존 부품 모양을 따른다 → 도유님 리뷰.
- Jaeger 화면(예시 데이터)과 `/api/preview/admin/*`, `sample.ts`는 배포판에서 뺀다. 메뉴의 "추적"은 Grafana 주소(`ADMIN_GRAFANA_URL`가 있을 때)로 바꾼다.
- `/preview/admin/*`는 `/admin/*`로 보내는 주소 바꾸기만 남긴다(옛 링크용).
- 개발 환경: `next dev`의 `/admin/api/*` → `ADMIN_URL` 전달(T3-66)은 그대로.

## Option A — 프론트로 바꾸고, 옛 Jinja 화면은 `/admin/classic`에 1주 남김 (권장)

- React 화면에 문제가 생기면 운영자가 바로 옛 화면을 쓸 수 있다. 1주 뒤(QA 끝, 12/04쯤) 별도 PR로 Jinja 화면·템플릿·`admin.css`를 지운다.
- 예상 효과: 배포판 React 운영자 화면 0 → 6, JSON API 1 → 7, 운영자 아닌 계정에 보이는 운영자 글자 0, 기존 화면과 숫자 차이 0.
- 비용·리스크: **약 2일**(리뷰 5: 새 화면 4개 + API 6개 + 옛 화면 주소 이동·테스트). 같은 기능이 1주 두 벌이라 고칠 때 두 곳(API는 하나라 화면만). 옛 화면 주소가 바뀌어 북마크는 깨짐(운영자 1명이라 영향 작음).

## Option B — 한 번에 바꾸고 Jinja 화면을 바로 지움
