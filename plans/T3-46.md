# T3-46 e2e 전용 골든셋 — 실패 유형별 ~600문항 + 규칙 분류 정답 라벨

## 범위 변경 (2026-11-20, 사용자 요청)
1단계(계산 골든 525문항으로 분포 확장, 아래 "1단계 기록")는 끝났다. 사용자가 범위를 바꿨다:
"기존 e2e 기본 데이터셋은 계산 골든셋이었는데, 대표 실패 유형을 고려한 ~600개 e2e 전용 골든셋으로 바꾼다.
① 검색된 표에서 숫자를 잘못 뽑거나 계산을 잘못함 ② 수식 선택(차트·숫자 계산에 쓸 수식을 코드가 고르는데 잘못 고르거나, 분류된 숫자가 틀림)
③ 멀티턴·멀티쿼리에서 복합 질문에 맞게 질의를 재작성했는지 ④ 질의 이해·질문 분류(되묻기 / 바로 RAG / 재작성 필요)
— 현재 룰 베이스 분류 type을 정답지에 정답과 함께 넣는다." live e2e는 이번에 돌리지 않는다(사용자 지시).

## Goal
- 완료 기준: e2e 기본 골든을 e2e 전용 파일 `evals/datasets/e2e_golden.jsonl`(~600문항)로 바꾼다. 문항마다 실패 유형(①~④)과
  규칙 분류 정답 라벨(아래 "정답 라벨")을 정답(셀 숫자·표·재작성 문장)과 함께 담는다. 숫자는 Parquet 셀에서 코드가 뽑는다.
  e2e 계층이 이 파일을 읽고, 라벨별 정확도를 리포트에 낸다. pytest.
- Baseline:
  - 지금 e2e 기본 = 계산 골든(1단계 후 `calculation_golden_wide.jsonl` 525문항, value·compare·trend·거절만). 유형 ②③④를 따로 재는 문항·라벨 없음.
  - 멀티턴·멀티쿼리는 agent 계층(`agent_scenarios_multiturn_dev.jsonl` 등)에만 있고 e2e와 따로 돈다. 질문 분류 정답 라벨은 어디에도 없음.
  - 규칙 분류 정확도: 측정 기록 없음 (= baseline 없음).

## 정답 라벨 (현재 코드의 규칙 분류 어휘 그대로, 리뷰 2~4 반영)
| 라벨 | 값 (코드 이름) | 정하는 코드 · 그래프에서 읽는 곳 |
|---|---|---|
| `route` (④, 파생) | `rag` 바로 검색 · `rewrite` 재작성 후 실행 · `clarify` 되묻기 · `refuse` 거절 | 파생: outcome=clarify → clarify, refused → refuse, reading∈{carry_over, reference, chart_only} 또는 split 2개 이상 → rewrite, 그 밖 rag |
| `reading` (③, 파생) | `new` · `chart_only` · `reference` · `carry_over` · `defer` | `graph/context.py` `read_turn(mode="rules")`의 Reading에서 파생: chart_only=True → chart_only, use_previous_table·resolved_question==원문 → reference(규칙3), use_previous_table·문장 바뀜 → carry_over(규칙5), by="rule"·새 질문 → new(규칙1·4), by="none"·직전 표 있음 → defer(규칙6: rules 모드에선 원문 새 검색). 그래프 state: reused_table·carried_over·chart_only·interpreted_by |
| `resolved_question` (③) | 실전 1에 넘길 독립 질문 (정답 = 빌더가 라벨을 바꿔 끼운 문장) | Reading.resolved_question · state.resolved_question |
| `split` (③) | `sub_questions` 목록 + `op` diff·sum·ratio·null | `graph/multiquery.py` `split_by_rules` · state.sub_questions·combine_op |
| `outcome` (④) | `answered` · `refused` · `clarify` (kosis_ai `Outcome`) | 실전 1 `judge/rules.py` `judge` → `Verdict.outcome` |
| `judge_rule` (④) | causal · out_of_scope · no_period · partial_range · same_name · vague_item · evaluative · unit_mismatch · not_aggregatable · no_cell · symbol · null | `Verdict.rule` (RULES 11개) |
| `refusal_reason` (④) | RefusalReason 8종 (no_period · no_item · class_mismatch · unit_mismatch · not_aggregatable · causal · missing_value · out_of_scope) | `Verdict.refusal.reason` |
| `default_applied` (④) | 코드가 채운 조건 dict (비어 있지 않으면 "기본값 허용" 문항) | `Verdict.default_applied` |

| `formula` (②) | CombineFn diff · ratio · pct_change · pp_diff · share · per · cagr · index · null | 표가 있어야 나옴: `build_plan`의 CombineStep.fn |
| `chart_request` | bar · line · pie · null (사용자가 말한 종류) | context `chart_request` (ChartType) |
| `chart_kind` | bar · timeline · line · pie · multi_line · grouped_bar · null | 실전 1 ChartKind (자동 선택, T3-37 `auto_chart`와 같은 뜻) — `chart_request`와 다른 열 |

오프라인 규칙 예측(`rule_pred`)은 **정답 표로** 실전 1 규칙을 돌린 값이다 = "검색이 맞았을 때의 규칙 분류 정확도". 검색 오류는 여기에 섞이지 않는다(그건 live e2e).

| 실패 유형 | 문항 | 만드는 법 |
|---|---|---|

| ③ 멀티턴·멀티쿼리 재작성 | ~120 | 멀티턴 ~80: ①의 문항에 후속 턴(시도·연도 이월, 상대 연도 "작년은?", 지시어 "그 표에서", 차트만 "막대로", 주제 전환) — 바뀐 라벨의 셀로 정답 숫자, 정답 독립 질문은 코드가 라벨을 바꿔 끼워 만든다(T3-27 빌더 방식). 멀티쿼리 ~40: 다른 표 두 문항을 한 질문으로 + "둘의 차이는?"(같은 단위만, combine 값 코드 계산), 같은 표 비교 대조군 포함(T3-28 N) |

## Option A — 골든 + 정답 라벨만 (채점 변경 없음)
- 접근: 위 구성을 빌더(`evals/builders/e2e_golden.py`, diverse·multiturn·multiquery 빌더 재사용)로 만든다. 질문 문장은 1단계처럼 Claude가 쓰고 `check_question`이 검사. e2e 기본값 = 단일턴 문항의 `e2e_golden_calc.jsonl`, agent 기본 시나리오에 멀티턴·멀티쿼리 문항 추가. 라벨은 저장만.
- 예상 성능 향상: 정확도 지표는 새로 안 생김. 유형별 문항 수 ②0→~120 · ③(e2e 쪽)0→~120 · ④ 분류 라벨 0→~600 — 사람이 trace를 볼 때 정답이 생김.
- 실질 반영 이점: 예외 처리·질의 이해 평가 근거 문항. 비용 최소.
- 비용·리스크: 1.5일. "어느 분류가 틀렸나"는 여전히 수동.

## Option B — A + 오프라인 규칙 분류 채점 (live 불필요, 추천)
- 접근: A + 빌드 때 현재 규칙 함수(`read_turn(mode="rules")`, `split_by_rules`, 정답 표로 `judge`·`rule_plan`·`build_plan`)를 돌려 `rule_pred`를 기록하고, `run_eval --layer rules`(새 계층, LLM·검색 0)가 라벨별 정확도·혼동표를 낸다.
- 예상 성능 향상: 규칙 분류 정확도 "측정 없음 → 라벨별 실측". 범위 추정: reading·resolved_question은 T3-27 빌더 표현 실측(이월 E 0.800 · 정정 X 0.857 · 지시어 0.941 · 차트만 1.000, 오라클 검색)과 비슷하거나 새 표·말투 때문에 낮음(~0.6~0.9), split은 T3-28 실측(다른 표 두 질문 0.967 · 표 사이 계산 0.600 · 대조군 과분해 0)과 비슷, outcome·judge_rule·qtype·formula는 실전 1 규칙이 90문항 기준으로 맞춰져 있어 새 표에서 ~0.6~0.85(근거: 1단계에서 템플릿 비교 문항의 단위 혼합처럼 새 표에서 처음 드러난 경우가 있었음). 빌드 후 실측으로 대체.
- 실질 반영 이점: A + 결과 검증(분류 단계별 "몇 → 몇"을 비용 0으로 반복, 규칙 수정 PR마다 회귀 확인), 기술 설계(어느 규칙을 LLM으로 바꿀지 T3-10 근거).
- 비용·리스크: 2일. 대형 인구총조사 표의 judge 오프라인 호출 시간. 실전 1 핀이 바뀌면 함수 이름이 바뀔 수 있음(테스트로 감지).

## Option C — B + live e2e 라벨 채점 (e2e 계층을 시나리오 러너로 교체)
- 접근: B + e2e 계층이 `e2e_golden.jsonl`(AgentScenario)을 직접 돌리게 `l4_e2e.py`를 시나리오 러너로 교체하고, 그래프 state(reused_table·carried_over·resolved_question·sub_questions·outcome)와 실전 1 결과를 라벨로 채점.
- 예상 성능 향상: B와 같은 라벨에 검색·LLM 단계까지 포함한 실제 서비스 정확도. 측정은 live run 필요(이번엔 안 돌림).
- 실질 반영 이점: 단일 e2e 진입점(단일턴·멀티턴 한 파일·한 리포트).
- 비용·리스크: 3일+. e2e 계층 교체라 기존 e2e 리포트·Ragas·회귀 게이트(CalcItem 전제)와 호환 작업 필요. live 측정은 별도 비용.

## Recommendation
Option B. 요구(실패 유형 4종 + 규칙 분류 정답 라벨, ~600)를 채우고, live run 없이 규칙 분류 정확도를 바로 숫자로 남긴다. e2e 계층 교체(C)는 live를 돌릴 때 하면 된다(B의 라벨·파일 형식 그대로 씀).
