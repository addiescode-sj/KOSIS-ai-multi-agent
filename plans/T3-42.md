## 현재 구조
- 숫자 `evaluators/agent/numbers.grade_numbers`:
  - calc_qid: 대표 표 셀로 채점 → FAIL이면 `key(=state_key, 마지막 표 키) in expect.alt_table_keys and same_values(item, answer)`로 PASS(via_alternate).
  - calc_qids(멀티쿼리 하위 답): FAIL이면 `same_values`만으로 PASS(표 확인 없음).
  - `same_values` = 골든 required 값이 답의 사실 값 어딘가에 있으면 통과. 기간·지역·분류·aux를 안 봄 → T3-41 규칙보다 느슨.

### 프로토타입 실측 (plan 단계, 같은 before run; 구현 후 같은 숫자가 재채점으로 나와야 함)

- 표 키: 턴의 calc_qid 기준 값 일치 대체 표를 정답에 더하면 상태 정답 **49 → 59턴(0.301 → 0.362)**. 늘어난 10턴은 전부 숫자도 틀려(`wrong_numbers`)

## Idea
"그 표가 이 문항의 대체 정답 표인가"를 agent 계층도 e2e 숫자 채점과 같은 함수(`alternates.alternate_item`)로 답한다.
- 숫자: 답의 출처 표가 대체 표면 remap한 골든으로 같은 채점기를 다시 돈다(e2e `common.grade`와 동일). `same_values` 삭제(`__all__` 포함).
- 표 키: `grade_turn`이 그 턴의 summarize_stat 호출 표 중 calc_qid(·calc_qids[k])의 대체 표인 것을 구해, `expect.model_copy(update={"alt_table_keys": [...]})`로
  state·tools 채점에 넘긴다 → state.py·tools.py 수정 0. 대화 안에서 인정된 대체 표는 calc_qid가 없는 다음 턴(차트만, "이거" 후속)에도 이월.
- 판정은 `(qid, 표 키)`로 메모(Parquet을 값으로 거르는 비용이 턴당 여러 번 들지 않게).
- 테스트: 판정 함수를 주입 가능하게(`alternate_of` 기본값 `alternates.alternate_item`) 하고, 가짜 표(`101_DT_ALT`)를 쓰는 기존 테스트는 tmp Parquet으로 다시 쓴다.

## Option A — 숫자 채점만 통일
- 접근: Idea의 "숫자"만. calc_qid 경로의 `key` 게이트도 답의 출처 표 기준으로 바꾼다. 표 키 판정은 기존 L1 목록 그대로.
- 예상 성능 향상(실측): 숫자 via_alternate 7 → 7, 최종 수치 0.364 그대로. 상태 0.301 그대로.
- 실질 반영 이점: 같은 답이 e2e·agent에서 같은 숫자 판정. 표 확인 없던 멀티쿼리 통과 제거.
- 비용·리스크: 반나절. "숫자는 대체 표로 PASS인데 상태는 lost_state"인 턴이 남음 → 실패 원인 분류가 계속 섞임.

## Option B — 숫자 + 표 키를 채점 시점 판정으로 (on-the-fly)
- 접근: Idea 전부. 시나리오·라벨 파일은 그대로.
- 예상 성능 향상(실측): 상태 정확도 0.301 → 0.362(+10턴), 숫자 변화 0, 대화 성공률 0.079 그대로. 툴 인자 정확도(table_key 필드)는 재채점으로 기록.
- 실질 반영 이점: 숫자·표 키가 e2e 숫자 채점과 한 규칙. lost_state가 "표를 잘못 고름"만 뜻하게 됨(위 10턴은 표가 아니라 숫자 문제로 분류됨).
- 비용·리스크: 1일. e2e의 **정답 표 판정(locate)**은 라벨 파일의 auto·accepted만 인정하는 반면 B는 규칙만 보므로 작은 값·비율 일치(needs_review 수준)도
  인정한다 — e2e 숫자 채점과는 같고 e2e 정답 표 판정보다는 넓다. 지금 needs_review 9건은 모두 accepted라 현재 데이터에서 차이 0.

## Option C — 표 키는 라벨 파일(auto·accepted)로 판정
