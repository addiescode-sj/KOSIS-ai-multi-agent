# T3-66 운영자 메트릭 화면(T3-65 React 화면)에 실제 지표 연결

## Goal
- 완료 기준: T3-65의 메트릭 대시보드가 견본 대신 **실제 DB 지표**(`kosis_store.log_metrics`, T3-57 운영자 화면과 같은 숫자)를 보여 준다. 운영자만 볼 수 있다(T3-57과 같은 카카오 로그인 + 허용 목록, 아니면 아무것도 보이지 않음). 실제 값이 없는 카드는 지어내지 않고 "데이터 없음". 같은 기간·필터에서 T3-57 `/admin/metrics`와 숫자 차이 0.
- Baseline: 대시보드 카드 18개 중 실제 지표 0개(전부 견본, T3-65). 실제 지표는 T3-57 Jinja 화면에서만 볼 수 있음.
- 의존: PR #64(T3-65) 위에 쌓는 브랜치. #64가 먼저 merge되어야 한다.

## 배경 (조사)
- 실제 지표: `log_metrics.METRICS`(SQL)와 `admin/app/queries.metrics()`(탭·필터, 프로세스별 5분 캐시). T3-57은 이 숫자를 다시 계산하지 않는다. 이번에도 같다.
- **기간 제약:** `MetricFilter.check`는 **어제까지**, 최대 90일 전까지만 받는다(하루가 끝나야 숫자가 고정). 그래서 대시보드의 "오늘"은 실제 지표로 보여 줄 수 없다.
- 운영자 인증(`admin/app/auth.py`): 서비스 로그인 쿠키(HTTP는 `kosis_session`, HTTPS는 `__Host-kosis_session`) → `login_sessions` → `ADMIN_USER_IDS`. 로그인 없으면 303(카카오 로그인으로), 허용 목록 밖이면 404(화면이 있다는 것도 알리지 않음, 감사 기록 1행).
- 배포 입구는 `/admin`으로 시작하는 모든 주소를 admin 앱(8100)으로 보낸다(`deploy/k8s/40-ingress.yaml`, Prefix). 그래서 `/admin/api/...`는 입구 설정 변경 없이 같은 주소(origin)에서 admin 앱에 닿는다.

## Option A — 프론트 서버가 admin 앱을 대신 부름 (쿠키 전달)
- 접근: admin 앱에 `GET /admin/api/metrics?tab=&start=&end=&user=&internal=` 추가(기존 `current_operator`·`queries.metrics()` 그대로, JSON + 조회 시각). 프론트 `lib/admin/read.server.ts`가 **서버에서** 이 API를 부른다. 로그인 쿠키 하나만 골라 넘기고(이름은 `auth.cookie_name`과 같은 규칙), `redirect: "manual"`로 303·404를 화면 상태(로그인 필요 / 권한 없음)로 바꾸고, `cache: "no-store"`. 지금처럼 서버 prefetch + `useSuspenseQuery`.
- 예상 성능 향상: 실제 카드 0 → 14, 견본 0, T3-57과 숫자 차이 0(같은 함수).
- 실질 반영 이점: 고객 화면과 같은 패턴(서버 prefetch) 유지.
- 비용·리스크: 1일. 쿠키를 서버가 다른 서비스로 넘기는 코드가 생긴다(이름 규칙·호스트·캐시 실수 시 다른 운영자 데이터가 섞일 위험) → 테스트로 막아야 함. `ADMIN_URL` 설정 추가. admin 앱(김병석 담당)에 엔드포인트 1개.

## Option B — 브라우저가 같은 주소의 `/admin/api`를 바로 부름 (쿠키 전달 없음)
- 접근: A와 같은 admin API. 프론트는 **브라우저에서** `/admin/api/metrics`를 부른다(배포는 입구가 이미 admin 앱으로 보냄, 로컬은 `next.config.ts` dev rewrite로 `/admin/api/*` → `localhost:8100`). 쿠키는 브라우저가 알아서 붙이고, 프론트 서버는 쿠키를 만지지 않는다. 서버 prefetch는 하지 않고 브라우저 `useSuspenseQuery`만(첫 화면에 짧은 불러오기). 401·404는 화면 상태로.
- 예상 성능 향상: A와 같음(실제 14, 견본 0, 차이 0).
- 실질 반영 이점: 인증·권한이 T3-57 그대로 한 곳에만 있다. 쿠키 전달 코드가 없어 보안 검토 범위가 가장 작다. 배포로 넘어갈 때(나중) 입구 변경 없음.
- 비용·리스크: 반나절~1일. 서버 prefetch 패턴에서 벗어남(이 화면만). 303을 따라가지 않게 fetch `redirect: "manual"` 처리 필요.

## Option C — API 없이 T3-57 화면으로 연결
- 접근: React 미리보기에서 견본 숫자를 지우고, 각 탭에 T3-57 `/admin/metrics?tab=…` 링크와 안내만 둔다. admin 앱 변경 0.
- 예상 성능 향상: 견본 0, React 화면의 실제 카드 0(숫자는 T3-57 화면에서 봄).
- 실질 반영 이점: 가장 작고 안전. 숫자가 한 곳에만 있다.
- 비용·리스크: 1~2시간. 요청한 "React 화면에 실제 데이터"는 이루지 못함.

## Recommendation
옵션 B. 실제 숫자를 다시 계산하지 않고(같은 함수), 인증을 새로 만들거나 쿠키를 넘기지 않아 위험이 가장 작다. 배포 입구도 이미 `/admin/*`를 admin 앱으로 보내고 있다. 없는 지표 4개를 채울지는 숫자를 본 뒤 따로 정한다(새 SQL, 별도 태스크).
