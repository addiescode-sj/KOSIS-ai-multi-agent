# T3-43 평가 파이프라인 구조 고정 — 오프라인 / 온라인 / 평가 리포트

## Goal
- 완료 기준 (TASK.md 그대로): 평가 파이프라인 구조 고정: 골든셋 → 오프라인(고정 골든셋·Ragas·기준선 비교·회귀 게이트) / 온라인(trace 수집·표본 평가·
  품질 저하 감지·실패 케이스 수집) → 평가 리포트(지표별 점수·실패 유형·이전 버전 대비 변화). `scripts/dev.sh`에서 오프라인 스위트(e2e → ragas → 게이트)와
  온라인 평가를 한 명령으로, pytest
- 사용자 요청 (2026-11-17): PR #29(`T3-41-alternate-tables`)에서 Ragas를 `scripts/dev.sh`에 통합해 한꺼번에 돌리고, 오프라인·온라인 구조를 아래 그림대로 고정.

```
                         Golden Dataset (질문 · 기준 정답 · 정답 통계표 ID · 기대 계산 결과)
                                   ↓
   Offline Evaluation (개발 / PR / 배포 전)          Online Evaluation (실제 사용자 요청)
   고정 Golden Set · Ragas 평가 · Baseline 비교       Trace 수집 · 표본 추출 평가
   · Regression Gate                                   · 품질 저하 감지 · 실패 케이스 수집
                                   ↓
                 Evaluation Report (지표별 점수 · 실패 유형 · 이전 버전 대비 변화)
```

## Baseline
- 오프라인: `bash scripts/dev.sh suite`가 L0~L4·agent를 돌리고 같은 조건 기준 run과 비교. **Ragas는 스위트 밖**(e2e 뒤 수동 실행), **회귀 게이트는 CI pytest에만**.
  dev.sh는 `uv run --group embed`로 실행돼 **ragas 그룹을 sync로 지운다**(eval·suite 41행, api 51행 둘 다).
- 온라인: 서비스 trace(T3-30)에 루트 `invoke_agent`(`kosis.outcome`·`kosis.no_answer_reason`)와 툴 span(인자·결과 JSON)이 있지만
  **사용자 질문과 최종 답 문장이 없다**(루트 속성 확인: `start_turn`·`_turn_done`). 검색 툴 인자는 context 노드가 재작성한 질의이고, 지시어 턴은 검색 호출이 없고,
  combine·거절 문장·마무리 문장은 summarize_stat 결과에 없다 → **trace만으로 턴 복원 불가. 온라인 평가 경로 0.**
- 실측 (온라인 검사 대상 규모, 실제 HCX 멀티턴 run 163턴 `20261117-140003-T3-42-after-live`): 답함 128 · 오류 16 · 계산 툴 없음 14 · 거절 5,
  최종 답 근거 없는 숫자 턴 0 · 출처 누락 턴 0(agent 계층 `answer.py` 규칙).

## Idea (공통: 오프라인 + 리포트)
- **스위트에 Ragas·게이트**: `evals.suite`가 e2e 다음에 ragas run을 돈다. RUNS 인자가 고정이라 run 루프에서 이번 스위트의 e2e 폴더를 `--from-run`으로 넘기는 특별 처리.
  e2e가 skip·실패·**mock**이면 ragas skip(mock 기록이 커밋되는 quality_history를 오염시키지 않게). 필요 조건 `judge`(OPENAI_API_KEY·ragas import).
- **게이트**: `quality.check()`(history의 최신)가 아니라 **이번 ragas run의 summary를 `compare()`에 직접** 넣는다. 비교 대상이 없으면(키 다름·ragas skip) "게이트 skipped"로
  표시하고 통과로 치지 않는다. exit: run 실패 1, 게이트 하락 2(구분).
- **리포트**: suite.md/html에 ragas 지표·e2e 실패 유형(`summary.failures` 단계별 수)·게이트 표(기준·이번·허용폭·통과).
- **dev.sh**: `uv run --group embed --group ragas`(eval·suite·api). `default-groups`는 CI `uv sync --frozen`까지 torch를 깔게 되어 안 씀.

## Option A — 오프라인만
- 접근: 공통 절만. 온라인은 구조 문서만 남기고 구현 0.
- 예상 성능 향상: 한 명령에 Ragas·게이트 포함(수동 단계 2 → 0), 게이트 결과가 리포트에 0 → 9개 지표. 온라인 0 그대로.
- 실질 반영 이점: PR 전 회귀 확인이 한 명령. 그림 오른쪽 미구현.
- 비용·리스크: 반나절.

## Option B — 오프라인 + 온라인: 서비스 trace 루트에 질문·답을 남기고 Jaeger에서 읽기
- 접근: 공통 절 +
  1. **서비스 계측 보강**(서비스 코드 소량): `/chat`·`/chat/stream`의 턴 루트 span에 `kosis.turn.question`(사용자 원문)·`kosis.turn.answer`(ChatResult 답)·
     `kosis.turn.table_key` 속성. 답 숫자는 이미 툴 결과 span에 있다. 답·그래프 동작 변경 0(패리티 pytest).
  2. **`--layer online`**: Jaeger API(`service=kosis-agent`, `deployment.environment.name=service`, `--lookback`)에서 턴 trace를 읽어 agent 기록과 같은 모양
     {question, answer, calls, outcome, trace_id}으로 복원. `--from-run <agent run>`도 받음(같은 모양, 재현·검증용).
  3. **평가**: 전 턴 코드 검사 = agent 계층 `answer.py`의 근거 없는 최종 숫자·출처 누락(대화 근거 누적, 같은 대화 trace를 `gen_ai.conversation.id`로 묶음) + 결과 분포
     (답함·거절(no_answer_reason별)·실패·오류). 답한 턴 중 표본 K=40(시드 고정)에 Ragas Faithfulness(근거 = 그 턴 summarize_stat 사실)·Response Relevancy
     (user_input = 검색 툴의 재작성 질의가 있으면 그것, 멀티턴 후속 "그럼 서울은?"을 단독 심판하면 낮게 나오므로). `eval.online` span으로 원 trace에 link.
  4. **저하 감지**: 온라인 집계는 **커밋되는 quality_history와 분리**해 `evals/datasets/online_history.jsonl`(gitignored)에 기록. 같은 키(심판·환경) 직전 기록 3개 이상일 때만
     중앙값과 비교, 허용폭 = max(심판 흔들림 0.03, 2 × 표본 표준오차)(K=40이면 표준오차가 0.03보다 큼 → 트래픽 변동으로 인한 오경보 방지). 저하면 리포트 표시 + exit 3.
  5. **실패 케이스 수집**: `evals/datasets/online_failures.jsonl`(gitignored, 로컬 전용) — 유형별: 오류·실패, 근거 없는 숫자, 출처 누락, Faithfulness < 0.5, 거절은
     no_answer_reason별 "검토 필요"로 따로(정당한 거절과 섞지 않음). trace_id로 중복 제거, 보존 30일(쓸 때 오래된 줄 정리). 골든셋 후보 입구(사람 검토 후 추가).
  6. **dev.sh**: `online` 모드(Jaeger 기동 후 `--layer online`), `pipeline` 모드(suite → online, 두 리포트 경로 출력, exit 코드 유지).
- 예상 성능 향상: 온라인 평가 경로 0 → 1. 검증(실제 HCX run 163턴을 온라인 입력으로): 코드 검사 163/163턴, Ragas 표본 40턴, 실패 케이스 수집(오류 16 + 거절 5 검토 +
  심판 저점), 저하 감지는 표본 답을 인위 훼손한 기록으로 감지 확인. trace 복원 경로는 로컬 서비스(mock 실전 1, stage 2 끔 → 모델 호출 0)에 요청 몇 개를 보내 Jaeger→온라인으로 확인.
- 실질 반영 이점: 그림 전체가 코드. 운영 중 근거 없는 숫자·출처 누락·오류가 trace 단위로 잡혀 골든셋 후보로 쌓인다(데이터 정확성·결과 검증). trace가 이미 쓰는 채널이라 새 저장소 없음.
- 비용·리스크: 1.5일. 서비스 코드 변경(루트 span 속성 3개). Jaeger 기본은 메모리 저장 → 재시작하면 trace 소실(운영 저장소 설정은 범위 밖, 리포트에 수집 기간 표시).
  툴 결과 JSON이 큰 span은 OTLP 4 MB 배치 한도에 걸릴 수 있음 → 이번엔 측정만(유실 수를 리포트에 표시).
