# T3-00 레포 초기 세팅

## Goal
- 완료 기준 (TASK.md 그대로): 실전 1·2 submodule(`vendor/phase1`, `vendor/phase2`), 하네스(skill·hook·agents·AGENTS.md·CLAUDE.md) 팀 공유 이식, 기술 스택 골격(FastAPI·LangGraph·Next.js·Docker Compose·CI), `scripts/verify.sh` OK
- Baseline: baseline 없음 (커밋 0. submodule 2개와 실전 2에서 복사한 하네스·frontend만 untracked로 있음)

## Idea
실전 2 레포가 실전 1을 `vendor/phase1` submodule로 import한 방식을 그대로 확장한다.

1. submodule: `vendor/phase1` = KOSIS-ai-nlp-summary @ `e248a45` (실전 2가 고정한 커밋과 같게, `kosis_ai.schemas` 계약 일치),
   `vendor/phase2` = KOSIS-ai-RAG @ `484bd06` (master). 실전 2 안의 중첩 submodule은 init하지 않는다 (phase1 중복).
2. 하네스: 실전 2의 `.claude/`(agents·hooks·skills·settings.json), AGENTS.md, `scripts/*.ts`, `.mcp.json`, PR 템플릿,
   `docs/templates/`를 그대로 복사해 커밋한다 (`settings.local.json`만 개인용으로 gitignore). CLAUDE.md는 Phase 3 내용으로 새로 쓴다.
3. import 경로: `pytest.ini` `pythonpath = . src vendor/phase2 vendor/phase2/src vendor/phase1 vendor/phase1/src`.
   `testpaths = tests`로 이 레포 tests만 돈다 (실전 1·2 tests·conftest는 수집 안 함).
   충돌은 `backend` 하나: 이 레포 `backend/app`이 실전 2 `backend.app`을 가린다. 실전 2 API(`backend.app.main`)는 import하지 않고
   로직(`kosis_rag.graph` 등)만 import한다고 CLAUDE.md에 적는다. 나머지(`eval`·`evals`·`kosis_chat`·`kosis_ai`·`kosis_rag`·`kosis_agent`)는 겹치지 않는다.
4. 데이터·비밀값 경로: 실전 1은 `KOSIS_WORKSPACE`를 따르지만 실전 2 `kosis_rag`는 `data/`·`.env`를 `vendor/phase2/` 아래로 고정한다(`parents[2]`).
   T3-00은 이 레포 루트를 `KOSIS_WORKSPACE`로 쓰고(backend·conftest가 설정), backend가 루트 `.env`를 먼저 읽는다(load_env는 기존 값을 덮지 않음).
   실전 2 데이터 경로를 `KOSIS_WORKSPACE`로 따르게 하는 수정은 실전 2 레포 PR로 T3-01(툴 래핑) 전에 처리한다. 그 전까지 검색 툴은 `vendor/phase2/data`가 필요하다.
5. 기술 스택 골격은 옵션별로 다르다 (아래).

## Option A — 하네스·submodule만
- 접근: 1~3만. 의존성(`pyproject.toml`)·`verify.sh`·pytest 1개(실전 1·2 import 스모크). 백엔드·프론트·compose는 각 태스크(T3-03, T3-11, M3)에서 만든다.
- 예상 성능 향상: 지표 없음. 다음 태스크 착수 시간 단축은 작다 (각자 골격부터 다시 만들어야 함).
- 실질 반영 이점: 가장 작은 diff. 구조 결정을 담당자에게 남긴다.
- 비용·리스크: 30분. 세 트랙이 동시에 backend/compose를 만들면 충돌 (M1 인터페이스 고정과 어긋남).

## Option B — A + 실행 가능한 스택 골격 (로컬·CI까지)
- 접근: A + `src/kosis_agent/graph.py`(LangGraph StateGraph 1노드, T3-03이 ReAct로 교체) + `backend/app/main.py`(FastAPI `/health`, `/chat/stream` SSE)
  + 실전 2 프론트(Next.js 16·Tailwind·shadcn·Vercel AI SDK) 복사 후 `/chat/stream` 연결 + `docker-compose.yml`(backend·frontend·chroma·postgres·redis·jaeger(obs))
  + GitHub Actions CI(`verify.sh`). 의존성에 SQLAlchemy·psycopg·redis·OTel 포함, Ragas·임베딩은 선택 group. K8s·AWS는 M6로 미룬다.
- 예상 성능 향상: 지표 없음. M1·M3 착수 시점에 "질문 → 그래프 → SSE → UI" 경로 0 → 1 (오프라인 pytest로 확인).
- 실질 반영 이점: 기술 설계(기술 스택 전부 compose에서 기동), 세 트랙이 같은 그래프·API 파일 위에서 시작. 실전 2 UI 재사용.
- 비용·리스크: 반나절(프론트 연결·compose 6서비스·CI 포함). 1노드 그래프는 T3-03에서 갈아엎는 임시 코드 (작게 유지). Postgres·Redis는 서비스만 띄우고 코드 연결은 KOS-86·M3.

### Option B' — B에서 Postgres·Redis 제외 (리뷰 제안)

## Option C — B + K8s·AWS 배포 골격
- 접근: B + `deploy/k8s/` 매니페스트(backend·frontend·chroma·redis·postgres·jaeger) + ECR push·EKS 배포 GitHub Actions CD + IaC.
- 예상 성능 향상: 지표 없음. M6 착수 시간 단축.
- 실질 반영 이점: 인프라 트랙 선행.
- 비용·리스크: 하루+. AWS 계정·클러스터·비용 결정 전이라 검증 불가한 매니페스트가 된다. 인프라 담당(신규 모집 중)의 설계를 선점한다.
