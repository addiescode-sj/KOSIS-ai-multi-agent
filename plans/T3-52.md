## Idea
검수는 "쓰기는 거의 없고 넓게 읽는" 분석(OLAP)형 작업이고, 로그 테이블은 질문마다 쓰는 거래(OLTP)형이다. 그래서 선택지는 세 가지다.
1. 정규화를 그대로 두고, 검수 쿼리 모양에 맞춘 **복합 인덱스**로 빠르게 한다.
2. 검수만을 위한 **비정규화 테이블**을 따로 만든다(읽기 전용, 배치로 채움).
3. 질문 행에 **조인 대신 쓸 값만 조금** 붙인다(부분 비정규화).

어느 옵션이든 검수 쿼리를 먼저 코드(`log_metrics.py`의 검수 조회 함수)로 정하고, 인덱스는 그 쿼리에 맞춘다. 측정은 버리는 Docker `pgvector/pgvector:0.8.1-pg17`에 지어낸 데이터(request_logs 20만 행: 답함 80%·거절 10%·되묻기 4%·오류(`failed`+`error`) 3%·이탈 3%, 세션 5천 개, 90일에 고르게 / ui_events 100만 행 중 피드백 10%)를 넣고 `EXPLAIN (ANALYZE, BUFFERS)` 전·후로 잰다. 골든셋·제공 데이터는 쓰지 않는다.

검수 쿼리 세 개:
| 이름 | 검수 내용 | WHERE / ORDER BY |
|---|---|---|
| R1 | 결과별 기간 검수: 기간 안의 한 결과(예: 거절) 질문과 사유. 결과는 한 번에 하나(저장 값 `refused`·`clarify`·`failed`·`error`·`aborted`를 따로) | `outcome = :o AND created_at` 범위, `ORDER BY created_at DESC LIMIT` (전체 건수는 따로 `count`) |
| R2 | 사용자별 기간 검수: 한 세션의 기간 안 질문 흐름 | `session_id = :s AND created_at` 범위, `ORDER BY created_at` |
| R3 | 기간 안 질문마다 마지막 피드백 (👎 답 목록·👍 비율과 같은 규칙) | 기간 안 질문을 먼저 고르고, 질문마다 `LATERAL (SELECT ... FROM ui_events WHERE request_id = t.request_id AND event_type = 'feedback' ORDER BY client_ts DESC, received_at DESC, event_id DESC LIMIT 1)` |

## Option A — 정규화 유지 + 복합 인덱스 (WikiDocs 원칙)
- 접근: 검수 조회 함수 `review_turns(session, flt, outcome=None, session_id=None, page, size)` 하나로 R1·R2를 받고(`request_logs` 직접 조회, 공통 필터 그대로), 각 행에 R3 방식(LATERAL 한 건)으로 마지막 피드백 값·선택지를 붙인다. 전체 건수는 `review_count(...)`로 따로. alembic `0005_review_indexes`:
  - `ix_request_logs_outcome_created (outcome, created_at)` — R1, 같다 조건 먼저·기간 다음
  - `ix_request_logs_session_created (session_id, created_at)` — R2. 기존 단일 `ix_request_logs_session_id`는 이 인덱스의 앞부분과 같아 지운다(중복 인덱스는 쓰기만 늘림)
  - `ix_ui_events_last_feedback (request_id, client_ts DESC, received_at DESC, event_id DESC) WHERE event_type = 'feedback' AND request_id IS NOT NULL` — R3의 질문마다 한 건 꺼내기와 순서가 같음. 검수 함수는 이 LATERAL 모양으로 쓴다. T3-49 메트릭의 `fb` CTE(`DISTINCT ON`, 기간 조건이 안으로 안 내려감)는 이번에 바꾸지 않으므로 메트릭 화면은 이 인덱스로 빨라진다고 보장하지 않는다(리뷰 3)
  - 모델: `log_models.py`의 `session_id` `index=True`를 빼고 `__table_args__`에 세 `Index`(부분 조건은 `postgresql_where`, DESC는 `.desc()`)를 넣는다. alembic은 DESC·부분 조건을 비교하지 않으므로 `pg_indexes.indexdef`를 pytest로 확인
  - 정리: 중복 정의된 `purge_rewrites`·`purge_texts`를 하나로
  - 벡터 조사명 인덱스는 넣지 않는다(크기가 작아 이득이 측정되지 않을 가능성이 높고, JSONB 식 인덱스는 alembic 비교에서 거짓 차이 위험).
- 예상 성능 향상: R1은 기간 안 전체 행 → 그 결과의 행만, 인덱스 순서로 읽어 정렬도 없음. 이론상 최대 배수 ≈ 1 / (그 결과의 비중)(지어낸 데이터: 거절 10%면 약 10배, 오류 3%면 약 30배), `LIMIT`가 있으면 첫 페이지는 더 빠름. R2는 세션 인덱스로 찾은 뒤 기간을 다시 거르던 것을 인덱스 범위 한 번으로, 세션당 행이 많을수록 이득. R3는 "전 기간 피드백 전체 읽기 + 정렬" → "기간 안 질문 수 × 한 건"이라 기간 비율만큼(하루/90일) 줄어듦. 배수는 측정으로 정한다.
- 실질 반영 이점: 데이터 정확성 검수(결과·사유 대조)와 질의 이해 검수(한 사용자의 흐름)가 같은 조회 함수로 된다. 스키마는 그대로라 무결성·90일 삭제 규칙에 변화 없음.
- 비용·리스크: 반나절. 질문마다 쓰는 `request_logs`는 인덱스가 2개 늘고 1개 줄어(순 +1) 쓰기마다 인덱스 갱신이 하나 더 생긴다. `ui_events`의 새 인덱스는 피드백 행에만 갱신. alembic은 부분 인덱스의 WHERE를 비교하지 않으므로 `pg_indexes.indexdef`를 pytest로 확인.

## Option B — 검수 전용 비정규화 테이블 (F-Lab 원칙: OLAP 쪽 비정규화)
- 접근: `review_snapshot` 테이블(질문 1건 = 1행)에 질문 행 + 마지막 피드백(값·선택지·가린 이유) + 다시 쓴 질문(가린 문장, ` / `로 이음) + 해석 종류를 미리 합쳐 둔다. 일별 배치(KOS-167, `daily_usage`와 같은 자리)가 전날 것을 다시 만든다. 이 테이블에 `(outcome, created_at)`, `(session_id, created_at)` 인덱스.
- 예상 성능 향상: 검수 조회가 조인·정렬 없이 한 테이블 한 번 읽기. 피드백이 붙은 목록에서 A보다 빠름(조인 제거). 대신 하루 늦은 데이터.
- 실질 반영 이점: 검수 화면·BI가 이 테이블 하나만 읽으면 된다. 서비스 쓰기 경로는 건드리지 않음.
- 비용·리스크: 하루 이상. 원문(질문·다시 쓴 질문·이유)이 두 곳에 있게 되어 90일 삭제가 이 테이블에도 닿아야 한다(개인정보·무결성 관리 비용, F-Lab이 말한 비정규화의 단점). 원본이 바뀌면(늦게 온 피드백) 다시 만들어야 맞는다.

## Option C — 질문 행에 조회용 값만 붙이기 (부분 비정규화)
- 접근: A의 R1·R2 인덱스를 그대로 두고(그래서 C는 A를 포함한다), `request_logs`에 원문이 아닌 값만 추가: `last_feedback`(`up`·`down`), `last_feedback_choice`, `feedback_at`. 피드백 이벤트가 들어올 때 수집기가 해당 질문 행을 갱신(마지막 값 규칙: `client_ts`가 더 늦을 때만). 인덱스는 A의 R1·R2 두 개 + `(last_feedback, created_at)`.
- 예상 성능 향상: 👎 답 목록·👍 비율이 `ui_events` 조인과 `DISTINCT ON` 없이 질문 행만 읽음. 피드백 읽기가 "모든 기간의 피드백 전체"에서 "기간 안 질문 행"으로 줄어 기간 비율만큼(하루/90일) 이득.
- 실질 반영 이점: 원문을 복사하지 않아 90일 삭제와 무관, 메트릭 화면도 같이 빨라짐.
- 비용·리스크: 하루. 쓰기 경로(수집기)가 이벤트마다 UPDATE를 하나 더 하고, 늦게 오거나 순서가 바뀐 피드백의 "마지막" 판단을 쓰기 시점에 맞게 해야 함(T3-49 규칙과 어긋나면 숫자가 달라짐). 이미 머지된 T3-48·49 코드를 바꿈.

## Recommendation
옵션 A. 지금 할 일은 A이고, B는 하지 않으며, C는 측정으로 필요가 확인될 때만 한다(아래 순서).
