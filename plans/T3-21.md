  - 기준 run과의 비교는 scratchpad 스크립트로 손으로 함(`report.md` diff).

## Idea
1. **`--llm hcx|mock`** (`run_eval` l3·e2e): `runners.stat.run`·`runners.e2e.run`이 받아 `ops.usage_client(load_settings(backend=…, model_name=…))`로 넘긴다
   (실전 1이 이미 받는 덮어쓰기; 두 runner 시그니처에 인자 하나씩 추가).
   mock에서 일어나는 일(리뷰 확인): `[mock] answer`는 compose 파싱 실패 → 재시도 1회 → **코드 템플릿 답**이 나와 L3 판정이 그럴듯해 보일 수 있고,
   fallback 챗봇으로 가는 문항은 오류 행이 된다. 그래서 mock run은 **경로 확인용**으로만 쓰고 점수로 쓰지 않는다:
   manifest·리포트 제목에 `llm: mock`, 모델 이름 `mock`, **ops_history에는 기록하지 않음**(커밋되는 기록에 HCX로 남지 않게).
2. **`run_eval.main`이 run 폴더를 돌려준다**(지금은 0) — 스위트가 결과를 읽기 위해.
3. **사전 점검**: 계층마다 필요한 것을 코드로 확인, 없으면 그 run을 건너뛰고 이유를 적는다.
   데이터(`data/tables.jsonl`·`values/`·`sigungu.json`), 골든 파일, Chroma heartbeat + 컬렉션(`CHROMA_COLLECTION`), `EMBED_CKPT`·`RERANK_CKPT` 파일, HCX 키(`--llm hcx`일 때), agent 시나리오·`--agent`. 키 값은 출력하지 않는다.
4. **실행**: run 목록을 차례로 `run_eval.main(argv)`. run마다 `SystemExit`·예외를 잡아 "실패: 사유"로 기록하고 다음 run으로 간다.
   stage는 `<접두어>-<run 이름>`(같은 초에 두 run이 같은 폴더 이름이 되는 것 방지).
5. **기준 run 찾기**: `--baseline <접두어 | run 폴더…>`. 접두어면 그 접두어의 run 중 **조건이 같은 것**을 manifest로 고른다 —
   계층·검색기·골든 해시·split·top_k·재채점 여부(`from_run`)·`llm`(없으면 hcx). 조건이 같은 run이 없으면 "조건 같은 기준 없음".
6. **비교 표**: 계층별 핵심 지표(L1 Hit@1·Hit@5·MRR·답 없음 F1, L2 all_fields·regions, L0 적재 일치·채움률, L3·e2e PASS·FAIL, agent 대화 성공률·툴 선택·상태)를 한 곳에 정의하고
   기준과 나란히 + 차이. 결과는 `evals/reports/<시각>-<접두어>-suite/`의 `suite.md`·`suite.json`과, `report_html.md_html`로 만든 `suite.html`(각 run의 report.html 링크).
7. **README**: 테스트 방법 절 — 준비(Docker·Chroma·셸 값), mock → HCX 순서, 계층별 명령과 비용, 한 번에 돌리기, 결과 읽기, 자주 나는 오류(PYTHONPATH 등).
- 테스트: 점검(가짜 환경)·기준 찾기(가짜 manifest)·비교 표·실패 run 기록을 pytest로(서버 없이). 이 PC에서 서버 없이 되는 run으로 스위트를 실제 실행.

## Option A — 셸 스크립트 + `--llm`
- 접근: 1·2 + `scripts/eval_all.sh <접두어> [mock|hcx]`가 정해진 명령을 순서대로. 점검은 파일 존재·포트 열림 정도, 비교 없음(run 폴더 목록 출력).
- 예상 효과: 손으로 치는 명령 9 → 1, L3·e2e 경로 확인 HCX 약 270회 → 0(mock). 전→후 비교는 여전히 손으로.
- 실질 반영 이점: 절차 재현. 반나절 미만.
- 비용·리스크: Windows 팀원은 bash가 없을 수 있음. 컬렉션 존재·체크포인트 같은 점검과 실패 run 계속 진행이 셸로는 어려움.
