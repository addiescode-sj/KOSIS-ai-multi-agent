# T3-18 PostgreSQL + SQLAlchemy ORM (Linear KOS-86)

## Goal
- 완료 기준 (TASK.md 그대로): 대화 기록·평가 결과 ORM 모델, compose `postgres`에 테이블 생성, 실제 PostgreSQL에서 쓰기·읽기 확인, pytest. API·대화 상태 연결(T3-04)은 범위 밖
- 마감: M2 11/14. KOS-86은 KOS-40(T3-04 대화 상태)을 막고 있다.
- 범위(사용자 지시 11/05): **ORM과 PostgreSQL까지만.** FastAPI `/chat/stream`에서 저장하는 연결, 대화 상태 복원, 보관 기간 삭제 작업은 하지 않는다.
- Baseline: 없음. compose에 `postgres:17-alpine` 서비스와 `DATABASE_URL`(backend), 의존성 `sqlalchemy>=2.0`·`psycopg[binary]>=3.2`는 T3-00에서 들어와 있지만 쓰는 코드가 없다(`docs/current-state.md`).

## 저장할 것 (지금 코드에서 나오는 모양)
- 대화: `/chat/stream`은 질문 1개를 받아 노드 이벤트, 토큰, 마지막 `SearchResult`(답·인용 표)를 낸다. 멀티턴(T3-04)이 붙으면 대화 하나에 턴이 여러 개다.
- 평가: `evals/reports/ops_history.jsonl` 한 줄이 실행 1회 집계다(`run_id`, `layer`, `stage`, `target`, 지연 p50·p95, 토큰, 비용, 실패율). 이 파일은 커밋되는 집계라 바로 적재할 수 있다.

## 공통 (세 옵션 모두)
- 위치: `src/kosis_store/` — `db.py`(엔진·세션, `DATABASE_URL`), `models.py`(ORM). 다른 패키지에 의존하지 않는다.
- 테이블 3개
  - `conversations`: `id`(UUID), `created_at`(인덱스)
  - `messages`: `id`, `conversation_id`(FK, 대화 삭제 시 함께 삭제), `turn`, `role`(user·assistant), `content`(질문 원문 또는 답 문장), `result`(JSON, `SearchResult` 그대로), `created_at`
  - `eval_runs`: ops_history 한 줄 = 한 행. `run_id`(PK), `layer`, `stage`, `target`, `latency_p50_ms`, `latency_p95_ms`, `input_tokens`, `output_tokens`, `cost`, `currency`, `tool_failure_rate`, `retry_rate`, `created_at`
  - `conversations.title`, 출처 표·노드 지연·문항별 판정 테이블은 쓰는 코드가 생길 때(T3-04·T3-06) 만든다.
- 이식 가능한 타입: SQLAlchemy 2.0 `Uuid`, `JSON().with_variant(JSONB, "postgresql")`. 오프라인 pytest는 SQLite 메모리 DB로 돈다.
- 개인정보·보안
  - `messages.content`·`result`에는 **사용자 질문 원문이 그대로 저장된다.** 사용자 식별자 테이블은 만들지 않고 대화는 임의 UUID로만 묶는다. 보관 기간(계획서 초안 30일, 팀 확정 전)이 지나면 `created_at` 기준으로 대화를 지운다 — 삭제 작업은 범위 밖, 계약 문서에 정책만 적는다.
  - 평가 테이블에는 골든 질문 문장·정답·문항 ID를 넣지 않는다(집계만).
  - compose `postgres` 포트를 `127.0.0.1:5432:5432`로 바꿔 호스트 밖에 열지 않는다. 비밀번호 기본값(`kosis`)은 로컬 개발용임을 `.env.example`에 적는다.
- PostgreSQL 테스트 격리: `TEST_DATABASE_URL`(예: `localhost:5432`의 별도 DB `kosis_test`)이 있을 때만 도는 `postgres` 마커 테스트. backend가 쓰는 `DATABASE_URL`은 테스트에서 쓰지 않는다. 테스트는 시작할 때 테이블을 만들고 끝날 때 지운다. `scripts/verify.sh`(CI)에는 `TEST_DATABASE_URL`이 없으므로 건너뛴다.

## Option A — 3개 테이블 + `create_all`
- 접근: `Base.metadata.create_all(engine)`을 부르는 `python -m kosis_store.init` 한 줄로 테이블을 만든다.
- 예상 성능 향상: 지표 없음 → 다음 단계 영향: T3-04가 `messages`로 이전 턴을 읽을 수 있다. 평가 실행 기록 조회가 jsonl 파싱에서 SQL로.
- 실질 반영 이점: 가장 빨리 끝나고 T3-04 선행 조건을 바로 푼다. 의존성 추가 없음.
- 비용·리스크: 0.5일. 열을 추가·변경하면 `create_all`이 기존 테이블을 고치지 못해, 이미 쌓인 대화가 있으면 손으로 옮기거나 지워야 한다.

## Option B — 3개 테이블 + Alembic 첫 마이그레이션
- 접근: A와 같은 모델에 `alembic` 의존성과 `migrations/0001_initial`을 더한다. 운영·로컬 DB는 `alembic upgrade head`로 만든다. PostgreSQL 테스트에서 `upgrade head` 후 `compare_metadata`로 모델과 마이그레이션이 같은지 확인한다.
- 예상 성능 향상: 지표 없음 → T3-04·T3-06이 테이블·열을 더할 때 `0002`부터 마이그레이션으로 쌓을 수 있다.
- 실질 반영 이점: 스키마 변경 이력이 코드로 남고, M6 배포(K8s·AWS)에서 같은 명령으로 DB를 맞춘다. 기술 설계 근거가 된다.
- 비용·리스크: 1일. 의존성 1개 추가. SQLite 오프라인 테스트는 `create_all`, PostgreSQL은 마이그레이션이라 둘이 어긋날 수 있어 `compare_metadata` 테스트로 막는다.

## Option C — 정규화 테이블 추가 + Alembic
- 접근: B에 더해 `citations`(메시지별 인용 표 키·순위), `tool_calls`(노드별 지연·payload) 테이블을 지금 만들고, `SearchResult`를 이 테이블들로 나눠 넣는 변환 함수까지 둔다.
- 예상 성능 향상: 지표 없음 → T3-06의 툴 정확도·노드 지연, 출처 정밀도를 SQL로 바로 셀 수 있다.
- 실질 반영 이점: 평가·분석 쿼리가 쉬워진다.
- 비용·리스크: 1.5~2일. API 연결이 범위 밖이라 지금은 쓰는 곳이 없고, T3-04·T3-06이 실제로 쓰면서 모양이 바뀔 가능성이 크다(필요한 것만 만든다는 원칙과 충돌).

## Recommendation
**Option B.** 마감 안에 끝나고, 지금 쓸 3개 테이블만 만들면서 이후 변경을 마이그레이션으로 쌓을 수 있다. C의 정규화 테이블은 T3-04·T3-06이 실제로 쓸 때 `0002`로 더한다.

## Decision
Option B (3개 테이블 + Alembic 첫 마이그레이션), 2026-11-05 사용자 선택. API 연결은 하지 않는다.

| 항목 | 전 | 후 |
|---|---|---|
| PostgreSQL을 쓰는 코드 | 없음 (compose 서비스만) | `src/kosis_store` ORM 3개 테이블 + Alembic `0001` |
| 테이블 생성 | — | `alembic upgrade head` → `conversations`·`messages`·`eval_runs`·`alembic_version`, `alembic current` = `0001 (head)` |

| 쓰기·읽기 (실제 PostgreSQL) | — | 2턴 대화 3개 메시지 저장·순서대로 읽기, `SearchResult` JSON 그대로, DB 수준 `ON DELETE CASCADE`로 메시지 0건 |
| 평가 실행 적재 | jsonl 파싱만 | `ops_history.jsonl` 53줄 → 47행(`run_id` 47종, 같은 `run_id`가 두 번 적힌 줄 6개는 한 번만), 0.05초, 다시 적재해도 0건 추가. 계층별 p50 지연 중앙값을 SQL 한 줄로 집계 |
| 포트 공개 | `5432` 모든 주소 | `127.0.0.1:5432`만 |

- pytest `tests/test_store.py` 5개: 오프라인(SQLite) 3개 통과, PostgreSQL 2개는 `TEST_DATABASE_URL`(버리는 DB `kosis_test`)로 통과. CI·기본 실행에서는 건너뛴다.
- 의존성 `alembic>=1.13` 추가(pyproject). 이 PC에는 `uv`가 없어 `uv.lock`은 갱신하지 못했다 — `uv lock`이 필요하다.
- 예상과 차이: SQLite는 외래 키가 기본으로 꺼져 있어 첫 오프라인 테스트에서 연쇄 삭제가 동작하지 않았다. 테스트 엔진에서 `PRAGMA foreign_keys=ON`을 켜 PostgreSQL과 같게 맞췄다.
- 문서: `docs/store.md`(테이블, 개인정보·보안, 실행, 테스트), `.env.example`에 PostgreSQL 변수.
- 남은 일: `/chat/stream`에서 저장(T3-04), 보관 기간 삭제 작업, `uv lock`.
