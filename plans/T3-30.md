# T3-30 서비스 실시간 trace + FastAPI 엔드포인트

## Goal
- 완료 기준 (TASK.md 그대로): backend API 요청마다 그래프 노드·툴·LLM span이 실시간 OTel trace로 남고(service `kosis-agent`,
  평가 provider와 분리), 그래프 노드 기준 엔드포인트(챗 SSE 토큰 스트리밍·동기 챗·툴별·대화 상태)를 둔다.
  Swagger API 문서, 답 문장·숫자는 지금과 같다(회귀 0), pytest. 대화 기록 저장은 KOS-183.
- Baseline (코드 확인, 2026-11-11):
  - 서비스 요청의 trace: **0** (`backend/app/main.py`는 콜백을 붙이지 않음. `LiveSpans`는 평가 runner만 씀)
  - 엔드포인트: `/health`, `/chat/stream` **2개**. 툴(`search_tables`·`summarize_stat`·`make_chart`)을 따로 부를 길 없음
  - 토큰 이벤트: **0**. 프런트(`frontend/app/api/chat/route.ts`)는 `token` 이벤트를 draft로 그릴 준비가 돼 있으나
    백엔드가 보내지 않아 답 문장은 `result`에서 한 번에 나온다 (첫 글자까지 시간 = 턴 전체 지연)
  - 대화 기록: Postgres ORM(`kosis_store.Conversation/Message`, T3-18) 있음, API는 쓰지 않음
  - 평가 쪽 KOS-114 항목은 T3-06에서 끝남: `LiveSpans`(노드 이름 하드코딩 없음) + `evals/runners/agent.py`
    `link_verdicts`(채점 뒤 `eval.scenario` span이 턴 루트 span에 Link). 이 태스크는 **서비스 쪽**만 남았다.

## Idea
1. **관측(서비스)과 평가를 provider 단위로 나눈다.** 공용은 콜백 하나(`kosis_agent.observability.tracing.LiveSpans`·
   `agent_turn`)뿐이다.
   - 서비스: `backend/app/telemetry.py`가 FastAPI lifespan에서 TracerProvider(`service.name=kosis-agent`)를 만든다.
     OTLP는 `OTEL_EXPORTER_OTLP_ENDPOINT`가 있을 때만, BatchSpanProcessor(전송은 별도 스레드 = 요청 지연에 안 붙음).
     전역 provider를 건드리지 않는다(`trace.set_tracer_provider` 안 씀).
   - 평가: 지금처럼 `evals/runners/agent.py`가 자기 provider(`kosis-agent-evals`, 메모리 + OTLP).
   - 경계: `build_agent()`는 콜백 없는 그래프만 돌려준다(평가 진입점 그대로). 콜백은 **요청 핸들러가** 실행 config에
     넣는다. backend는 `evals`를 import하지 않고, evals는 `backend.app.main:build_agent`만 쓴다(앱 lifespan은 안 돎).
     → 평가 실행이 서비스 trace에 섞이지 않고, 서비스 요청이 평가 리포트에 섞이지 않는다. 이를 pytest로 고정.
2. **요청마다 trace 하나.** 챗 요청 = 루트 `invoke_agent`(`gen_ai.conversation.id`=thread_id) 아래
   노드·툴·LLM span. 툴 엔드포인트 = 루트 `execute_tool <name>` 하나(기존 툴 객체를 ToolCall 형태로 `.invoke` →
   콜백이 툴 span을 열고 거절 경로도 그대로). 응답에 `trace_id`를 돌려준다(SSE 첫 `meta` 이벤트, JSON 응답 필드)
   → 프런트·사용자 제보에서 Jaeger로 바로 간다.
   `kosis.turn.index` = checkpointer에 이미 있는 HumanMessage 수(user+assistant를 함께 세지 않음 → 평가의 턴 번호 i와 같음).
   - **루트 span은 contextvar에 붙이지 않는다**(리뷰 3): `/chat/stream`은 sync generator라 Starlette가 `next()`마다
     다른 threadpool 작업에서 돌린다. `start_as_current_span`이면 yield 사이에 attach/detach Context가 달라 "Failed to
     detach context"·current span 누수가 난다. `tracing.py`에 `open_turn()`(= `start_span` + 명시 부모 `LiveSpans`,
     `finally`에서 `end()`)를 두고 `agent_turn`도 그 위에 얹는다. 클라이언트가 끊겨 GeneratorExit가 나도 루트가
     닫히는지 pytest로 고정.
   - **실전 1 LLM 호출 span**(리뷰 4): 실전 1 HCX 호출은 urllib라 `on_chat_model_start`가 불리지 않는다. 그래서
     summarize_stat 툴 span 아래에 실전 1이 돌려주는 `StatOutput.spans`(단계별 이름·상태·시간)를 자식 span으로
     옮긴다(끝난 뒤 시각으로 기록, 실전 1 수정 없음). 핵심 LLM 지연이 trace에 나타나고, 평가 runner도 같은 span을 받는다.
3. **엔드포인트 (그래프 노드·툴 기준, KOS-182)**
   | 메서드 | 경로 | 그래프 요소 | 응답 |
   |---|---|---|---|
   | POST | `/chat/stream` | 전체 그래프 | SSE: `meta` → 노드 이벤트·`stat` → `token`* → `result` (`error`) |
   | POST | `/chat` | 전체 그래프 | JSON `ChatResult` + `trace_id` |
   | POST | `/tools/search_tables` | search 노드의 툴 | `SearchOutput` |
   | POST | `/tools/summarize_stat` | statistics 노드의 툴 | `StatAnswer` (+ 차트) |
   | POST | `/tools/make_chart` | chart 노드의 툴 | Vega-Lite |
   | GET | `/threads/{thread_id}` | checkpointer 상태 | active_table·messages 요약 (없는 thread는 404) |
   | GET | `/health` | — | 그대로 |
   입출력 모델은 기존 계약(`kosis_rag.schemas`, `kosis_ai.schemas`, `ChatResult`)을 그대로 쓴다. 새 Pydantic은
   요청 바디 3개뿐.
4. **동기/비동기.** 실전 1·2는 동기 I/O(urllib, Chroma 클라이언트)라 핸들러는 `def`로 두어 FastAPI threadpool에서
   돈다(이벤트 루프 막지 않음). SSE generator도 FastAPI가 `iterate_in_threadpool`로 돌린다. OTLP 전송은
   BatchSpanProcessor 스레드라 요청 지연에 붙지 않는다. 대화 기록 Postgres 저장(BackgroundTasks)은 **범위 밖 → KOS-183**
   (김병석, 2026-11-11 사용자 결정). 이 PR에는 I/O가 큰 후처리가 남지 않아 BackgroundTasks를 쓰지 않는다.
   **Swagger**: 엔드포인트마다 tags·summary·description·응답 모델·예시·오류 응답(503·404)을 달아 `/docs`·`/redoc`에서
   그대로 읽히게 한다. SSE 이벤트 순서와 데이터 형식은 `/chat/stream` 설명에 적는다.
5. **토큰 스트리밍** — 옵션마다 다르다(아래).

옵션은 **답 문장 토큰을 어디서 가져오는가**만 다르다. 1~4(trace·엔드포인트·background)는 세 옵션 공통.
측정 지표(공통): ① 서비스 요청 중 trace가 남는 비율 ② trace에서 실전 1 LLM 단계 지연이 보이는가 ③ 답 패리티(콜백·
스트리밍 유무로 ChatResult 동일) ④ 첫 `token` 이벤트까지 시간(TTFT, 같은 질문 5개 mock·HCX).
Baseline: ① 0% ② 아니오 ③ — ④ TTFT 없음(답은 `result`에서 한 번에 = 턴 전체 지연).

## Option A — 검증된 답을 어절 단위 `token`으로 흘림 (실전 1·2 수정 없음)
- 접근: 1~4 + finalize가 정한 답 문장(실전 1이 verify를 통과시킨 `StatAnswer.text`, 거절·되묻기·멀티쿼리 합친 문장)을
  `result` 직전에 `token` 이벤트(`{"delta": ...}`, 프런트 기존 형식)로 잘라 보낸다.
- 예상 성능 향상: ① 0 → 100% ② 아니오 → 예 ③ 동일(같은 finalize) ④ TTFT ≈ 턴 전체 지연(**줄지 않음**, 검증 뒤에
  흘리므로 result가 수 ms 늦어짐). 사용자에게 보이는 차이는 답이 타이핑되듯 나오는 화면 효과뿐이다.
- 실질 반영 이점: 데이터 정확성 유지(검증 전 숫자 노출 0). 프런트 `token` 경로가 실제로 쓰여서, 나중에 실제 토큰(B·C)으로
  바꿀 때 백엔드 이벤트 출처만 바꾸면 된다. 실전 1·2 PR 없음.
- 비용·리스크: 1일. LLM 비용 0. 한계: 실제 LLM 토큰이 아님(문서·API 설명에 적음).

## Option B — 실전 1 compose LLM의 실제 토큰을 그대로 draft로 흘리고 검증 답으로 교체
- 접근: 1~4 + 실전 1 레포 PR: HCX 클라이언트에 `stream=true`(CLOVA Studio v3 SSE) + `on_token` 콜백(compose 단계만).
  summarize_stat 툴이 콜백을 stream writer `token`으로 잇는다. 프런트는 draft를 그리다가 `result`(검증 답)로 교체
  (실전 2 guide 패턴). compose 재시도(최대 2회)면 `token_reset`.
- 예상 성능 향상: ①②③ A와 같음. ④ TTFT = 실전 1 compose 첫 토큰 시점. 감소폭은 지금 추정 근거가 없다 —
  공통 작업 ②(실전 1 단계 span)로 compose 앞 단계 비중을 먼저 재야 한다.
- 실질 반영 이점: 진짜 LLM 토큰 스트리밍. 그러나 **검증 전 숫자가 화면에 보였다가 바뀔 수 있다** → 평가 1순위(데이터
  정확성)와 CLAUDE.md 원칙("LLM이 만든 숫자는 버그") 위반 소지.
- 비용·리스크: 2~3일(실전 1 PR·리뷰·submodule bump, 실전 2가 고정한 phase1 커밋과 맞춰야 함). HCX 스트리밍의 usage
  집계 변화(비용 지표 재확인). 마감(11/14) 넘길 위험.

## Option C — 실전 1 실제 토큰을 흘리되 숫자는 검증 뒤에만 보임
- 접근: B와 같은 실전 1 PR + 이 레포 스트리밍 필터: 토큰 안의 숫자 덩어리(`\d[\d,.]*`)는 `▢`로 가려 보내고,
  `result`(검증 답)가 오면 전체를 교체한다. 글자는 실시간, 숫자는 검증된 값만.
- 예상 성능 향상: ①②③ A와 같음. ④ TTFT는 B와 같음(측정 전 추정 불가, B와 같은 이유).
- 실질 반영 이점: 실제 토큰 스트리밍 + 검증 전 숫자 노출 0. 가려진 자리가 많은 답(수치 나열)은 체감 이득이 작다.
- 비용·리스크: 3일(B + 필터·경계 처리: 토큰이 숫자 중간에서 끊길 때 버퍼링). 실전 1 PR 의존은 B와 같다.

## Recommendation
**옵션 A.** 공통 작업(서비스 trace·실전 1 단계 span·엔드포인트·Swagger 문서)이 이 태스크의 실제 성과이고, A는 그것을
실전 1·2 수정 없이 11/14 안에 끝낸다. 실제 토큰(B·C)의 이득(TTFT)은 A로 생기는 실전 1 단계 span으로 compose 앞 단계
비중을 잰 뒤에 판단할 수 있다. 이득이 크면 C를 후속 태스크로 연다(B는 정확성 원칙 때문에 비추천).
"가짜 token 이벤트를 빼고 trace·엔드포인트만" 하는 더 단순한 안도 있다(리뷰 1). A와의 차이는 finalize 몇 줄이고,
요청에 토큰 스트리밍이 있어 A에 포함했다.
