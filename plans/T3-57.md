# T3-57 운영자 페이지 1차 (홈·지표·질문 검수·👎 처리함)

## Goal
- 완료 기준 (TASK.md 그대로): 서비스와 분리된 운영자 앱 `admin/`(같은 주소의 `/admin`)으로 홈·지표 4탭·질문 검수·👎 처리함을 만든다. 기존 카카오 로그인 + 허용 목록, 지표 숫자는 `kosis_store.log_metrics` 결과 그대로, 👎 처리 상태 4종 저장. 서비스 프론트·백엔드 코드 변경 0. pytest 통과.
- 배경: 기능명세 F-PVOWFN(운영자 메트릭)·와이어프레임 "새 플로우 1 v2". 운영 설계는 김병석 `kosis-infra/11-운영-관제-설계.md`, 화면 상세는 `12-운영자페이지-1차-상세설계.md`.
- Baseline: 운영자가 로그를 보는 화면 0개. 지표·검수는 SQL을 직접 실행해야 함(`log_metrics.py` 함수만 있음). 👎 처리 기록을 남길 곳 없음.

## 범위 밖
- 공지 띠(11/26 팀 논의에서 제외), 로그 화면(2차, Loki 설치 뒤).
- 답 문장 표시: 11/26 팀 결정으로 저장하지 않음. 상세 화면에 안내만.
- 상태 카드의 실제 값(Prometheus 설치 뒤). 1차는 "확인 안 됨".
- 로그 집계 코드 문제(실패 단계 이름표, 결과 종류 6종)는 QA 뒤. 화면에 "실제와 다를 수 있음" 안내.

## Idea
1. `admin/` 앱: FastAPI + Jinja2(서버에서 그림). `kosis_store.log_metrics`·`log_models`·`masking`만 import(`service_store`는 쓰지 않음).
2. 로그인: 쿠키(`__Host-kosis_session`/`kosis_session`)의 SHA-256을 `login_sessions`에서 찾음(백엔드와 같은 방식, 테스트로 확인) → `ADMIN_USER_IDS`에 있으면 통과. 없으면 404, 쿠키 없음·만료는 로그인으로, DB 오류는 503.
3. 쓰기: `admin` 스키마의 `feedback_reviews`·`audit`. 서비스 마이그레이션과 따로 번호를 매기는 alembic(`admin/migrations`, 버전 표도 `admin` 스키마). 서비스 테이블에 외래 키 없음 → 매일 정리 명령(`python -m admin.app.cleanup`).
4. DB 계정 `kosis_admin` 권한 SQL(`admin/sql/grants.sql`): 로그 테이블 읽기, `login_sessions`·`users` 칸 단위 읽기, 대화·메시지 권한 없음.
5. 보호: POST만 쓰기, Origin 검사 + 폼 위조 방지 값, `no-store`, `frame-ancestors 'none'`, 외부 파일 없음, `noindex`.
6. 이미지: `admin/Dockerfile`(torch 없음), CI에 빌드 1줄. 의존성은 `pyproject.toml`의 `admin` 그룹(jinja2).

## Option A — 서비스 안에 넣기
- 접근: 백엔드에 `/admin/*` API, 프론트(Next.js)에 화면.
- 예상 성능 향상: 화면 0 → 4. 로그인·화면 부품 재사용.
- 실질 반영 이점: 하나의 앱.
- 비용·리스크: 기능 동결(11/22)·QA 기간에 서비스 코드를 크게 바꿈, 프론트·백엔드 담당과 충돌, 운영자 화면 오류가 사용자 서비스와 같이 배포됨.

## Option B — 별도 앱 `admin/` (서버에서 그리는 화면)
- 접근: 위 Idea.
- 예상 성능 향상: 화면 0 → 4, 👎 처리 기록 0 → 상태 4종, 지표 SQL 직접 실행 → 화면에서 필터.
- 실질 반영 이점: 서비스 코드 변경 0, 지표 정의는 `log_metrics.py` 한 곳 그대로, 운영자 앱이 멈춰도 사용자 서비스 영향 없음. DB 권한을 칸 단위로 좁힘.
- 비용·리스크: 이미지·배포 1개 추가(메모리 256Mi), admin 스키마 정리 작업 필요.

## Option C — Grafana만
- 접근: Grafana PostgreSQL 데이터 소스로 지표 패널, 처리함은 없음.
- 예상 성능 향상: 지표 화면 0 → 1, 처리 기록 0 그대로.
- 실질 반영 이점: 코드 거의 없음.
- 비용·리스크: 지표 SQL을 Grafana에 다시 써야 해서 "지표 정의는 코드 한 곳" 원칙이 깨짐, 👎 처리·질문 상세 링크 불가, DB 계정에 넓은 읽기 권한.

## Recommendation
옵션 B. 동결 기간에 서비스 코드를 건드리지 않고, 지표 정의를 한 곳에 둔 채 처리함까지 만들 수 있다.
