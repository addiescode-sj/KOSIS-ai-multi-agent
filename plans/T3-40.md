# T3-40 답변 품질 채점 강화 — 출처 표기 검사(KOS-196) · 근거 없는 숫자 허용 집합 축소(KOS-198)

## Goal
- 완료 기준 (Linear KOS-196 · KOS-198 그대로):
  - KOS-196: 최종 답 문장에 그 턴에서 답한 `summarize_stat`마다 `StatAnswer.source`의 조사명(`survey_nm`)·통계표명(`tbl_nm`)이 들어 있어야 한다. 없으면 에이전트 턴 오류 `missing_source`. 거절·되묻기 턴, `summarize_stat` 답이 없는 턴은 건너뛴다. 멀티쿼리 턴은 하위 답마다 검사한다. L3·e2e `calculation.grade()`에도 같은 규칙을 PARTIAL 오류 `missing_source`로 넣는다(`ERROR_INFO`, README §4).
  - KOS-198: `answer.grounding()`이 툴 결과 JSON 전체(표 키 `101_DT_…`, 항목 코드, 셀 참조, 후보 목록)의 숫자를 허용 집합에 넣어 `unsupported_final_number`가 사실상 항상 0이다. 허용 집합을 질문 숫자 · 사실 값(반올림 허용) + `calculation.allowed_text_numbers(facts)` · `combine_values` 결과 값 · 인용한 표 ID로 좁힌다. "약 10만", "3천 명" 같은 한국어 수 단위를 정규화한 뒤 검사한다. L3·e2e `unsupported_claim`은 건드리지 않는다.
- Baseline (재채점, LLM 0회): 저장된 agent run 2개를 현재 채점기로 다시 채점 — `unsupported_final_number` 턴 0, `missing_source` 지표 없음. oracle 자기검증 1.000. pytest 242 passed.

## Idea
먼저 에이전트가 출처를 최종 답에 넣는지 확인했다. `main_graph.finalize_node`는 단일 경로에서 `stat.answer.text`를, 멀티쿼리에서 하위 답의 `answer.text`를 그대로 잇는다. 실전 1 `render/text.py:final_text`가 본문 뒤에 `출처: {source.citation()}`(`KOSIS / 조사명 / 통계표명 (url)`)을 코드로 붙이므로 출처는 들어간다. 저장된 L3·e2e run을 세어 보니 답한 `StatAnswer` 126건 모두 `source`가 있고 `text`에 조사명·통계표명이 들어 있다. `parts`(FactPart·TextPart)에는 출처가 들어가지 않는다(코드가 붙이는 줄은 parts 밖). 그래서 L3 규칙은 "답했으면 `source`가 있고 `text`에 조사명·통계표명이 있다"로 한다.

숫자 허용 집합:
1. 대화의 질문 숫자 (지금까지 턴 누적, 기존과 같음)
2. 대화의 `summarize_stat` 답의 사실 값(반올림 허용) + `allowed_text_numbers(facts)`(시점·라벨 숫자)
3. `combine_values` 결과 값(반올림 허용)
4. 인용한 표: 답 문장에서 출처 문자열(`citation()`, url, 조사명·통계표명, 표 ID)을 지운 뒤 숫자를 센다. url·표 ID의 숫자(`orgId=101`, `DT_1B83A03`)를 허용 집합에 통째로 넣으면 "1"·"83" 같은 숫자가 전부 허용되므로 문자열을 지우는 쪽이 더 좁다.
5. 실전 1이 코드로 쓰는 기본값 문장(`default_applied` 값의 숫자, 예: "최근 3개 시점")
검색 결과(`picked`·`candidates`), 셀 참조, 항목 코드, 툴 인자는 넣지 않는다.

한국어 수 단위: `\d+(.\d+)?` 뒤 `조·억·천만·백만·만·천`을 붙여 읽고 이어지는 단위(`1억 2천만`)는 더한다. 펼친 값이 사실 값에 단위 반올림 범위 안(예: "10만" → ±5,000)이면 근거 있음. 사실 단위가 그 수 단위로 시작하면(`억원`·`천명`) 앞 숫자 그대로도 비교한다.

## Option A — 이슈 그대로: 출처 검사 + 허용 집합 축소 + 수 단위 정규화
- 접근: 위 Idea 그대로. `answer.py`에 `missing_sources()`·새 `grounding()`, `calculation.grade()`에 PARTIAL `missing_source`, `trace.blame`의 compose 규칙에 `missing_source` 추가, oracle 답 문장에 출처를 넣는다
- 예상 성능 향상: 시스템 성능은 그대로, 채점이 엄격해진다. `unsupported_final_number` 턴 0 → 재채점에서 실제로 근거 없는 숫자 수만큼(미리 알 수 없음, 오탐 0이 목표). `missing_source` 턴 0 예상(실전 1이 출처를 붙이므로)
- 실질 반영 이점: 데이터 정확성 — 앞으로 ReAct 등 LLM이 최종 답을 쓰는 아키텍처(T3-07~10)에서 지어낸 숫자·빠진 출처를 같은 골든셋으로 잡는다. 지금은 0으로 고정된 지표가 의미를 갖는다
- 비용·리스크: 반나절, LLM 비용 0. 실전 1 코드 문장(참고 줄·거절 메시지)의 숫자가 사실에 없으면 오탐이 날 수 있다 → 재채점으로 새로 걸린 턴을 손으로 확인한다

## Option B — 출처 검사만, 숫자는 수 단위 정규화만
- 접근: KOS-196만 하고 허용 집합은 그대로 둔 채 수 단위 정규화만 넣는다
- 예상 성능 향상: `missing_source` 지표만 생긴다. `unsupported_final_number`는 계속 0(툴 결과 JSON 전체 허용이 그대로)
- 실질 반영 이점: 오탐 위험이 없다
- 비용·리스크: KOS-198 완료 기준을 채우지 못한다

## Option C — 허용 집합을 `StatAnswer.text` 숫자로
- 접근: 허용 집합을 "툴이 쓴 문장(`StatAnswer.text`)의 숫자"로 바꾼다
- 예상 성능 향상: 오탐은 거의 없지만, 지금 그래프는 최종 답 = `StatAnswer.text`라 단일 경로에서 다시 항상 0이다
- 실질 반영 이점: 에이전트 쪽 LLM이 답을 고쳐 쓸 때만 잡는다
- 비용·리스크: 이슈가 정한 허용 집합(사실·질문·합산·표 ID)과 다르고, 실전 1 문장 안의 근거 없는 숫자는 못 잡는다
