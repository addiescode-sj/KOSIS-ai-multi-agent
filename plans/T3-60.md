# T3-60 메인 ReAct 그래프에 검색 분리(②·③)·미리 검색과 후속 질문 규칙 옮기기

## Goal
- 완료 기준: main(T3-03 옵션 B) 그래프의 판단(understand·rewrite)은 그대로 두고, `search` 노드를 ② 후보 찾기 → ③ 2차 리랭커·gate로 나눠 understand와 동시에 ②를 미리 돌린다. 11/25 서버 점검에서 나온 후속 질문 세 경우를 understand의 이어 묻기 해석에 더한다. 툴 4개 이름·인자·결과와 채점 계약은 바뀌지 않는다. pytest 통과, 같은 e2e 골든으로 전→후(정확도 회귀 없음, 검색 턴 지연)를 남긴다.
- 출처: `min-multiagent-service`(T3-09 멀티에이전트 실험, `src/kosis_multi/`)의 S3·S4와 a071713. 그 브랜치의 ① 판단(rag/direct, Qwen 즉시 답변)은 main의 ReAct 판단과 겹쳐서 가져오지 않는다. S4b 계산용 질문 다듬기도 가져오지 않는다(판단 쪽 Qwen 호출, 기본 꺼짐이었음).
- Baseline: main `1c58899` 그래프의 e2e test run (사용자가 실행, 같은 골든 `e2e_golden`+`e2e_golden_calc`, `--split test`).

## 현재 상태 (main 1c58899 코드 읽기)
- `search` 노드가 `search_tables` 툴 한 번으로 실전 2 검색 그래프 전체(parse → 목록들 → fuse → rerank1 → rerank2 → gate)를 돈다. 판단(understand의 Qwen 호출)이 끝난 뒤에 검색이 시작된다.
- understand는 `read_turn`만으로 이어 묻기를 해석한다. 서버 점검(dc39ce8)에서 나온 세 경우를 놓친다.
  1. "2024년 출생아 수" 다음 "이혼은?": 지표 낱말이 있어 새 질문으로 보고 원문 검색 → 2024년을 잃음.
  2. "2024년 서울 출생아 수" 다음 "부산이랑 비교해줘": 시도를 바꿔 끼워 부산 값만 답함.
  3. 전국 표로 답한 뒤 "서울은?": 직전 표를 다시 써서, 시도 칸이 없는 표의 전국 값을 서울 값처럼 답함.

## Idea
- ②·③ 분리는 실전 2 `graph_nodes`의 노드를 그대로 써서 작은 그래프 둘로 묶는다(실전 2 코드 수정 없음). 둘을 이어 돌면 `run_search`와 같은 결과다. ②가 만든 중간 상태는 (thread_id, 질문)으로 보관하고, ③의 `search_tables` 툴이 꺼내 rerank2·gate를 마저 돈다. 그래서 툴 인자·결과·span 이름은 지금과 같다.
- 미리 검색: understand가 시작할 때 원문으로 ②를 옆 스레드에서 돌린다. 검색 턴이 같은 원문을 쓰면 기다려 쓰고, 다른 문장(재작성·이월)이면 다시 찾는다. 쓰지 않은 미리 검색은 finalize에서 끝나기를 기다렸다 버린다. 미리 검색은 툴 span이 없어서 template·clarify 턴에서 버려도 extra_call이 생기지 않는다.
- 후속 질문 규칙은 `graph/followup.py`(규칙만, LLM 없음)로 두고 understand의 `read_turn` 앞에서 본다.

## Option A — search 노드만 ②→③으로 바꾸고 미리 검색 + 후속 질문 규칙 (multi 노드는 그대로)
- 접근: `search` 노드를 `retrieve`(②)·`search`(③) 둘로 나눈다. ③은 지금 search 노드와 같은 상태(search·degraded·refusal_reason·researched·trace verify)를 남겨 `after_search`(no_item 거절 → 재작성 1회)가 그대로 돈다. 재작성·이월 턴의 검색 문장 규칙도 지금과 같다. multi 노드는 지금처럼 하위 질문마다 `search_tables`를 부른다(②가 없으면 툴이 처음부터 다 돎). statistics·chart·review·finalize는 그대로이고, finalize 앞에 미리 검색 정리만 더한다.
- 예상 성능 향상: 정확도는 같다(② + ③ = 지금 검색, 패리티 테스트로 확인). 검색 턴 지연은 understand Qwen 판단 시간만큼 줄어든다(추정 턴당 1~3초, 미측정 → e2e `timings`로 잰다). 후속 질문 3경우는 서버 점검 사례 3개가 맞게 바뀐다(test_followup 13개). e2e 골든에 같은 유형 턴이 있으면 멀티턴 성공률이 오른다(골든 확인 전이라 수치 미정).
- 실질 반영 이점: 판단을 ReAct로 바꾼 뒤 생긴 "매 턴 Qwen 먼저 → 검색이 늦게 시작"을 줄인다. 그래프 모양(노드 이름·경로)은 거의 그대로라 리뷰·디버깅이 쉽다.
- 비용·리스크: 반나절. 미리 검색 스레드가 실패하면 ②가 다시 찾는다(결과 같음). 원문과 검색 문장이 다른 턴(재작성·이월)에서는 미리 검색이 버려져 1차 검색 계산만 늘어난다(GPU 추론 서버 부하).

## Option B — A + multi 노드도 ②·③으로 (하위 질문 검색을 미리 검색과 같은 경로로)
- 접근: A에 더해 multi 노드의 하위 질문 검색도 ②(질문마다 후보)·③(질문마다 search_tables)으로 나눈다.
- 예상 성능 향상: A와 같다. 멀티쿼리 턴은 원문과 하위 질문이 달라 미리 검색을 못 쓰므로 지연 이득이 없다.
- 실질 반영 이점: 검색 경로가 하나로 모인다.
- 비용·리스크: +반나절. multi 노드는 검색과 계산이 한 노드라 나누면 경로가 늘고, 이득은 없다.

## Option C — 후속 질문 규칙만 (검색 분리·미리 검색 없음)
- 접근: `graph/followup.py`와 understand 연결만 한다.
- 예상 성능 향상: 후속 질문 3경우는 A와 같다. 지연 이득 없음.
- 실질 반영 이점: 바뀌는 곳이 가장 적다.
- 비용·리스크: 2시간. 검색 분리 실험(T3-09)은 main에 들어가지 않는다.

## Recommendation
**옵션 A.** 지연 이득은 단일 질문 검색 턴에서만 생기고, 멀티쿼리는 미리 검색을 못 쓰므로 B의 추가 작업은 이득이 없다. 후속 질문 규칙은 A에 포함된다.
