# T3-32 계측 방식 통일

## Goal
- 완료 기준 (TASK.md 그대로): Jaeger 서비스 3개(`kosis-agent`·`kosis-agent-evals`·`kosis-evals`)를 파이프라인 하나의 이름으로
  합치고 실사용·평가는 `deployment.environment.name`으로 구분한다. l3·e2e도 서비스·agent와 같은 실시간 콜백(`LiveSpans`)과
  같은 span 이름(`execute_tool …`)으로 계측하고, 채점 판정은 채점 뒤 링크로 붙인다. 같은 입력에서 채점·ops summary
  패리티(회귀 0), pytest.
- Baseline (코드 확인, 2026-11-12, T3-31 `385a822` 위):

  | 계층 | service.name | 방식 | 시각 | 같은 실전 1 호출의 span 이름 |
  |---|---|---|---|---|
  | API 서버 | `kosis-agent` | `LiveSpans` 실시간 | 실제 | `execute_tool summarize_stat` → 실전 1 단계 |
  | agent | `kosis-agent-evals` | `LiveSpans` 실시간 + 채점 뒤 `eval.scenario` 링크 | 실제 | 같음 |
  | l1(그래프)·l3·e2e | `kosis-evals` | 채점 뒤 재생(`evals/trace.py` `export`·`_replay`, 약 70줄) | **가짜**(끝에서 거꾸로 이어 붙임) | `tool.summarize_stat` / `retrieve` / `search_tables` |

  - 계측 코드 경로 2개(실시간 콜백, 재생). 같은 호출이 계층마다 다른 이름 → Jaeger 검색·대시보드를 계층마다 따로 짜야 함.
  - l3·e2e는 실전 1 private `_build` + `bot.ask`(`evals/trace.summarize`, ponytail 주석: "실전 1이 span을 내면 지움")를 쓴다.
    실전 1 `summarize_stat_run`은 이제 `client=`를 받고 `StatOutput.spans`를 돌려준다 → 툴 경유가 가능하다.
  - `trace.blame`·`blame_search`·리포트 span 경로는 trace가 아니라 **행에 저장된 span dict**(`row["spans"]`, `row["search_spans"]`)를
    읽는다 → 계측 방식을 바꿔도 판정 규칙은 그대로 둘 수 있다.

## Idea
1. **분리할 것은 "실사용 vs 평가" 하나.** 평가 한 번에 HCX 수백 회가 나가므로 서비스 메트릭(비용·거절률·예외율)과 섞이면 안 된다.
   이건 서비스 이름이 아니라 OTel 표준 resource 속성 `deployment.environment.name`(`service` | `eval`)으로 한다.
   계층은 resource `kosis.eval.layer`(l1 | l3 | e2e | agent), run은 `kosis.eval.run`. Jaeger UI tag 검색은 process(resource) 태그도 찾는다.
   한 서비스 목록에 실사용·평가 trace가 섞이므로 README·Jaeger 링크에 `deployment.environment.name=service`(또는 `eval`) 필터를 기본으로 단다(리뷰 3).
2. **같은 호출은 같은 코드로 계측한다.** 평가도 서비스가 부르는 툴 객체(`summarize_stat`, `search_tables`)를 같은 `LiveSpans`로 부른다.
3. **판정은 나중에 링크로.** 판정은 채점 뒤에만 안다. agent의 `link_verdicts`처럼 `eval.question` span을 채점 뒤 하나 열고
   실행 trace의 루트에 Link로 판정(`kosis.verdict`, `failure.*`)을 붙인다. 행의 `trace_id`는 실행 trace.
4. provider를 만드는 코드는 한 곳(`kosis_agent.observability`)에: `provider(environment, **resource)` → TracerProvider(+OTLP) ·
   MeterProvider. 서비스 telemetry.py·평가 runner가 같이 쓴다.

## Option C — 모든 계층을 에이전트 그래프로 실행
- 접근: e2e = `build_agent()` 한 턴(질문 → 그래프 전체), l3 = 같은 그래프에 정답 표를 주는 oracle 검색. 계측은 agent 계층과 완전히 같은 것
  (`invoke_agent` 루트). retriever 프리셋별 e2e는 없어지고 서비스 설정(`SearchModule`)만 남는다.
- 예상 성능 향상: B의 계측 통일 + "평가 = 서비스"가 완전히 같아짐. 대신 e2e·l3 수치가 바뀐다(context 노드·멀티쿼리 분해·parse_query 조건이 끼어듦)
  → 과거 e2e·l3와 비교 불가, 패리티 기준 없음.
- 실질 반영 이점: 서비스 그래프 자체의 단일턴 정확도를 잼(지금은 agent 시나리오만).
- 비용·리스크: 2~3일. 계층 정의(L3 = 정답 표를 준 실전 1 단독, L4 = 검색 1위 → 실전 1)가 바뀌어 기준 문서·골든 비교가 끊김.
  검색기 실험(프리셋별 e2e)을 못 함. 계측 통일이라는 목표보다 범위가 큼.

## Recommendation
**옵션 B2** (안 되면 B1). 실패 행 span이 평가 패리티의 전제이고, 같은 결함이 서비스에도 있다(실전 1 실패 호출의 단계가 Jaeger에서 빠짐).
B2는 그 원인을 실전 1 계약 한 곳에서 고친다. PR 머지를 기다릴 수 없으면 B1로 같은 결과를 내고, B2 머지 후 evals 쪽 함수를 지운다.
아래 B 설명은 둘 공통: 목표(이름 하나, 방식 하나)를 다 채우면서 계층 정의와 채점 수치는 그대로 둔다(패리티로 확인 가능). A는 이름만 맞추고
코드 경로 2개가 남아 다시 갈라지고, C는 계층 정의를 바꾸는 별도 결정이다.
