# T3-32 사용자 로그 리서치 · 스키마 설계 (Linear KOS-169)

## Goal
- 완료 기준 (TASK.md 그대로): 로그 스키마 사례 조사(출처 포함)와 우리 서비스에 옮긴 결정, 질문 1건이 `request_id`로 원문·표 키·판정·단계별 지연·피드백과 묶이는 스키마(기능명세 US-10), 원문 보관·삭제와 개인정보 규칙, 메트릭 화면 지표를 스키마로 계산할 수 있는지 확인. 수집 API·writer(KOS-170)와 정제 배치(KOS-167)는 범위 밖
- 마감: 11/12. KOS-170(수집 파이프라인, 11/22)과 KOS-158(백엔드 DB, 김병석)이 이 스키마를 받는다.
- Baseline
  - 저장소: `conversations`·`messages`·`eval_runs` 3개 테이블(T3-18). 사용자 로그를 담는 테이블 0개.
  - 문서: 로그 설계 초안(11/06, 저장소 밖 작업 폴더)에 이벤트 15종, 공통 레코드 13필드, 메트릭 화면 지표 18개(요약 4 · 답 품질 5 · 사용 패턴 5 · 성능·비용 4)가 있다. 테이블·타입·제약은 정해지지 않았다.
  - 메트릭 화면 지표 18개 중 지금 DB에서 SQL로 계산되는 것: 0개.
- Linear 이슈 본문은 이 세션에서 읽지 못했다(연결 끊김). 완료 기준은 이슈 제목, 상위 이슈 KOS-168 제목, KOS-155 범위 결정 문서의 "로그·분석에 미치는 영향 (KOS-169)" 절, 기능명세 US-08·US-10에서 가져왔다. 본문과 다르면 고친다.

## 이미 정해진 것 (바꾸지 않는다)
- 질문 원문과 피드백은 비회원·회원 모두 남긴다. 저장 전 전화번호·이메일 패턴을 가린다. 원문 보관 30일(제안값).
- IP·기기 식별자는 남기지 않는다. 골든셋 문항·정답은 로그·DB에 넣지 않는다. 하네스 요청은 `is_internal=true`.
- 피드백은 `request_id`로 답과 묶는다(비회원 답에는 `messages` 행이 없다). 👍/👎 + 선택지 1개 + 이유 200자, 같은 답에 다시 누르면 마지막 값.
- `feedback`·`users`·`suggestions`·`faqs` 테이블과 마이그레이션 `0002`는 KOS-155 문서가 KOS-158(백엔드)에 배정했다. 이 태스크는 `feedback`을 만들지 않고, 로그 쪽에서 필요한 열·제약만 요구 사항으로 넘긴다.
- 서버 단계 기록은 평가 코드에서 OTel span 모양으로 나온다(`evals/trace.py`). 단, `backend/app/main.py`에는 아직 `request_id`도 OTel도 없다.

## 리서치에서 가져올 것 (요약, 본문은 산출 문서에)
- Langfuse 데이터 모델: session → trace → observation, 피드백·평가는 score로 trace·observation·session 중 하나에 붙는다. → "질문 1건 = 1행, 단계는 그 아래, 피드백은 질문 ID에 붙임"의 근거.
- OpenTelemetry GenAI 규약: `gen_ai.conversation.id`, `gen_ai.usage.input_tokens`·`output_tokens`, `error.type`. 아직 안정 단계가 아니고 별도 저장소로 옮겨졌다. → 이름은 맞추되 우리 열로 꺼내 둔다.
- Snowplow 추적 설계: 여러 행동을 한 이벤트에 `type`으로 뭉치지 말 것, 재전송으로 같은 `event_id`가 온다(1% 미만은 정상), 중복은 `event_id` + 수집 시각으로 제거, 기기 시각과 수집 시각을 둘 다 둔다.
- 암묵 피드백 연구: 재질문, 이탈, "아니" 같은 정정 표현이 불만족 신호이고 턴 사이 시간 간격이 판별에 도움이 된다. → KOS-176이 쓸 열을 둔다.
- 개인정보보호위원회 생성형 AI 안내서(2025-08): 목적·범위 명확화, 서비스 단계 투명성. 프롬프트 보관 기간의 구체 기준은 확인하지 못했다. → 30일은 제안값으로 두고 "미확인"으로 적는다.

## 공통 (세 옵션 모두)
- 산출 문서 `docs/log-schema.md`: 리서치(출처), 결정, 테이블·열·제약, 보관·삭제·개인정보 규칙, 지표 18개별 SQL, 백엔드에 넘길 요구 사항.
- `request_id`는 서버가 만드는 UUID다. OTel trace id는 별도 `trace_id` 열(없을 수 있음)로 둔다. `request_id`는 SSE **첫** 이벤트에 실어야 화면의 첫 토큰·이탈 이벤트가 같은 ID를 쓴다 → KOS-158에 요청.
- 대화 ID는 `conversations` FK가 아니라 UUID 값 + 인덱스로 둔다(비회원 대화는 `conversations`에 없고, 회원이 대화를 지워도 로그는 30일 남는다, US-09).
- 원문이 들어갈 수 있는 곳을 열로 한정한다: 질문 원문, 피드백 이유. 단계 기록의 속성은 **허용 목록**(이름·지연·상태·`error_type`·토큰)만 저장한다. 예외 메시지(`"Type: message"`)와 실전 1의 `unresolved` 같은 값에는 질문 조각이 섞일 수 있어 넣지 않는다.
- 하네스 요청은 원문을 저장하지 않는다: `CHECK (NOT is_internal OR question IS NULL)`.
- 측정: 지표별 SQL을 시드 행(지어낸 요청, 골든 아님)에 돌려 손으로 센 값과 맞는 개수(`-m postgres` pytest).

## Option A — 단일 이벤트 테이블 (`events` 하나 + JSONB)
- 접근: 초안의 공통 레코드 13필드를 그대로 한 테이블로 만든다. 화면·서버 이벤트, 질문 원문이 모두 `event_type` + `props`(JSONB) 행이다. ORM + 마이그레이션, 문서.
- 예상 성능 향상: 지표 SQL 계산 0/18 → 테스트로 확인 약 14/18 (피드백 4개는 KOS-158의 `feedback`이 있어야 함. 근거: 값이 한 테이블에 있으나 질문 단위 지표는 `request_id`로 이벤트를 다시 묶는 피벗이 필요).
- 실질 반영 이점: 테이블 1개, 수집 경로 1개라 KOS-170이 가장 단순하다. 이벤트 종류를 더해도 마이그레이션이 없다.
- 비용·리스크: 0.5~1일. 원문이 `props` 안에 섞여 "원문만 지우고 집계는 남긴다"가 행 단위 JSON 수정이 된다. 허용 목록·하네스 원문 금지를 DB 제약으로 걸 수 없다. US-10의 "한 묶음"이 매번 조인으로만 만들어진다.

## Option B — 질문 로그 1개 테이블 (`request_logs`, 단계는 JSON 열)
- 접근: 질문 1건 = 1행인 `request_logs` 하나만 지금 만든다.
  - 열: `request_id`(PK), `trace_id`, `conversation_id`·`turn`·`prev_request_id`, `session_id`, `is_member`, `is_internal`, `input_method`(직접·추천 버튼), `question`(가린 원문, 30일 뒤 NULL)·`question_len`, `outcome`(answered·refused·clarify·error·aborted)·`reason_code`·`failed_stage`, `picked_key`·`survey_name`, `has_numbers`·`has_chart`, `latency_ms`·`first_token_ms`, `llm_calls`·`input_tokens`·`output_tokens`·`llm_model`, `spans`(JSON 배열, 허용 키만), `log_version`, `created_at`.
  - KOS-176용 자리: `rephrase_of`(이전 요청 ID), `negative_reaction`(bool) — 원문이 있는 30일 안에 탐지 결과만 남긴다. 값은 KOS-176이 채운다.
  - `ui_events`(화면 행동)와 수신 탈락 기록은 **문서에 열 정의만** 두고 테이블은 KOS-170에서 만든다. `feedback`은 KOS-158 것을 쓰되 요구 사항(`request_id` unique, `message_id` nullable, 값·선택지 CHECK, "기타면 이유 필수", `request_logs` FK 없음)을 문서로 넘긴다.
  - ORM 모델 + pytest. `failed_stage`는 정답 없이 쓸 수 있는 규칙(span 상태 error, 계산 거절, 대체 답변 경로)만 쓴다.
- 예상 성능 향상: 지표 SQL 계산 0/18 → 테스트로 확인 10/18, SQL 문서화 18/18 (근거: 질문 수, 결과 비율, 응답 지연, 거절 사유, 실패 단계, 많이 쓰인 표·조사, 대화당 턴 수, 단계별 지연, 첫 글자 시간, LLM 호출·토큰이 이 테이블만으로 나온다. 피드백 4개는 KOS-158, 화면 행동 3개와 로그 품질 1개는 KOS-170 뒤 확인).
- 실질 반영 이점: 원문이 열 하나에만 있어 보관 삭제가 UPDATE 한 번이고, 하네스 원문 금지·허용 목록이 제약과 코드 한 곳으로 지켜진다. 새 테이블이 1개라 KOS-158과 겹치지 않는다. 단계 기록이 평가 trace와 같은 모양이라 Jaeger로 이어 보기 쉽다.
- 비용·리스크: 1일(마감 11/12 안). 단계별 지연은 JSON을 풀어(`jsonb_array_elements`) 집계해야 해서 SQLite 오프라인 테스트로는 확인할 수 없다(PostgreSQL 테스트만). 단계 수가 많아지면 행이 커진다(질문당 20개 안팎이라 지금은 문제없음).

## Option C — 정규화 테이블 전부 지금 (`request_logs` · `request_spans` · `ui_events` · `quality_signals` · `ingest_rejects`)
- 접근: B의 `spans` 열을 `request_spans`(`(request_id, seq)` PK, `parent_seq`, 연쇄 삭제) 테이블로 빼고, 화면 행동·품질 신호·수신 탈락 테이블까지 이번에 모두 만든다. 수신 입력 계약(Pydantic)도 같이 둔다.
- 예상 성능 향상: 지표 SQL 계산 0/18 → 테스트로 확인 14/18 (피드백 4개 제외 전부. 근거: 화면 행동·로그 품질 테이블이 지금 생긴다).
- 실질 반영 이점: KOS-170·176이 테이블을 새로 만들 필요가 없다. 단계별 집계가 일반 SQL이다.
- 비용·리스크: 2일(마감 초과 위험). 화면 이벤트 테이블과 수신 계약은 화면 명세(KOS-155, 진행 중)와 수집 방식(KOS-170)이 정해지기 전이라 바뀔 가능성이 크다. 쓰는 코드가 없는 테이블 4개를 먼저 만든다("필요한 것만 만든다"와 충돌). 백엔드와 마이그레이션 순서가 더 많이 얽힌다.

검토하고 뺀 안: Langfuse 자체 호스팅(trace·피드백 저장을 도구에 맡김). compose 서비스가 여러 개 늘어 인프라 범위이고 Jaeger·Grafana 계획과 겹치며, 질문 원문이 도구 DB에 들어가 30일 삭제와 가림을 우리 코드로 보장하기 어렵다.

## Recommendation
**Option B.** 질문 1건이 한 행이라 US-10의 "한 묶음"과 "원문만 지운다"를 스키마가 보장하고, 새 테이블이 하나뿐이라 마감 안에 끝나며 KOS-158과 겹치지 않는다. 화면 행동·품질 신호 테이블은 쓰는 코드가 생기는 KOS-170·176에서 문서 정의대로 만든다.

1. 원래 C(Langfuse)는 처음부터 탈락이라 비교가 A/B뿐 → 반영: Langfuse는 "검토하고 뺀 안"으로 내리고, 리뷰가 낸 1개 테이블 안을 B로, 4개 테이블 안을 C로 재구성.

4. 키·관계 빈틈(대화 FK, 피드백 FK, `message_id`, span PK, `request_id` = trace id가 아직 성립 안 함, `request_id`가 SSE 마지막 이벤트) → 반영: 대화는 FK 없는 UUID, `trace_id` 별도 열, 피드백 요구 사항과 SSE 첫 이벤트 요청을 백엔드 전달 항목으로.
5. KOS-176에 필요한 열 없음 → 반영: `input_method`, `prev_request_id`, `question_len`, `rephrase_of`, `negative_reaction`. `(conversation_id, turn)`은 unique로 두지 않는다(재시도).
6. 범위: 마이그레이션 `0002`와 `feedback`은 KOS-158 배정, 수신 Pydantic 계약은 KOS-170 몫 → 반영: `feedback` 정의와 수신 계약을 뺌. 마이그레이션을 이번에 넣을지는 사용자 결정으로 올린다.
7. Linear 본문 미확인 → Goal에 적어 둠. 승인 전에 사용자에게 알린다.

## Decision
Option B (질문 로그 1개 테이블 `request_logs`, 단계는 JSON 열), 2026-11-10 사용자 선택. 마이그레이션은 이번에 넣지 않는다: 문서 DDL + ORM 초안까지만 하고, 번호는 KOS-158(김병석 님)과 정한 뒤 넣는다.
