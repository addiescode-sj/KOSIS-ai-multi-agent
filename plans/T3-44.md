# T3-44 계측 span 크기 상한

## Goal
- 완료 기준 (TASK.md 그대로): 서비스·평가 공용 계측에서 속성·오류 메시지·상태 설명 길이에 상한을 두어 한 문항의 span이 한도 안에 들게 한다.
  같은 실패 문항으로 전→후, pytest
- 계기 (2026-11-18, T3-43 live run `20261118-104236-T3-43-live2-e2e`): 평가 로그에 `grpc: received message larger than max (17765849 vs. 4194304)`
  12회 → Jaeger에서 span이 빠진 trace **13/90**(1개는 통째로 없음). 채점은 로컬 results.jsonl이라 수치 영향 0, trace만 불완전.
- Baseline (실측):
  - 원인 문항 S-CX-MON-01·02: 검색이 `101_DT_1B8000G`를 골랐고 실전 1이 `SchemaError`(중복 셀을 하나씩 나열한 **2.0 MB** 메시지)로 실패.
  - 그 메시지가 `record_exception`(exception.message + exception.stacktrace, 스택트레이스에도 메시지 포함)과 상태 설명에 그대로, 오류가 지나간 span(툴·노드·루트)마다 들어감.
  - 재현(같은 크기 메시지, span 3개): 한 문항 OTLP 크기 **18.7 MB**. SDK `SpanLimits(max_attribute_length=64 KB)`만 걸면 **6.6 MB**(상태 설명은 SDK 상한 밖) → 여전히 4 MB 초과.
  - 정상 span 크기: 툴 span 중앙 3~4 KB, 최대 6.6 KB(summarize_stat 결과 JSON).
  - 거부 단위가 묶음(BatchSpanProcessor 기본 최대 512 span)이라 한 문항의 거대 span이 이웃 문항 span까지 지움. 서비스도 같은 계측 → 운영 중 같은 오류 한 번이면 다른
    사용자 요청 trace도 소실, 온라인 평가(T3-43)가 그 턴을 못 읽음.

## Idea
**오류가 span에 기록되는 지점에서만 자른다.** 툴 결과 JSON 같은 정상 속성은 건드리지 않는다 — 평가 러너는 같은 provider로 메모리(채점용 results.jsonl)와 OTLP에
함께 보내므로, provider 전체에 속성 상한(SDK `SpanLimits`·`OTEL_ATTRIBUTE_VALUE_LENGTH_LIMIT`)을 걸면 채점에 쓰는 `gen_ai.tool.call.result`가 잘려
`turn_record`가 JSON 대신 문자열을 읽고 채점·온라인 복원이 조용히 틀어진다(리뷰).
- `short(text, limit=2 KB)` 헬퍼(`kosis_agent.observability.tracing`): 앞부분 + `… (+N자 생략, 전체 M자)`.
- `record_exception(error, attributes={"exception.message": short(...), "exception.stacktrace": short(traceback)})` — SDK가 속성 덮어쓰기를 허용해 형식 유지.
- 상태 설명 `set_status(..., short(...))`.
- 적용 지점: `LiveSpans._end`(툴·노드), LLM 오류 상태, 서비스 `_fail`, 평가 러너 턴 루트 2곳, `link_questions`·`link_verdicts`의 상태 설명과
  `kosis.failure.*` 속성(e2e `run_failure`의 실패 사유에 같은 2 MB 오류가 들어감).
- 전문은 범위 밖에서 그대로: 평가 results.jsonl의 `error`, 서비스 SSE `error` 이벤트·HTTP 500 본문(이번 태스크는 trace만).

## Option A — 오류 기록 지점만 자르기 (채점 경로 불변)
- 접근: Idea 그대로.
- 예상 성능 향상: 재현 문항 OTLP 18.7 MB → 수십 KB(span 3개 × 2 KB 메시지·스택트레이스·상태). 실패 2문항 재실행에서 묶음 거부 12 → 0, span 빠진 trace 0.
- 실질 반영 이점: 원인(상한 없는 오류 문자열)만 정확히 막고, 툴 결과·채점·온라인 복원은 바이트 단위로 그대로.
- 비용·리스크: 반나절 미만. 오류가 아닌 큰 속성(앞으로 큰 표·차트 spec이 툴 결과에 들어오는 경우)은 상한 없음 — 지금 최대 6.6 KB.

## Option B — A + OTLP로 나가는 사본만 속성 상한
- 접근: A + OTLP exporter를 감싸, 내보내기 직전에만 64 KB 넘는 속성을 잘라 보낸다(메모리·채점 경로는 원본 그대로).
- 예상 성능 향상: 이번 원인은 A와 같음. 앞으로 생길 큰 속성까지 Jaeger 한도 안.
- 실질 반영 이점: 방어 한 겹 더, 채점 영향 0.
- 비용·리스크: 반나절. exporter 래퍼(ReadableSpan 사본 생성) 유지 비용. 지금 데이터로는 효과 0.

## Option C — provider 전체 속성 상한 (SDK SpanLimits 또는 환경변수)
- 접근: `SpanLimits(max_attribute_length=64 KB)`를 서비스·평가 provider에 + 상태 설명 자르기. 코드 최소(환경변수면 0).
- 예상 성능 향상: 재현 18.7 MB → 약 0.4 MB.
- 실질 반영 이점: 모든 경로 한 번에.
- 비용·리스크: **채점 경로까지 자름**(64 KB 넘는 툴 결과가 생기면 results.jsonl의 JSON이 잘려 채점이 조용히 틀어짐) → 잘림 검출 장치를 따로 만들어야 함.

## Recommendation
**옵션 A.** 원인이 상한 없는 오류 문자열이므로 그 지점만 자르면 되고, 채점·온라인 복원 경로를 건드리지 않는다. B는 지금 데이터로 효과가 0인 방어라
큰 속성이 실제로 생길 때 추가한다(CLAUDE.md "필요한 것만 만든다"). C는 채점을 조용히 깨뜨릴 수 있다.
묶음 단위 확인: 정상 span 최대 6.6 KB × 512 = 3.4 MB로 한도 안, 오류 span은 A 뒤 수 KB → 오류 문항이 섞여도 한도 안(측정으로 확인).
