# T3-56 여러 표 문항을 실전 1 다중 표(T1-30)로 답하고 채점하기

## Goal
- 완료 기준 (TASK.md 그대로): 실전 1 pin을 master `c44151e`(T1-30 multi table 포함)로 올리고, 계산 골든 `CalcItem`이 `table_keys`(표 2~3개)를 받아 셀을 각 `source_ref`의 표에서 읽어 채점한다. 새 e2e 골든(팀 사람 골든 120문항, `questions.csv`·`facts.csv`)을 여러 표 문항 = 계산 항목 하나로 다시 만들고, 여러 표에 걸친 파생값(지금 채점 안 되는 52개)을 채점한다. 같은 골든으로 전→후 e2e 수치, pytest.
- Baseline: 새 e2e 골든(120)으로 잰 run 없음 → 구현 전에 지금 코드(pin `907b703`)로 같은 골든 baseline을 먼저 잰다.
  - 현재 골든 변환 결과: 여러 표 문항 37개(2표 25·3표 12, 전부 answerable). 표를 넘는 파생값 61개 중 `combine_values` 하나로 채점되는 것 9개, 채점 안 됨 52개.
  - 실전 1 T1-30 Result: dev 27문항 oracle 27/27, mock 3/27, HCX 미측정.

## Idea
1. **pin**: `vendor/phase1`을 `c44151e`로 올린다. 이 사이에 T1-29(로더 정리), T1-30(다중 표), T1-31(셀 창구 store), T1-32(차트 모듈)가 들어온다. `kosis_ai.schemas` 변경(StatInput.tables·StatAnswer.sources)이 이 레포 툴·채점기와 맞는지 pytest·verify.sh로 먼저 확인한다.
   - 실전 2 master가 고정한 실전 1은 `e248a45`라 CLAUDE.md의 "실전 2와 같은 커밋" 규칙과 어긋난다. 이번 태스크에서는 예외로 기록하고(CLAUDE.md 3장 문구 갱신), 실전 2 pin 맞추기는 실전 2 레포 PR로 따로 한다.
2. **채점기** (`evals/schemas.py`, `evals/evaluators/calculation.py`, `alternates.py`, `agent/numbers.py`, `tasks/l4_e2e.py`):
   `CalcItem.table_keys: list[str]`(기본 `[]` = `[table_key]`)를 추가한다. 셀 읽기는 `source_ref`의 첫 칸(tbl_id)으로 표를 나눠 표마다 `read_cells(path, refs)`를 부른다. `table_sha256`은 첫 표 그대로 두고, `table_sha256s`를 추가한다. 기존 단일 표 골든은 바이트 그대로 읽힌다(필드 생략).
3. **골든 변환**: 변환 스크립트를 `evals/builders/e2e_human.py`로 옮긴다(스크래치패드에서 지워질 수 있음). 여러 표 문항은 계산 항목 하나(`table_keys`, 모든 fact)로 만들고, 턴 기대값은 `summarize_stat` 한 번(args `table_keys`)이 된다.
4. **에이전트 툴** (옵션 B 이상): `summarize_stat`에 `table_keys`(선택)를 더해 2~3개면 `kosis_chat.api.summarize_stats_run`을 부른다. 결과의 `sources`가 출처 줄에 모두 나와야 한다(review 노드). 여러 표가 필요한 질문인지는 multi 노드가 하위 질문마다 찾은 표를 모아 한 번에 넘기는 방식으로 정한다.
0. 구현 전 측정(리뷰 반영): ① 지금 코드(pin `907b703`)로 새 골든 e2e baseline ② 새 pin에서 실전 1 T1-30 dev 27문항을 HCX로 한 번(`python -m eval.multi_dev --backend hcx`) — B의 예상치 근거. 둘 다 B·B-lite 공통.
5. 측정: 새 골든 e2e를 전(지금 코드)·후로 돌려 여러 표 37문항 숫자 정확도, 단일 표 83문항 회귀, 요청당 지연·비용을 남긴다.

옵션 공통(1~3): pin 갱신 + 채점기 `table_keys` + 골든 재변환. 옵션은 에이전트가 여러 표 질문을 실전 1에 어떻게 넘기는지로 갈린다.

## Option A — 채점기만 (에이전트는 그대로)
- 접근: 1~3만 한다. 에이전트는 지금처럼 하위 질문마다 summarize_stat + combine_values. 여러 표 파생값은 이제 채점되지만 에이전트가 만들지 못하므로 실패로 잡힌다.
- 예상 성능 향상: 지표 자체는 오르지 않는다. 여러 표 37문항 숫자 PASS는 지금 "부분 채점이라 과대평가된 값"에서 실제 값(대부분 FAIL 예상, 단일 binary op 9개만 가능)으로 내려간다. 근거: combine_values는 값 하나만 계산.
- 실질 반영 이점: 데이터 정확성 측정이 정직해진다(결과 검증). 다른 옵션의 baseline이 된다.
- 비용·리스크: 반나절. pin 업데이트 회귀가 유일한 리스크.

## Option B-lite — 원문 + 검색 상위 표를 바로 다중 표로
- 접근: multi 분해를 거치지 않는다. understand가 "여러 지표"로 본 질문은 원문 그대로 검색하고 picked 상위 2~3개의 서로 다른 표 키를 `summarize_stat(table_keys=...)`에 넘긴다. 어느 표를 쓸지는 실전 1 다중 표 계획(표마다 라벨)이 고른다. multi·combine_values 경로는 손대지 않고 이 분기에만 쓴다.
- 예상 성능 향상: 여러 표 37문항 숫자 PASS 0~25% → 측정 전 추정 ~30%. 근거: 원문 한 번 검색의 상위 후보는 같은 지표의 비슷한 표가 많아, 필요한 표 둘이 상위 3개에 함께 드는 비율이 낮을 것(새 골든 L1으로 먼저 잰다).
- 실질 반영 이점: 바꾸는 코드가 가장 적고(분기 하나 + 툴 인자), 검색 한 번이라 지연이 적다.
- 비용·리스크: 1일. 엉뚱한 후보 표가 섞이면 실전 1이 틀린 표로 계산할 위험(T3-23의 틀린 표 사례와 같은 종류).

## Option B — multi 분해로 표를 모아 다중 표 한 번 (Recommended)
- 접근: 1~4. multi 노드는 지금처럼 하위 질문으로 나눠 각각 검색한다. 그다음 규칙:
  - 분해가 op(diff·sum·ratio)를 정했고 하위 질문이 각각 혼자 답할 수 있는 질문이면(기존 MQ, "A는? B는? 둘을 더하면?") → 지금처럼 하위 답 + combine_values. 부분 거절(T3-38 refuse_parts)도 이 경로 그대로.
  - 그 밖에 표가 서로 다른 경우(원문 하나가 여러 표의 값을 엮어야 하는 질문: 자연증가, 출처 간 차이, 비율 분자·분모) → `summarize_stat(question=원문, table_keys=[하위 질문별 1순위 표])` 한 번.
  - 다중 표 호출이 거절하면 되돌아가는 경로: 하위 질문 답(표마다 summarize_stat)을 그대로 보여 주고 표를 넘는 계산은 하지 않는다고 말한다(지어내지 않음).
- 예상 성능 향상: 여러 표 37문항 숫자 PASS 0~25% → ~40~50%. 근거: T1-30 oracle 27/27(표가 맞으면 계산 코드는 맞음) × 하위 질문별 1순위 표 적중률(새 골든 L1) × HCX 다중 표 계획 정확도(0단계 ②에서 측정, 측정 후 이 추정을 고친다). 단일 표 83문항·기존 MQ 골든 회귀 0 목표.
- 실질 반영 이점: 데이터 정확성·기능 완성도. "숫자는 코드가 계산" 원칙을 여러 표 계산까지 유지하고, 계산 로직이 실전 1 한 곳에만 있다. 기존 MQ·부분 거절 계약을 지킨다. 발표에 "여러 표 문항 몇 → 몇"이 남는다.
- 비용·리스크: 1~2일. 지연: `summarize_stats_run`은 캐시가 없어(docstring "Not cached") 호출마다 표 로드와 파이프라인을 새로 만든다. 그래서 지연은 하위 질문 두 번보다 늘 수 있다. 측정해서 기록하고, 문제가 되면 실전 1에 캐시 PR을 따로 낸다. 리스크: 하위 검색이 한 표를 틀리면 틀린 표로 계산(재생 측정에서 확인).

제외한 안: combine_values 폐기·MQ까지 다중 표로 통일(기존 C) — 부분 거절(T3-38)·기존 MQ 골든을 다시 만들어야 하고 여러 표 문항 이득은 B와 같다. combine_values를 값 여러 개로 늘리는 안 — 실전 1에 이미 있는 계산을 이 레포에 다시 짜는 것이다.
