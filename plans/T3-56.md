# T3-56 CI 이미지 저장 (GHCR) — 자동 배포 연동 1단계

## Goal
- 완료 기준 (TASK.md 그대로): main push에서 backend·frontend·migrate 이미지 3개를 커밋 번호 태그로 GHCR에 저장하고, 3개가 모두 저장된 뒤 배포 대상 표시(`main` 태그)를 옮긴다. PR에서는 저장하지 않는다. 이미지에 제공 데이터·`.env`가 없다. 검사 이름(`verify`, `images`)은 그대로다.
- Baseline (11/25 배포 기록, 저장소 밖 `kosis-infra/08-배포-기록-2026-11-25.md`):
  - 배포마다 사람이 node-1에서 하는 일 6단계(코드 사본 받기, 빌드, node-2에 이미지 옮기기, 설정 사본, 태그 수정, 적용). 빌드는 node-1(t3.large, 서비스 중인 노드)에서 함
  - CI 실행 4~5분, `images` job은 `docker build`만 하고 저장 안 함, migrate 이미지는 CI에서 만들지 않음
  - 서버에 배포된 코드가 어느 커밋인지 이미지만으로 알 수 없음(태그는 `1125mms2`처럼 손으로 정함)

## Idea
CI/CD 전체 계획은 저장소 밖 `kosis-infra/10-CICD-자동배포-계획.md`다. 11/26 결정은 연동은 모두 구성하되 자동 배포는 꺼 두는 것이다. 이 태스크는 그중 저장소 안 부분인 `.github/workflows/ci.yml`만 바꾼다.

서버(node-1)는 저장소 밖 스크립트로 배포한다. 수동 명령이나 꺼 둔 예약 실행으로 하며, GitHub에 서버 키는 넣지 않는다. 서버 스크립트, k8s 설정, DB 백업은 이 태스크 범위가 아니다.

**모든 옵션에 공통으로 들어가는 것** (옵션 비교와 무관):
- PR에서는 지금처럼 빌드 검사만 한다. main push에서만 GHCR에 로그인해 저장한다. 권한은 `images` job에만 `packages: write`.
- 이미지 3개: `ghcr.io/addiescode-sj/kosis-agent-{backend,frontend,migrate}`, 태그 `sha-<커밋 전체>`.
  - backend는 `--target backend`, migrate는 `--target migrate`(지금 CI에 없음).
  - 둘은 같은 base 단계를 쓴다.
- 검사 이름 유지: job을 나누거나 matrix로 바꾸지 않는다. matrix는 이름이 `images (backend)`처럼 바뀐다. `images` job 안에서 순서대로 실행한다.
- 이미지 표시(OCI label): 커밋 번호, 저장소 주소. 저장소 주소는 패키지를 이 저장소에 연결한다. `provenance: false`로 태그가 이미지 하나만 가리키게 한다.
- 저장 전 검사: 이미지 안에 `/app/data`, `/app/vendor/*/data`, `.env*` 파일이 없어야 한다.
  - CI 사본에는 `data/`, `.env`가 원래 없으므로 지금은 늘 통과한다. 앞으로 COPY 추가나 실수로 커밋된 파일을 막는 장치다.
  - `frontend/.dockerignore`에 `.env*`가 없어 로컬 빌드 위험은 남는다. 앱 파일이라 이 태스크에서 고치지 않고 담당자에게 전달한다.
- backend `WITH_EMBED=0`: 지금 main Dockerfile은 이 값을 쓰지 않아 경고만 나온다. `min-multiagent-service`가 merge되면 torch 없는 판이 된다.
  - 서버 배포판은 원래 torch 없이 GPU 서버의 임베더·리랭커(`EMBED_URL`, `RERANK_URL`)를 부르는 구성이다(11/25 2·3차 배포). 이 이미지들은 서버 배포용이라 의도한 동작이다.
  - 로컬 compose는 이 값을 쓰지 않아 영향이 없다.
- 빌드 캐시: 이미지별 범위, `mode=min`. 지금 main backend는 CPU torch가 들어 있어 수 GB이고, 캐시 한도 10GB를 넘지 않게 한다.

## Option A — 커밋 번호 태그만, 서버가 고름
- 접근: 공통 항목만. 서버 스크립트는 main 최신 커밋(`git ls-remote`)을 확인하고, 그 커밋의 이미지 3개가 모두 있을 때만 배포한다.
  - 하나라도 없으면(CI 진행 중이나 실패) 아무것도 하지 않는다.
  - CI 쪽에는 순서 처리나 태그 옮기기가 필요 없다.
- 예상 성능 향상: 서버 스크립트와 패키지 공개(또는 서버의 읽기 전용 토큰)가 준비되면 배포 수동 단계 6 → 1(배포 명령). 그 전에는 향상 0. node-1에서 빌드하지 않음(근거: 빌드·tar 옮기기가 CI·레지스트리로 이동).
- 실질 반영 이점: 기술 설계(커밋과 이미지 1:1, 재현 가능). 예외 처리(3개 모두 있는 커밋만 배포). 가장 작은 CI 변경.
- 비용·리스크:
  - 최신 커밋의 CI가 실패하면 다음 merge까지 배포 대상이 없다. 이전 커밋은 `--sha`로 지정한다.
  - 연달아 merge하면 중간 커밋은 CI가 건너뛰어 이미지가 없을 수 있다. 최신만 배포하므로 문제없다.

## Option B — A + `main` 태그로 배포 대상 표시
- 접근: A에 더해 3개가 모두 저장되면 세 이미지에 `main` 태그를 붙인다(`docker buildx imagetools create`, 다시 빌드 안 함).
  - 붙이기 전에 이 커밋이 아직 main 최신인지 GitHub에 묻는다(`git ls-remote`, 체크아웃이 얕아 로컬로는 모름).
  - main push 실행만 같은 순서 그룹(`concurrency`)에 넣는다.
  - 서버는 `main` 태그 하나만 읽는다.
- 예상 성능 향상: A와 같다(6 → 1). 서버 스크립트가 GitHub에 묻지 않아도 되는 정도의 차이.
- 실질 반영 이점: "검사를 통과한 최신 배포판"이 레지스트리에 한 이름으로 남는다.
- 비용·리스크:
  - CI 단계 2개 추가, 순서 그룹 설정 필요.
  - 실패하면 `main` 태그가 옛 커밋에 남아 A와 같은 결과다. 결국 서버도 커밋 확인이 필요하다(되돌리기 `--sha`).

## Option C — B + Actions에서 서버 배포
- 접근: B에 더해 Actions job이 SSH로 node-1에 접속해 배포한다. 배포 승인 버튼(environment) 사용.
- 예상 성능 향상: 배포 결과가 GitHub 화면에 남음. 수동 단계는 1(버튼).
- 실질 반영 이점: 배포 이력이 GitHub에 모임.
- 비용·리스크:
  - 서버 SSH 키를 저장소 secret에 넣어야 하고 저장소 관리자만 등록할 수 있다.
  - 서버가 자동 중지되어 꺼져 있으면 실패한다. 22번 포트를 GitHub에 열어 둬야 한다.
  - 11/26 결정(서버 쪽 스위치, 키를 GitHub에 두지 않음)과 맞지 않는다. 비교용으로만 남긴다.

## Recommendation
옵션 A. B의 `main` 태그는 A보다 나은 안전장치가 없다. 순서 그룹, 최신 확인, 태그 옮기기만 늘고, 서버가 확인할 것(3개 모두 있는가)은 같다. 자동 배포를 켤 때도 저장소 변경이 필요 없다.

## Decision
옵션 A (김병석, 2026-11-26). CI는 커밋 번호 태그만 저장하고, 배포할 커밋은 서버 스크립트가 고른다(main 최신 커밋의 이미지 3개가 모두 있을 때만). 자동 배포는 꺼 둔다. 이미지는 공개(패키지 소유자 이선주가 설정), main merge 승인 0명 유지·필수 검사만 추가.
