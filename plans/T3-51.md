# T3-51 멀티표 한 질문: 2차 리랭커의 멀티표 판단 → 실전 1에 표 2~3개

## Goal
- 완료 기준 (TASK.md 그대로): 멀티쿼리(T3-28)를 쓰지 않는 한 질문 경로에서 실전 2 2차 리랭커가 표 여러 개가 함께 필요하다고 판단하면 statistics 노드가 그 표 2~3개를 실전 1 `summarize_stats_run`(T1-30, phase1 `cdccc39`)에 한 번에 넘긴다. 표 사이 계산은 실전 1 코드. 실전 1 multi_table_dev 27문항을 에이전트 시나리오로 옮겨 수치 정확도 전→후, e2e 골든(T3-46)으로 한 표 과판단·회귀 0.
- Baseline:
  - 실전 1 단독, 정답 표 목록을 줄 때: `vendor/phase1/eval/dev/multi_table_dev.jsonl` 27문항(answer 24 + refuse 3) oracle 27/27, mock 3/27, **HCX 미측정** (`vendor/phase1/plans/T1-30.md` Result).
  - 에이전트 경로: **baseline 없음**. 지금은 표 하나만 넘기므로 표 두 개가 필요한 문항은 구조상 답할 수 없다. 구현 전에 같은 27문항을 지금 그래프로 돌려 baseline을 잡는다.
  - 검색 상한: **미측정**. 참고로 실전 2 L1 multi_table 7문항 Complete@2 = Complete@3 = 2/7(T3-34, 이미 2차를 거친 값, 다른 셋). 27문항으로 Complete@2(필요한 표가 모두 picked 2위 안)를 Step 0에서 먼저 잰다. 이 값이 모든 옵션의 상한이다.
  - 한 표 회귀 기준: e2e 골든 `eval/golden/e2e_golden.jsonl` + `e2e_golden_calc.jsonl`(T3-46)은 멀티표 문항 0개(전부 한 표). 이 셋 dev로 "멀티로 잘못 판단한 턴 수"와 수치 정확도 회귀를 본다.

## 적용 범위 (리뷰 반영)
- context가 멀티쿼리로 보내는 턴(규칙·LLM 분해가 서로 다른 지표 2개 이상으로 나눈 턴, T3-28)은 이 경로에 오지 않는다. 이 태스크가 다루는 것은 **나눌 수 없는 관계형 질문**("혼인 100건당 이혼", "추계 대비 실적", "혼인이 이혼보다 몇 건 많아")과 분해기가 나누지 않은 턴이다. multi_table_dev 27문항 중 지금 분해기가 나누는 문항 수를 Step 0에서 함께 센다(그 문항은 멀티쿼리 경로로 답함).

## Idea
0. Step 0 (모든 옵션 공통, 코드 변경 없음): 27문항으로 ① 검색 Complete@2 ② 분해기가 나누는 문항 수 ③ 지금 그래프 수치 정확도(baseline)를 잰다.
1. 판단: 2차 리랭커 결과에서 "함께 써야 할 표 묶음(needed)"을 얻는다 (옵션마다 방법이 다름).
2. 계약: `SearchOutput`(실전 2)은 그대로 두고, 판단 결과는 stage2 메타데이터(문서마다 붙는 `stage2_*` dict)에 키를 더해 싣는다.
3. 툴: `summarize_stat`에 선택 인자 `table_keys: list[str] | None`(2~3개)을 더한다. 있으면 실전 1 `summarize_stats_run`, 없으면 지금 그대로 `summarize_stat_run`. `table_key`는 첫 표로 계속 채워서 하네스 `state_key()`·L3 채점이 그대로 읽게 한다.
4. 그래프: statistics 노드가 needed가 2개 이상이면 `table_keys`로 한 번 묻는다. **멀티 답이 거절이면 picked[0] 한 표로 다시 묻는다**(지금 경로와 같은 답으로 돌아감). 지시어 이월 턴은 직전 표(들)를 그대로 쓴다.
5. 출처: 실전 1 multi 그래프가 `StatAnswer.sources`(표 전부, source = 첫 표)와 출처 줄 하나를 채운다(`kosis_chat/graph/multi.py` with_sources에서 확인). finalize가 sources를 출처에 쓴다.
6. 측정: 27문항 에이전트 시나리오(정답 = search_tables 1회 + summarize_stat table_keys) 전→후, e2e 골든 dev 한 표 과판단·회귀.

## Option A — 판단 없이 2차 1·2위를 실전 1 멀티 계획에 맡김
- 접근: 2차 v4 그대로. 2차가 2개 이상 골랐고 멀티쿼리가 아닌 턴이면 picked 1·2위를 늘 `summarize_stats_run`에 넘기고, 실전 1 MultiStatPipeline의 계획(표마다 select)이 어느 표를 쓸지 정한다.
- 예상 성능 향상: 멀티표 dev 수치 정확도 0 → Step 0 상한 × 실전 1 HCX 멀티 계획 정확도(둘 다 미측정이라 수치 추정 없음). 한 표 과판단: 2차가 2개 이상 고르는 한 표 턴 전부가 멀티 계획을 타므로 크다. 두 번째 표가 섞이면 한 표 수치 정확도가 바로 깨질 위험.
- 실질 반영 이점: 실전 2 수정 0, LLM 호출 수 0 추가, 구현 가장 작음.
- 비용·리스크: 반나절. 한 표 질문 대부분이 멀티 계획(프롬프트가 다름)을 타서 한 표 회귀 위험이 가장 크다. 사용자가 정한 "2차 LLM 판단" 설계와 다르다.

## Option B — 2차 리랭커 출력에 together 필드 (v4 → v4m, 이 레포 selector 래퍼로 먼저)
- 접근: v4 본문은 그대로 두고 출력에 `"together": [후보 번호 2~3개] | null`만 더한 `stage2-hcx-v4m.md`. v4 예시 2("지표마다 한 표씩" picked)와 겹치지 않게 의미를 "질문 하나의 답을 계산하려면 표들을 함께 읽어야 할 때만"으로 좁히고, 한 표 예시에 together=null을 명시한다. 파서는 together를 읽어 `stage2_together`(picked 안의 키, 2~3개, 서로 다름; 아니면 버림)로 싣는다. 판단은 2차 LLM, 검사는 코드. **처음에는 이 레포에서 실전 2 HcxSelector를 감싼 래퍼로 붙이고(실전 2 코드 무수정, 설정으로 v4/v4m 전환), 측정 후 채택이면 실전 2 PR로 옮긴다.**
- 예상 성능 향상: 멀티표 dev 0 → Step 0 상한 × 실전 1 HCX 멀티 계획 정확도 (추정치 없음, Step 0 후 plan에 기록). 한 표 과판단 목표 0건(e2e 골든 dev), 넘으면 예시를 고치거나 기각.
- 실질 반영 이점: 사용자가 정한 설계 그대로. 호출 수 같음(출력 토큰 몇 개 증가). together 정확도를 L1에서도 따로 잴 수 있다.
- 비용·리스크: 1~1.5일. 프롬프트가 바뀌므로 picked가 흔들릴 수 있다 → L1 KOS-192 600문항(Qwen off + condyears) 재측정 필수(~45분, Colab 서버). Hit@1이 0.01 넘게 떨어지면 v4로 되돌림. 마감(11/30) 안, 실전 2 PR은 채택 뒤라 리뷰 대기가 막지 않음.

## Option C — 2차 뒤 멀티 판단 전용 LLM 한 번 (관계어 사전 필터)
- 접근: 2차·v4 그대로. 관계어("당·대비·보다·비율·비중·차이·합") 사전 필터를 통과하고 멀티쿼리가 아닌 턴만, 질문 + picked 1~2위 표 설명을 작은 모델(`INTERPRETER_MODEL`, gpt-4o-mini)에 주고 `{"tables": [...]}`를 받는다. 코드가 검사.
- 예상 성능 향상: 멀티표 dev는 B와 같은 상한(추정치 없음). 한 표 과판단 목표 0건, 관계어 필터로 대부분 턴은 호출하지 않음. 단 관계어는 한 표 비교 질문("서울과 부산 차이")에도 흔해 필터 통과 턴이 적지 않다.
- 실질 반영 이점: 실전 2·L1 최고 설정 무변경, L1 재측정 불필요.
- 비용·리스크: 1일. 필터 통과 턴은 LLM 1회(~0.5~1 s) 추가. 2차 LLM 판단이 아니다.

## Recommendation
옵션 B. 사용자가 정한 설계와 같고 호출 수가 늘지 않는다. 이 레포 래퍼로 먼저 붙여 실전 2 PR 대기 위험을 없애고, 채택 조건을 숫자로 둔다: ① e2e 골든 dev 한 표 과판단 0건 ② L1 KOS-192 Hit@1 하락 ≤ 0.01 ③ 27문항 수치 정확도 baseline보다 상승. 하나라도 못 넘으면 v4로 되돌리고 C를 검토한다. 어느 옵션이든 Step 0을 먼저 해서 상한을 숫자로 적는다.
