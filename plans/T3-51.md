# T3-51 표 안 항목(분류 코드) 오선택 줄이기 — 질문 낱말 하나가 두 분류축에 코드를 거는 문제

## Goal
- 완료 기준 (TASK.md 그대로): 표는 맞게 찾았는데 실전 1이 다른 칸을 읽는 턴(wrong_dims)을 줄인다. 같은 per10 e2e 표본과 실전 1 stat 골든으로 전→후를 남기고, 실전 1 회귀가 없다.
- Baseline: e2e per10(40대화·57턴, 로컬, Qwen 판단 b + 프롬프트 수정) `evals/reports/20261124-121725-T3-03-after-b-prompt-per10-local/`
  대화 성공률 0.625 · 최종 수치 정확도 0.617(29/47) · wrong_numbers 18턴 (그중 wrong_dims 7턴)

## 진단 (2026-11-24, 위 run의 실패 21턴)
처음 가설은 "에이전트가 summarize_stat에 dimensions를 비워 넘겨서 실전 1이 항목을 추측한다"였다. 확인해 보니 틀렸다.
- 실전 1은 `dimensions` 인자를 받지 않는다(`services/statistics.py`: 기록·채점용, 실전 1은 질문 문장에서 조건을 읽음).
- 실전 1 analyze에는 이미 "표 메뉴 → 모델이 코드 선택 → 표에 있는 코드만 통과"(analyze-fill-v2, T1-06)가 있다. 규칙이 못 정한 분류만 모델에 간다.
- 표가 맞은 실패 12턴은 **모두 규칙 경로(`plan_rules`)로 끝났고 fill은 한 번도 돌지 않았다** → 규칙이 틀린 코드를 확신하고 정했다.

표는 맞았는데 수치가 틀린 12턴의 원인 (`rule_plan` 결과와 `e2e_golden_calc.jsonl` 정답 셀 비교):

## Idea
①의 공통점은 "질문 낱말이 이미 다른 곳에 쓰였는데 또 코드를 고른다"이다. 이미 쓰인 곳은 두 경우다.
(가) 같은 낱말이 다른 축에서 이미 코드를 골랐다(미상).
(나) 그 낱말이 표 이름(`tbl_nm`)이나 조사명(`survey_nm`)에 들어 있다. 기타는 표 이름 "한국국적을 취득한 자-기타(계)"에, 사할린은 조사명 "영주귀국사할린동포실태조사"에 있다.
고칠 위치는 실전 1 `kosis_chat/analyze/rules.py` `rule_plan` 안, `resolve` 호출 **뒤**다. `judge/rules.resolve`를 고치면 judge 판정(`_same_name`·`_no_cell`·`_unit_mismatch`)까지 바뀌므로 건드리지 않는다.
지운 축을 계·전체로 채울 때는 `default_applied`에 가정("연령 계 기준" 등)을 남긴다. 조용히 바꾸지 않는다. 실전 1은 submodule이라 실전 1 레포에 PR → 여기서 `git submodule update --remote vendor/phase1`.
측정은 같은 per10 e2e 표본, 실전 1 stat 골든 회귀(`vendor/phase1`에서 `python -m eval.run_eval` → `python -m eval.regress --run …`, 기준선 `eval/baselines/stat.json`), 끝으로 e2e test 전체 1회로 한다.

## Option A — 규칙 보정 (결정적, 실전 1 rules.py)
- 접근: `rule_plan`이 코드를 정한 뒤 두 규칙을 더한다.
  (가) 같은 `Match.form`(공백 제거한 낱말)이 ITEM_AXIS와 다른 축에 함께 코드를 걸면 ITEM_AXIS만 남기고 다른 축은 지운다(→ 기본값 계·전체). 둘 다 항목 축이 아니면 정하지 않고 `unresolved`로 넘긴다.
     `match_labels`에는 문자열 위치가 없고, `_dedupe`가 이미 "짧은 form이 긴 form 안에 들어간" 경우를 지우므로 남는 경우는 form이 똑같을 때뿐이다(리뷰 3).
  (나) ITEM_AXIS가 아닌 축에서 일치한 form이 3글자 이상이면서 표 이름·조사명(`meta.tbl_nm`·`meta.survey_nm`)에 들어 있거나, 표 이름의 구분된 조각(`-기타`, 괄호 안)과 통째로 같고, 그 축에 합계 코드가 있으면 그 축은 고르지 않는다(→ 계·전체).
     항목 축을 빼는 이유: 항목 이름은 표 이름에 자주 들어간다("…합계출산율" 표에 "합계출산율" 질문, 리뷰 4).
- 예상 성능 향상 (**상한**): per10 최종 수치 정확도 0.617 → 최대 0.766(29 → 36/47, 7턴 모두 고치고 회귀 0일 때) · 대화 성공률 0.625 → 최대 0.70(25 → 28/40).
  근거: ① 7턴 중 (가)가 XY-002 3턴, (나)가 XY-009 3턴·value-003 1턴을 대상으로 한다. 멀티턴은 첫 턴 코드가 이어지므로 3턴이 같이 바뀐다. 대상이 3대화뿐이라 결과는 "최대 +7턴"으로 쓰고 e2e test 전체 확인을 필수로 둔다(리뷰 2).
- 실질 반영 이점: 데이터 정확성(평가 1순위). LLM 호출·지연 0. 실전 1 모듈 자체가 좋아져서 실전 2·종합이 같이 이득을 본다. "규칙 2개로 0.62 → 0.74"처럼 설명하기 쉽다.
- 비용·리스크: 반나절 + 실전 1 PR. (나)는 표 이름 낱말을 일부러 묻는 질문("기타 국적은?")을 놓칠 수 있다 → 실전 1 stat 골든 회귀로 확인하고, 회귀가 나면 (나)를 "합계 코드가 있고 질문에 '중'·'별' 같은 하위 지정 말이 없을 때"로 좁힌다. 마감(11/30 기능 동결) 안.

## Option B — 혼합: (가)는 규칙, (나)는 실전 1의 기존 모델 fill에 넘김 (리뷰 5 제안)
- 접근: (가)는 A와 같은 규칙으로 고친다. (나) 상황(비항목 축 form이 표 이름·조사명과 겹침)은 규칙이 정하지 않고 그 축을 `Plan.unresolved`에 올린다. 그러면 이미 있는 analyze-fill-v2(HCX)가 표 메뉴에서 그 축의 코드를 고르고, 표에 없는 코드는 코드가 버린다. 처음 제안한 "표 실제 항목 목록에서 LLM이 고르고 코드가 검증"을 맞는 위치(실전 1)에서, 모호한 경우에만 하는 안이다.

  근거: (가) 3턴은 A와 같다. (나) 4턴은 모델 선택에 달렸다. fill이 "기타"를 다시 국적 기타로 고르면 덜 고친다(실측 전).

- 비용·리스크: (나)에 걸리는 턴에만 HCX 1회(+2~4s, 요청당 +0.1~0.3원 추정). fill 프롬프트에 "표 이름·조사명에 있는 낱말은 그 표 전체를 가리킨다"를 넣어야 같은 실수를 피한다. 1일 + 실전 1 PR.

## Recommendation
