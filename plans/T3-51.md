## 세 옵션의 차이: 대화 상태·소유권·만료를 어디서 판정하나

배포는 서비스 서버 2대(node-1·node-2, k3s, 11/23 생성 — `kosis-infra/01·05` 문서, 저장소 밖)다. 요청이 어느 노드로 가도 같은 대화를 이어야 한다.

## Option A — 메모리 상태 유지 + 같은 노드 고정(sticky)
- 접근: checkpointer는 InMemorySaver 그대로. ingress에 쿠키 기반 고정(같은 브라우저 → 같은 backend pod). 만료·소유권은 프로세스 메모리 표(`thread_id → session_id, last_used_at`)로 판정. 피드백·삭제 대상 확인도 같은 표. `/feedback`은 `feedback` 테이블에 저장(이건 DB 필요).
- 예상 효과: 계약 테스트 S1~S9 중 S1~S4·S6~S9 통과(8/9). S5(재시작 뒤 이어 묻기)는 실패 그대로. 근거: 저장 위치만 메모리이고 판정 규칙은 B와 같다.
- 실질 반영 이점: 새 의존성 0, 가장 빠름(1~1.5일). 
- 비용·리스크: pod 재시작·배포 때마다 모든 대화 맥락이 사라짐. pod가 죽으면 그 노드 사용자 전부 끊김. 11/08 결정(PostgreSQL session id)과 다름. ingress 설정 의존.

## Option B — PostgreSQL checkpointer + 세션 테이블
- 접근: LangGraph sync `PostgresSaver` + psycopg `ConnectionPool`(핸들러가 sync `def`). 직렬화 허용 목록 `CHECKPOINT_TYPES`를 같게 넘긴다. 별도 `chat_sessions` 테이블(`thread_id` PK, `session_id`, `created_at`, `last_used_at`)과 `chat_requests`(`request_id` PK, `thread_id`, `session_id`, `created_at`)를 **`meta`를 보내기 전에 동기로** 쓴다 → 소유권·만료·피드백 404를 로그 쓰기 스레드와 상관없이 판정(경합 없음).
- 예상 효과: S1~S9 통과 9/9. 
- 실질 반영 이점: 11/08 결정 이행(Redis 없이 PostgreSQL 하나), 노드·재시작과 무관. 세션·요청 테이블은 나중 로그인 태스크와 정리 배치에서 그대로 씀.
- 비용·리스크: 2.5~3일. 의존성 `langgraph-checkpoint-postgres` 1개. checkpoint 테이블은 `PostgresSaver.setup()`이 Alembic 밖에서 만듦 → `migrations/env.py`에 `include_object` 필터를 넣어 autogenerate가 지우지 않게 함. DB가 없거나 실패하면 메모리로 떨어지고 경고(답은 계속 나감).

## Option C — PostgreSQL checkpointer만 (세션 테이블 없음)
- 접근: B와 같은 `PostgresSaver`. 소유권·만료는 별도 테이블 없이 checkpoint metadata(`session_id`를 config metadata로 기록)와 마지막 checkpoint 시각으로 판정. 피드백 404는 `request_logs.session_id`로 판정.
- 예상 효과: S1~S8 통과, S9(답 직후 피드백)는 `request_logs`가 응답 뒤 별도 스레드로 써져 거짓 404가 날 수 있음 → 8/9(경합 시).
- 실질 반영 이점: 새 테이블 0, 마이그레이션 최소.
- 비용·리스크: 2일. checkpoint 내부 형식(metadata 질의)에 의존 → LangGraph 버전이 바뀌면 깨질 수 있음. 내부 트래픽·trace 없는 요청은 `request_logs` 행이 없어 피드백을 못 받음.

## Recommendation
**Option B.** 세 노드 고정·재시작 문제가 없고(A 대비), 피드백 판정에 경합이 없다(C 대비). 추가 비용은 테이블 2개와 반나절이다.
