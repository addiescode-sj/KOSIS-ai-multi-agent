# T3-29 평가 모듈 태스크별 분리

## Goal
- 완료 기준 (TASK.md 그대로): `evals/run_eval.py`(691줄)에 섞인 계층별 실행·리포트를 평가 태스크마다 모듈로 나누고,
  에이전트 채점기를 툴·멀티턴 상태·수치(멀티쿼리 포함)·답변 품질로 나눈다. 같은 실행을 재채점해 리팩토링 전후 summary가
  같음을 확인(패리티), 오프라인 pytest 통과
- Baseline (지표가 아니라 구조):
  - `run_eval.py` 691줄 — CLI, 8개 계층의 `run_*`(실행+채점 호출+report.md 문자열), 고칠 담당(`owner_section`의 계층별 if),
    trace 섹션, manifest·ops_history 기록(계층별 if 6곳)이 한 파일에 있다. 새 평가 하나 넣으려면 이 파일 5곳 이상을 고친다.
  - `evaluators/agent.py` 379줄 — `grade_turn` 한 함수(80줄)가 툴 선택·인자, 상태(지시어·이월), 거절, L3 수치,
    멀티쿼리 하위 수치(`calc_qids`)·합산(`combine_value`), 답변 품질(근거 없는 숫자)을 모두 판정한다.
  - 리포트에 멀티턴(`MT-*`)·멀티쿼리(`MQ-*`) 성공률이 따로 없다 (README §6: "results.jsonl의 sid로 나눠 본다").
  - 기준 실행(재채점 패리티용): `20261110-151003-T3-28-mq-gpt4omini`(멀티쿼리, 대화 성공 0.948 · 수치 0.969),
    `20261110-140723-T3-27-relyear-paraphrase-hybrid`(멀티턴, 대화 성공 0.886), `T3-28-oracle`(1.000), L1·L3 재채점 가능한 최근 실행.

## Idea
동작은 바꾸지 않는 리팩토링이다. 순서: ① 패리티 기준 수집(리팩토링 전 코드로 oracle·`--from-run` 재채점 summary 저장)
→ ② 모듈 이동 → ③ 같은 명령 재실행, `summary`·`results.jsonl` 동일 비교 → ④ pytest·`scripts/verify.sh`.
CLI(`python -m evals.run_eval --layer ...`), 결과 폴더 형식, `ops_history.jsonl` 형식, `evals.suite`·`report_html`이 읽는 manifest 키는 그대로 둔다.

## Option A — run_eval만 태스크 모듈로 쪼갬
- 접근: `evals/tasks/` 아래 계층마다 한 파일 — `l0_metadata.py` · `l1_retrieval.py` · `l2_query.py` · `ablation.py`(l012 포함) ·
  `l3_calculation.py` · `e2e.py` · `agent.py`. 각 파일은 `run(args) -> (rows, summary, report)`와 그 계층의 `owners(rows, summary)`,
  history `target(args, op)`를 둔다. `run_eval.py`는 CLI + `TASKS = {"l0": l0_metadata, ...}` 표 하나 + 폴더 기록만(~200줄).
  공용 리포트 조각(ops·trace 섹션, `pct`, `calc_items`)은 `evals/tasks/common.py`. `evaluators/agent.py`는 손대지 않는다.
- 예상 성능 향상: 평가 지표 변화 0 (리팩토링). 구조: `run_eval.py` 691 → ~200줄, 새 평가 추가 시 run_eval 안에서 고치는 곳 5+ → 1(표 한 줄 + 새 파일). `suite.metrics`·`report_html` `dedicated`는 그대로라 전체로는 4곳(리뷰 1).
- 실질 반영 이점: 기술 설계·결과 검증. T3-07~10(아키텍처 3종 비교)에서 agent 태스크만 열면 된다. 패리티로 "동작 동일"을 수치로 남김.
- 비용·리스크: 0.5일, LLM 비용 0(재채점·oracle만). 테스트가 `run_eval.run_agent`·`run_l1`·`owner_section`을 import하고,
  `test_evals_ablation`은 `run_eval.run_l0/run_ablation/run_l2`, `test_evals_e2e`는 `run_eval.CALC_GOLDEN/REPORTS/ROOT`를 monkeypatch한다(리뷰 3a)
  → l012는 `l0_metadata.run` 식으로 모듈 속성을 거쳐 부르고, 상수는 정의된 모듈에서 읽어 patch 대상을 새 위치로 옮긴다.
  요청의 핵심(답변 품질·멀티턴·멀티쿼리 분리)은 채점기 안에 그대로 섞여 남는다.

## Option B — A + 에이전트 채점기를 평가 태스크별로 분리 (+ 태스크별 성공률)
- 접근: A 전부, 그리고 `evaluators/agent.py` → 패키지 `evaluators/agent/`:
  - `tools.py` — 툴 선택·순서·빠진/불필요 호출·인자 (`final_calls`, 대체 표 시도 제외 포함)
  - `state.py` — 멀티턴: 끝난 표(`state_key`)·지시어/이월(`lost_state`)·거절(`missed/false_refusal`)
  - `numbers.py` — 수치: L3 연결(`calc_qid`), 멀티쿼리 하위 수치(`calc_qids`)·합산(`combine_value`), 대체 표 동일 값
  - `answer.py` — 답변 품질: 근거 숫자 수집(`_grounding`)·`unsupported_final_numbers`
  - `__init__.py` — `grade_turn`이 네 모듈 결과를 합치고 `ERRORS`·`grade_conversation`·`aggregate`·oracle 유지
    (`from evals.evaluators import agent` 경로 그대로 → 테스트·`tests/test_workflow.py` import 무변경).
  - `aggregate`에 `by_task` 추가(기존 키는 그대로): sid 접두어로 `multiturn`(MT-*)·`multiquery`(MQ-*)·기타별
    대화 성공률·턴 통과율·수치 정확도 + `answer_quality`(근거 없는 숫자 턴, 수치 PASS). report.md에 표 하나 추가.
    sid 접두어는 빌더(`builders/multiturn.py` `MT-`, `builders/multiquery.py` `MQ-`)가 정한다.
  - MT·MQ 시나리오가 파일이 따로라 한 실행에 섞이지 않으면 `by_task`가 전체와 같다(리뷰 2) → `--scenarios`를 여러 파일(`nargs="+"`, sid 중복 금지)로 받아
    한 실행에서 멀티턴·멀티쿼리를 같이 돌리고 따로 본다. 파일 하나만 주면 지금과 같다.
- 예상 성능 향상: 기존 지표 변화 0(패리티). 새로 보이는 수치: `--scenarios <MT 파일> <MQ 파일>` 한 실행에서 멀티턴·멀티쿼리 성공률·
  답변 품질이 따로 나온다 — 지금은 실행을 둘로 나누거나 results.jsonl을 수작업 집계. 값은 측정 후 Result에 기록.
- 실질 반영 이점: 결과 검증·기술 설계. 핵심 지표 "멀티턴 성공률"이 리포트에 직접 나와 T3-07~10 비교표·발표에 그대로 쓴다.
  답변 품질 판정(근거 없는 숫자)이 한 파일이라 이후 Ragas 등 심판 지표(plans/T3-06 범위 밖)를 붙일 자리가 생긴다.
- 비용·리스크: 1일, LLM 비용 0. `grade_turn` 분해 시 오류 순서(`errors` 리스트 순서)가 바뀌면 results.jsonl 패리티가 깨짐 → 순서 고정.
  `summary`에 키가 하나 늘어남(`by_task`) — suite(`metrics`)·`report_html.agent_body`는 정해진 키만 읽고 `ops.append_history`는 summary를 안 써서 영향 없음(리뷰 4).
  `wrong_numbers`는 지금 `calc_qid`·`calc_qids`·`combine_value`에서 따로 붙어 한 턴에 중복될 수 있고 summary `errors`가 그대로 센다 → 중복 그대로 유지(리뷰 3b).
