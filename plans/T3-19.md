## 현재 구조에서 확인한 사실 (계획의 전제)
1. **Ragas 설치**: `pyproject.toml`에 `ragas` dependency group이 이미 있고 lock은 0.4.3. `ragas.llms.base`가
   `langchain_community.chat_models.vertexai`를 import하는데 langchain-community 0.4.2에 없다 → 그대로는 실패.
   `sys.modules`에 빈 `ChatVertexAI` 스텁 모듈을 넣으면 0.4.3 전체가 import되는 것을 확인 (2026-11-17, `uv run --with ragas`).
   langchain-community를 0.3으로 내리는 건 langchain-core>=1.7(LangGraph 1.2) 때문에 불가.
2. **Ragas 0.4.3 API**: `ragas.metrics.collections`의 `Faithfulness(llm)`, `AnswerRelevancy(llm, embeddings)`,
   `ContextPrecisionWithReference(llm)`, `ContextRecall(llm)` — 각각 `await m.ascore(...)` → `MetricResult.value`.
   LLM은 `ragas.llms.llm_factory(model, client=AsyncOpenAI())`(instructor 기반), 임베딩은 `ragas.embeddings.embedding_factory`.
   (Response Relevancy의 0.4 클래스 이름이 `AnswerRelevancy`다.)
3. **입력은 이미 저장돼 있다**: e2e `results.jsonl` 한 줄 = `question`(골든 문항) · `answer`(StatAnswer: `text`, `result.facts`
   = pandas가 계산한 값, `source`) · `top_keys`(검색 순위) · `gold_keys`(L1 정답 슬롯) · `used_table` · `trace_id`/`span_id` ·
   `trace_spans`(노드 span: context/search/statistics/chart/finalize + 툴 span) · `failure`(노드 단위 책임, `evals/trace.py`).
   → **그래프를 다시 돌리지 않고** Ragas 샘플을 만들 수 있다 (`--from-run`, 연구 문서 §6의 "다시 실행하지 않는다").
4. **표 텍스트**: 실전 2 `kosis_rag.shared.tabletext.build_doc(record, "n2-L60")["bm25_text"]`(표 전체 텍스트),
   `kosis_rag.adapters.files.read_records(data/tables.jsonl)`. 새 포맷을 만들지 않는다. `embed_text`는 단위·지역 꼬리를 지우고
   라벨을 요약해 reference 주장이 거짓으로 미확인될 수 있어 쓰지 않는다(리뷰).
5. **CI 제약**: `data/`·`evals/datasets/`·`evals/reports/<run>/`는 gitignore이고 `verify.sh`가 추적 금지를 검사한다.
   CI(GitHub Actions)에는 골든 문항·표·Chroma·API 키가 없다 → CI는 평가를 **실행**할 수 없고, 커밋된 **집계**만 볼 수 있다
   (기존 `ops_history.jsonl`이 같은 방식: 집계만 커밋).
6. 연구 문서 §6은 Response Relevancy를 "한국어 임베딩에 따라 흔들려 뺌"으로 정했다. 사용자가 이번에 명시 요청했으므로 넣되,
   **절대값 목표 없이 회귀(직전 대비 하락) 지표로만** 쓴다.

## Idea

### 지표 정의 — "이 시스템에서 컨텍스트란 무엇인가"
RAG의 검색 결과는 문단이 아니라 **통계표**이고, 답의 숫자는 LLM이 아니라 pandas가 계산한다. 그래서 지표마다 컨텍스트를 다르게 잡는다.

| 지표 | 계층 | user_input | response | retrieved_contexts | reference |
|---|---|---|---|---|---|
| Faithfulness | 생성 | 질문 | `answer.text` | 답이 근거로 쓴 것: 계산 결과 사실 줄(`f1: 2025 · 시도별=경기도 · … = 76,309 명`) + 사용한 표 텍스트 | — |
| Response Relevancy | 생성 | 질문 | `answer.text` | — | — |
| Context Precision | 검색 | 질문 | — | 검색 상위 k개 표 텍스트(순위대로) | 골든에서 코드로 만든 정답 근거 문장 |
| Context Recall | 검색 | 질문 | — | 검색 상위 k개 표 텍스트 | 같은 reference |

- **reference는 코드가 골든에서 만든다** (LLM이 정답을 쓰지 않는다): 정답 표(`gold_keys`)의 조사명·표명 + 필요한 사실의
  기간·분류·항목(`required_facts`의 period·dims·unit). 예: "인구동향조사의 「시도/성/…별 출생」 표가 필요하다. 2025년 시도별=경기도의
  출생아 수를 담고 있어야 한다." → 표 텍스트(숫자 없음)로 판정 가능한 주장만 담는다. 단위는 넣지 않는다(표 텍스트에 없을 수 있음).
- **답이 없는 행은 Ragas에 넣지 않는다**: outcome이 refused/clarify인 행은 Faithfulness·Relevancy 대상 아님(거절은 결정적 채점이 맡음).
  `kind=not_answerable` 문항은 Context 지표 대상 아님(정답 표가 없음). 대상 수를 리포트에 그대로 적는다.
- **결정적 교차 확인**: 같은 행에서 코드로 ID 기반 Precision@k(정답 표가 있는 순위의 평균 정밀도)·Recall@k(정답 슬롯 중 상위 k에
  든 비율)를 같이 계산한다. LLM Context Precision/Recall이 ID 기반 값과 크게 다르면(문항 단위 일치율 리포트) 심판을 의심한다.
  — 연구 문서 원칙 "코드로 채점할 수 있으면 심판에 맡기지 않는다"를 지키면서 사용자가 요청한 Ragas 지표를 근거와 함께 쓴다.
- **심판 모델 ≠ 파이프라인 모델**: 답은 HCX(실전 1), 해석기·멀티쿼리는 gpt-4o-mini. 심판은 둘 다 아닌 `RAGAS_JUDGE_MODEL`(기본 `gpt-4.1-mini`), 임베딩
  `RAGAS_EMBED_MODEL`(기본 `text-embedding-3-small`). 디스크 캐시(`data/cache/ragas`, gitignored)로 같은 입력 재채점은 호출 0.

### 파이프라인 (세 단계를 하나의 흐름으로)
```
골든셋(calculation_golden + retrieval_golden)  ──>  e2e 실행 (기존, HCX·검색·trace)  ──>  results.jsonl
                                                                                            │
                     ┌──────────────────────────────────────────────────────────────────────┘
                     ▼
  ① --layer ragas --from-run <e2e run>   : 행 → Ragas 샘플(코드) → 4개 지표(심판) + ID 기반 P/R(코드)
  ② 노드 연결                             : 행의 trace_id·노드 span·failure.span → 지표별 담당 노드, eval.ragas span(Jaeger link)
  ③ quality_history.jsonl (집계만 커밋)    : stage·골든 hash·심판 모델·지표 평균·결정적 PASS율
                     ▼
  pytest tests/test_quality_gate.py (CI)  : 같은 비교 키의 직전 기록 대비 하락 > 허용폭이면 FAIL
```

## Option A — 사후 점수기 + 고정 임계값
- 접근: `evals/ragas_score.py` 스크립트 하나가 e2e run 폴더를 읽어 4개 지표를 계산해 `ragas.json`으로 저장. 노드 연결은
  trace_id 컬럼만 붙임. CI는 pytest가 커밋된 `ragas_latest.json`의 평균이 고정 임계값(예: Faithfulness ≥ 0.9) 이상인지만 본다.
- 예상 성능 향상: Ragas 지표 0 → 4개 측정. CI 게이트 0 → 4개 지표(고정선). 회귀 감지력: 고정선 위에서의 하락은 못 잡음
  (예: 0.97 → 0.91 하락도 통과).
- 실질 반영 이점: 결과 검증 항목에 숫자가 생김. 다만 하네스(`run_eval`, report.html, ops_history) 밖이라 suite·리포트에 안 나오고,
  노드별 원인은 사람이 trace를 직접 찾아야 함.
- 비용·리스크: 0.5일. 심판 비용 1회 ≈ $0.3(90문항). 임계값을 근거 없이 정하게 됨(베이스라인 전), 하네스 이원화.

## Option B — 하네스 계층 `ragas` + 노드 귀속 + 직전 대비 회귀 게이트 (오프라인 CI)
- 접근:
  1. `evals/tasks/ragas.py`를 `run_eval`의 새 계층으로 등록 (`--layer ragas --from-run <e2e run>`): 기존 task 규약
     `run(args) -> (rows, summary, report)` 그대로 → results.jsonl·manifest·report.md·report.html·history가 자동으로 생김.
     샘플 생성(`evals/evaluators/ragas_metrics.py`: 사실 줄·표 텍스트·reference — 순수 함수)과 심판 호출(같은 파일, 비동기 병렬,
     동시성 제한)을 분리해 앞쪽은 오프라인 pytest로 고정.
  2. 노드 귀속: 지표 → 노드 규칙(Context Precision/Recall → `search` 노드, 그 안은 `failure.span`/`lost_at`이 가리킨 검색 노드;
     Faithfulness → `statistics` 노드의 실전 1 `compose` span; Relevancy → `context`(질의 해석)·`statistics`). 리포트에
     "지표 × 노드" 표(노드별 저점 문항 수·평균·해당 노드 지연 p50). `OTEL_EXPORTER_OTLP_ENDPOINT`가 있으면 `link_questions`와
     같은 방식으로 `eval.ragas` span을 원래 턴 trace에 link하고 `kosis.ragas.<metric>` 속성·저점 노드를 단다 → Jaeger에서
     문항 trace ↔ 점수 양방향 이동.
  3. **기준선 대비 게이트 (리뷰 반영: 직전 기록 대비 → 커밋된 기준선 대비)**
     - `evals/reports/quality_history.jsonl`(집계만, 커밋): ragas 계층 실행마다 한 줄 — 비교 키 + 지표.
       비교 키 = 골든 hash · split · tables.jsonl hash · e2e target(에이전트 그래프·모델) · 심판·임베딩 모델 · ragas 버전 · 컨텍스트 포맷 · k.
     - `evals/quality_baseline.json`(커밋): 키 + 지표별 기준값·허용폭. 사람이 `python -m evals.quality --promote <run>`으로만 갱신
       (PR diff에 기준선 변경이 보임). → 허용폭 안 하락이 쌓이는 래칫, 일부러 나쁜 실험(T3-07~10, target이 달라 키가 다름)의 오염,
       jsonl 줄 순서 문제가 없다. 최신 = 키가 같은 줄 중 run_id(시각 접두) 최대.
     - 게이트 지표: Ragas 4개 + ID P/R@k + 결정적 PASS율 + 정답 표율 + **답한 문항 수**(거절이 늘면 Faithfulness 평균이 오히려
       오르는 생존 편향 차단).
  4. `tests/test_quality_gate.py`(오프라인, verify.sh → CI): 최신 기록 vs 기준선을 지표별 parametrize → CI 로그에 "지표 몇 → 몇".
     키가 같은 기록이 없으면 skip(사유 출력). 게이트 로직은 합성 기록으로 단위 테스트.
     CI: PR에서 파이프라인 경로가 바뀌었는데 `quality_history.jsonl`이 안 바뀌면 `::warning::`(base fetch 필요 → `fetch-depth: 0`).
     한계(리뷰 d): 기록을 안 올린 PR은 경고만 — 평가 실행에 데이터·키가 필요해 CI가 대신 돌릴 수 없다(옵션 C 사유).
  5. 허용폭: Ragas 지표 = 같은 입력 캐시 없이 2회 채점한 심판 흔들림 → `max(2×흔들림, 0.03)`. 결정적 비율 지표 = 2문항(2/n).
     한계(리뷰 c): HCX 재실행 분산은 재지 않음(e2e 재실행 비용) → Result에 명시, 거짓 FAIL이 나면 기준선 갱신과 함께 넓힌다.
  6. 저하 감지 검증(리뷰: 평균만 낮춘 합성 기록은 동어반복) → 저하시킨 **행**을 심판이 실제로 다시 채점: ① 검색 순위 뒤집기
     ② 답 문장의 숫자 훼손 ③ 답을 다른 문항 답으로 바꾸기. 각각 해당 지표가 떨어지고 게이트가 FAIL하는지 본다(history에 남기지 않음).
- 예상 성능 향상:
  - Ragas 지표 0 → 4개 + ID 교차 확인 2개 (e2e 90문항, 대상 수는 실측).
  - CI 품질 게이트 0 → 9개 지표(Ragas 4 + ID P/R + PASS율·정답 표율·답한 수), **커밋된 기준선 대비**.
  - 회귀 감지: 실제로 재채점한 저하 3종에서 게이트 FAIL 0/3 → 3/3 목표.
  - 노드 귀속: 저점 문항 중 담당 노드가 정해진 비율 0 → ~100% (trace_spans가 있는 행).
  - 지표 절대값은 추정하지 않는다(실측 없음). 방향만: 숫자는 pandas가 계산하므로 Faithfulness는 높아야 하고, LLM Context Recall은
    reference가 정답 표 메타데이터라 구조상 ID Recall@k와 가까워야 한다(멀면 심판 또는 표 텍스트 문제).
- 실질 반영 이점: 결과 검증·기술 설계 — 기존 하네스 규약(task 모듈·report.html·suite·history)에 들어가 T3-07~10 아키텍처 비교에서
  같은 명령으로 재사용. Ragas 점수가 trace의 어느 노드 문제인지까지 연결되어 "무엇을 바꿔서 몇 → 몇"의 원인 추적이 됨.
  CI가 품질 저하 PR을 막는 근거(포트폴리오 P2 평가 엔지니어링).
- 비용·리스크: 1.5~2일. 심판 1회 ≈ $0.3~1(문항당 LLM 약 8~10회: CP는 컨텍스트 k개마다 1회). 리스크: (a) CI는 커밋된 기록만 보므로
  PR 작성자가 로컬에서 평가를 돌려 기록을 커밋해야 함(안 돌리면 경고만) (b) 한국어 Response Relevancy 흔들림 → 허용폭 실측으로 대응
  (c) Ragas 스텁 우회는 버전업 시 깨질 수 있음 → import 실패를 명확한 오류로, ragas 버전 고정.

## Option C — CI에서 직접 평가 실행 (온라인 게이트)
- 접근: B의 계층에 더해 GitHub Actions에 `eval` 잡(PR 라벨·야간 schedule). 비밀값(OPENAI/HCX 키)과 골든셋·tables.jsonl·Chroma
  스냅샷을 암호화 아티팩트나 self-hosted runner로 제공, 매 PR마다 e2e 소표본(예: 30문항) 실행 → Ragas → main 기준선과 비교,
  결과를 PR 코멘트로 남김. 문항 하나하나를 `pytest` 테스트로 parametrize(`deepeval` 스타일).
- 예상 성능 향상: B와 같은 지표 + "기록을 안 올린 PR"도 실제로 측정(stale 0). 소표본이라 지표 분산 커짐(30문항이면 ±0.05 수준).
