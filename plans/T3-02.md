## Option A — 패턴 표 (실전 1이 고른 종류를 표 하나로 덮어쓰기 + 요청 가드)
- 접근: `services/chart.py`에 `(pattern, 실전 1 kind) → kind` 표 하나와, 패턴별로 허용하는 요청 종류 표를 둔다.
  - 자동: `extreme`·`avg`·`sum`의 `timeline`(기간 막대) → `line`, `shr`(구성비 변화) → `stacked_bar`. 나머지는 그대로.
  - 요청: 원형은 `share` 패턴만, 꺾은선은 시간 축이 있는 패턴(trend, avg/sum, 기간 extreme, compare·gap·grid의

  - `stacked_bar`는 `register_kind`로 그리는 법을 등록한다. 이 등록은 실전 1의 전역 `DRAW`를 import 시점에 바꾼다
    (같은 프로세스의 실전 1 호출에도 보인다. 실전 1은 이 종류를 만들지 않으므로 영향 없음).
  - 종류를 바꾼 뒤에는 `vega_lite=None`으로 비워 다시 그린다(그렇지 않으면 `to_vega`가 예전 spec을 돌려준다).
- 예상 성능 향상: 설계용 12/15 → 15/15 · 4/10 → 10/10 · 오해 6 → 0 (정의상). 검증용 자동 2/5 → ~5/5, 요청 2/4 → ~4/4

## Option B — 데이터 모양 판정기 (사실을 읽어 종류를 고름)
- 접근: `summarize_stat` 결과의 사실(`StatAnswer.facts`)과 `ChartSpec.fact_ids`로 차트의 모양을 계산한다: 서로 다른 시점
  수, 서로 다른 대상(분류·지역) 수, 부분과 전체 관계(비중 사실과 그 분모). 이 모양에서 종류를 고른다
  (시점 ≥3·대상 1 → 꺾은선, 대상 ≥2·시점 1 → 막대, 부분 + 전체 1시점 → 원형, 여러 시점 → 누적막대, 대상 × 시점 → 지금의 격자).
  요청 가드도 같은 모양으로 판정한다. 패턴 이름은 보지 않는다.
- 예상 성능 향상: 설계용·검증용 모두 A와 같은 값을 목표로 한다. A와 다른 점은 표에 없는 패턴(실전 1 `plan` 경로,
  T3-28 합친 차트)에도 규칙이 적용된다는 것. 단 그 경우를 잴 세트가 지금 없어 수치로 말할 수 없다.
- 실질 반영 이점: 규칙이 패턴 목록에 묶이지 않는다. 기술 설계 점수에 유리하다.

  T3-27 하네스 채점 인자(`ARG_FIELDS`)와 그래프 노드 수정. 시점·대상 수를 사실에서 다시 세는 코드가 실전 1 빌더 로직과
  겹쳐, 둘이 어긋나면 차트 점과 판정이 다른 것을 볼 수 있다.

## Option C — LLM이 허용된 종류 중 고르기 (코드 가드 + LLM 선택)
- 접근: A의 요청 가드 표로 "이 데이터에 그릴 수 있는 종류"를 코드가 먼저 정한다. 그 안에서 질문 문장을 보고 어떤 종류가
  나은지 LLM(HCX) 한 번으로 고른다(예: 기간 평균 질문은 막대가 나은가 꺾은선이 나은가). 출력은 허용 목록 중 하나로
  고정(Pydantic), 벗어나면 실전 1 종류.
- 예상 성능 향상: 오해 차트는 A와 같이 0(가드가 코드). 자동 선택 일치는 LLM에 따라 흔들린다(규칙 문구와 다른 선택을
  할 수 있음) → 측정 세트로는 A보다 낮거나 같을 것으로 본다.
- 실질 반영 이점: 규칙 문구가 정하지 않는 애매한 경우(한 값, 기간 평균)에 질문 의도를 반영할 수 있다.
- 비용·리스크: 1.5일 + 차트가 있는 답마다 HCX 1회(지연 ~1초, 비용). 결정적이지 않아 T3-07 베이스라인 측정이 흔들린다.
  숫자는 건드리지 않지만 "LLM은 문장만"이라는 설계 원칙의 범위를 넓힌다.
