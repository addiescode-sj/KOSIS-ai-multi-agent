# T3-68 사용자 피드백 신호 지표 빈 곳 채우기 (답변 복사율·재시도율·로그 품질)

## Idea
수집 경로는 이미 있다. 빈 곳은 "쌓이는데 세지 않는" 지표다. `log_metrics.METRICS`에 SQL을 더하고 탭에 붙인 뒤,
프론트 `lib/admin/schemas.ts`(zod) → `view.ts`(매핑) → `dashboard-body.tsx`(카드)로 잇는다. 운영자 앱 JSON API는 탭 단위로
`log_metrics.tab()`을 내보내므로 백엔드 API는 손대지 않아도 따라온다(확인 필요).

## 세 옵션 공통 (재시도율 외)
- **답변 복사율** = 복사 이벤트가 있는 답 수 ÷ `outcome='answered'` 질문 수, 둘 다 `count(DISTINCT request_id)`.
  분모가 출처 클릭률(`has_numbers`)과 다른 이유: 복사는 숫자 없는 답(문장 답·차트)도 대상이다. 한 답의 여러 번 복사는 1건.
  `daily_usage.copy_answers`는 전체 사용자 하루 합계라 회원/비회원·기간 필터를 못 받으므로 `log_metrics`에 SQL을 둔다(원천은 같은 `ui_events`).
- **로그 품질** = `ingest_rejects` 사유별 탈락 건수(비율 아님: 받은 이벤트 총수를 따로 저장하지 않음). 이 테이블에는 회원·내부 열이 없어
  사용자 필터가 먹지 않는다 → 화면에 "필터 무관 · 화면 이벤트 탈락만" 표시. 서버 쓰기 실패 수는 프로세스 메모리에만 있어 이 카드에 없다.
- 재시도율은 두 값으로 나눈다: **오류 후 다시 시도**(원래 턴 outcome이 error/failed/aborted) / **정상 답 다시 받기**(그 외).
  `chat.tsx` retry()는 실패가 없을 때도 마지막 답의 request_id를 `retry_of`로 보내기 때문이다(리뷰 3).

## Option A — 이미 쌓인 행에서 추정 (마이그레이션 없음)
- 접근: 같은 `(conversation_id, turn_index)` 행이 둘 이상이면 뒤 행을 재시도로 본다(`ix_request_logs_conversation_turn`이 unique가 아닌 이유).
  앞 행 outcome으로 오류 후/정상 후를 나눈다.
- 예상 향상: 재시도율 카드 0 → 2, 복사율 0 → 1, 로그 품질 "데이터 없음" → 값. 실제 지표 카드 15/18 → 16/18.
- 이점: 코드 SQL만, 지난 로그에도 소급 적용.
- 비용·리스크: 반나절. **정확도 리스크 큼**: 실패한 턴이 checkpoint를 남겼는지에 따라 재시도의 turn_index가 +1이 될 수 있고(`_turn_index`는 checkpoint의 질문 수),
  같은 turn_index 중복이 다른 원인(동시 요청)으로도 생긴다. 맞는지 PostgreSQL 테스트로 보장하기 어렵다.

## Option B — 서버가 이미 아는 `retry_of`를 request_logs에 적재 (마이그레이션 1개)
- 접근: `request_logs.retry_of`(String(32), nullable) 열을 마이그레이션 `0009`로 추가, `row_from_turn`이 루트 span 속성 `kosis.turn.retry_of`를 옮긴다.
  `retry_rate` SQL은 `retry_of`로 원래 행을 LEFT JOIN해 outcome으로 둘로 나눈다(원래 행이 없으면 "원래 턴 미상").
- 예상 향상: A와 같은 카드 수, 재시도 값은 화면이 실제로 보낸 표시라 오차 0(테스트로 손으로 센 값 = SQL).
- 이점: 예외 처리 평가 근거(오류 후 다시 시도 비율)를 질문 단위로 추적. 계획 문장("재시도율을 자동 기록")과 실제가 일치.
- 비용·리스크: 1일. nullable 열 추가라 기존 행·쓰기 경로 영향 없음. `test_migration_matches_models`가 모델·마이그레이션 일치를 검사. 이전 로그는 소급 안 됨.

## Option C — 화면 이벤트로 수집 (`retry_click` 이벤트 추가)
- 접근: "다시 시도" 버튼에서 `retry_click`(props: `after_failure: bool`)을 `/events`로 보내고 `ui_events`로 센다.
  `UI_EVENT_TYPES` CHECK 제약 변경 마이그레이션 + 프론트 zod·백엔드 `EVENT_PROPS` 3곳 수정.
- 예상 향상: 카드 수는 A·B와 같음. 버튼 클릭 기준이라 서버에 닿지 못한 재시도(네트워크 실패)도 센다.
- 이점: 화면 행동 로그로 일관.
- 비용·리스크: 1일. 서버가 이미 아는 값을 화면이 다시 보내는 이중 집계(`abort_rate`를 화면 `stream_abort`에서 서버 `aborted`로 바꾼 것과 반대 방향).
  광고 차단·탭 닫기로 이벤트가 빠지면 과소 집계.

## Recommendation
**옵션 B.** 재시도 값을 서버가 받은 그대로 저장해 정확도 리스크가 없고(A), 이중 집계도 없다(C). 비용(단가표)은 단가 정의가 정해진 뒤 별도 태스크.
