# T3-50 재작성된 질문 로그

## Goal
- 완료 기준 (TASK.md 그대로): 사용자 질문 원문과 함께, 에이전트가 다시 쓴 질문(이월 독립 질문 `resolved_question`, 멀티쿼리 하위 질문)과 해석 방식을 `request_logs`에 남긴다. 원문과 같은 가림·내부 트래픽 무저장·90일 삭제 규칙. 완료 기준: 재작성 턴에서 재작성 문장이 가린 값으로 저장, 새 질문 턴은 비움, 90일 삭제 대상 포함, PostgreSQL pytest
- 요청 (11/23, 임도유): "사용자 질문 말고도 재작성된 쿼리를 로그로 남겨줘"
- 브랜치: T3-49(PR #37, 머지 전) 위에서 시작한다. 90일 삭제 함수(`log_metrics.py`)를 T3-49가 옮겨 놓았기 때문이다. PR은 T3-49 머지 뒤 main 기준으로 맞춘다.
- Baseline (`456ad57`): 재작성 문장이 남는 곳 = Jaeger trace 루트 속성 `kosis.turn.resolved_question`뿐(보관 규칙 없음, SQL 조회 불가). `request_logs`에는 원문 `question`만. 재작성 턴인지 알 칸 없음 → "재작성 턴의 👎·거절 비율" 조회 0개

## Idea
재작성 문장은 그래프가 이미 만들어 `ChatResult`에 담는다. 로그 행을 만드는 `row_from_turn`이 그 결과를 받으므로 그래프·에이전트 코드는 건드리지 않는다.

판정은 아래 순서로, 처음 맞는 것 하나 (리뷰 반영: 턴이 끝난 뒤의 `ChatResult` 값으로 판정한다).

| 순서 | 턴 종류 | 판정 (`ChatResult`) | 남기는 문장 |
|---|---|---|---|
| 1 | 차트만 ("막대로") | `answer_origin == "chart"` | 없음. `resolved_question`이 직전 질문 복사본이라 넣지 않는다 |
| 2 | 멀티쿼리 ("서울이랑 부산 비교") | `sub_results`가 None 아님 | `sub_questions` = `sub_results[].question`. `resolved_question`은 마지막 하위 질문으로 덮어써져 있어 넣지 않는다 |
| 3 | 이월·정정 ("부산은?", "아니 2023년으로") | `resolved_question`이 있고 원문과 다름 | `rewritten_question`. 직전 표가 못 답해 다시 검색한 턴은 `reused_table`이 거짓으로 바뀌므로 `reused_table`은 보지 않는다 |
| 4 | 지시어 ("그 표에서 …") | `reused_table` 참 | 없음 (원문 그대로) |
| 5 | 새 질문 | 그 밖 | 없음 |
| - | 결과 없이 예외로 끝난 턴 | `result`가 None | 네 칸 모두 NULL |

- 가림: `ChatResult`의 문장은 가리지 않은 원문이고, LLM이 다시 쓴 문장에는 직전 질문 원문이 섞인다. 그래서 `row_from_turn`이 저장 직전에 `mask()`를 부른다(원문 `question`은 지금처럼 핸들러가 가린 값을 넘김).
- 한계: 하위 질문이 모두 같은 표를 찾아 한 턴 경로로 합쳐진 멀티쿼리(`main_graph.py` 210행)는 `sub_results`가 None이라 "새 질문"으로 남는다. 알려면 그래프가 `sub_questions`를 `ChatResult`에 내보내야 하는데 에이전트 코드라 담당 밖이다.

해석 종류(`rewrite_kind`: new · carry_over · reference · chart_only · multi)와 해석 주체(`interpreted_by`: rule · llm · none)는 원문이 아니라 정해진 값이라 90일 뒤에도 남긴다. 문장은 원문과 같은 규칙(저장 전 가림, 내부 트래픽은 저장 안 함, 90일 뒤 NULL)을 따른다.

## Option A — `request_logs`에 칸 추가 (같은 행)
- 접근: 마이그레이션 0004로 `request_logs`에 4칸.
  - `rewritten_question` (text): 원문과 다를 때만 가린 값, 같으면 NULL
  - `sub_questions` (JSON 배열): 멀티쿼리 하위 질문, 가린 값
  - `rewrite_kind`, `interpreted_by` (CHECK로 값 고정)
  - CHECK: 내부 트래픽은 두 문장 칸이 비어야 함(원문 칸과 같은 규칙). 90일 삭제 SQL이 세 칸을 함께 비움(`WHERE question IS NOT NULL OR rewritten_question IS NOT NULL OR sub_questions IS NOT NULL`).
  - "자유 텍스트는 `question`과 피드백 이유에만" 불변식을 적은 곳(`log_models.py` 머리말, `masking.py`, `docs/log-schema.md`)을 "질문 원문·재작성 문장·피드백 이유"로 고친다.
  - 마이그레이션 0004 (`down_revision = "0003_pgvector"`, main 기준 최신).
  - T3-49 조회에 지표 1개: 재작성 종류별 질문 수·결과 비율·👍 비율(같은 공통 필터).
- 예상 성능 향상: 재작성 문장을 SQL로 조회할 수 있는 턴 0% → 재작성 턴 100%(멀티쿼리 같은 표 합침 제외). 재작성 종류별 결과·👍 비율 조회 0개 → 1개. 근거: 판정이 `ChatResult` 값만으로 결정적이라 지어낸 턴 5종에서 손 계산과 대조 가능
- 실질 반영 이점: 데이터 정확성(멀티턴 오답이 재작성 탓인지 원문에서 확인) · 예외 처리(LLM 해석 턴의 실패율). 👎 답 목록(T3-49)에 "다시 쓴 질문" 칸을 한 줄로 추가. 기존 행·스키마와 호환(새 칸은 NULL 허용)
- 비용·리스크: 반나절. 멀티쿼리 하위 질문이 JSON 배열이라 개별 하위 질문 단위 집계는 `jsonb_array_elements`가 필요. T3-49 머지 순서 의존

## Option B — 별도 테이블 `request_rewrites` (질문 1 : 재작성 N)
- 접근: `request_rewrites(request_id FK, seq, kind, text, interpreted_by)` — 이월 문장 1행, 멀티쿼리면 하위 질문마다 1행. `request_logs`에는 `rewrite_kind`만. 삭제 배치에 이 테이블 추가.
- 예상 성능 향상: A와 같은 지표 + 하위 질문 단위 조회(하위 질문별 표·결과까지 넣으면 멀티쿼리 부분 실패 분석 가능)
- 실질 반영 이점: 멀티쿼리 하위 질문별 결과를 행으로 다룰 수 있음(정규화)
- 비용·리스크: 하루. 테이블·FK·쓰기 경로(한 턴에 두 테이블 쓰기, 한 트랜잭션)·삭제 배치·조회 조인이 모두 늘어남. 실제 서비스의 멀티쿼리 비중은 아직 모른다(로그가 없음). A로 먼저 쌓아 비중을 보고 필요하면 옮기는 편이 싸다

## Option C — DB 대신 trace에만 두고 보관 규칙만 추가
- 접근: 재작성 문장은 이미 Jaeger 루트 속성에 있다. DB는 바꾸지 않고 `request_logs`에 `rewrite_kind`만 추가, 문장은 `request_id`로 Jaeger에서 본다. Jaeger 보관 기간을 90일 이하로 맞추는 설정과 가림 처리(span 속성에 가린 값)를 넣는다.
- 예상 성능 향상: 종류별 지표 1개는 A와 같음. 문장 SQL 조회는 불가(Jaeger UI에서 한 건씩)
- 실질 반영 이점: 스키마 변경 최소, 문장 칸이 DB에 늘지 않음
- 비용·리스크: 내 몫은 반나절이지만 trace 쪽 가림은 에이전트 코드(`_record_turn`, 담당 밖), Jaeger 보관 설정은 인프라(김병석) 담당이라 다른 사람 작업이 필요하다. 요청("로그로 남겨줘")과 달리 메트릭 화면·SQL에서 문장을 못 봄

## Recommendation
옵션 A. 요청이 "로그로 남겨줘"이고, 원문 `question`과 같은 행·같은 규칙에 두는 것이 가장 단순하다. 하위 질문은 한 턴에 2~3개라 JSON 배열로 충분하다. 내 담당(로그 스키마·수집) 안에서 끝나고 에이전트·인프라 코드를 건드리지 않는다.
