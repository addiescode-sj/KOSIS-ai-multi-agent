# T3-48 사용자 로그 수집 파이프라인 (Linear KOS-170)

## Goal
- 완료 기준 (TASK.md 그대로): `docs/log-schema.md`(로그 버전 3) 기준으로 서비스 턴마다 `request_logs` 1행을 쓰고(원문 가림, 하네스 표시, 이탈·첫 글자 시각), 화면 이벤트 수신·검사(`ui_events`, `ingest_rejects`)를 만든다. 로그 쓰기 실패가 답을 막지 않는다. 완료 기준: 서비스 턴 → 저장 행 경로 테스트, 가림 함수 pytest, 쓰기 실패 시 답 정상, 질문 1건 = 행 1건(중복·누락 0) 전→후
- Linear KOS-170 본문은 이 세션에서 읽지 못했다(Linear 미연결). 범위는 `docs/log-schema.md` 5장(백엔드 요구 6번)·10.5(수집 3번)·12장, 기능명세서 FEAT-035~038에서 가져왔다. 본문과 다르면 고친다.
- Baseline (main `3aecb50`)
  - 서비스 턴 → 저장된 로그 행: **0** (`backend/app/main.py`는 DB를 쓰지 않는다. `DATABASE_URL`은 compose에 있지만 읽는 코드 없음)
  - 서비스 trace → 행 변환: `row_from_turn` 있음(T3-36), 부르는 곳 없음
  - 원문 가림 함수: 없음. `ui_events`·`ingest_rejects` 테이블: 정의(문서 4장)만, 모델 없음
  - 세션 ID·하네스 표시·입력 방식: 화면이 보내지 않는다(`frontend/app/api/chat/route.ts`는 `question`, `thread_id`만)
  - 마이그레이션: `0001`만. `request_logs`는 `LogBase` 초안. PR #34(pgvector)가 `0002_pgvector`, KOS-158이 `feedback`·`users`로 `0002`를 쓰려 한다

## Idea
1. **원문 가림 함수** (`kosis_store.masking`): 전화번호·이메일(+주민등록번호·카드번호 형태) 패턴을 `[전화]` 식으로 바꾼다. 규칙은 한 곳, 표본 pytest.
2. **턴 → 행**: 턴이 끝날 때 `row_from_turn`으로 한 행을 만든다. 원문은 span에서 읽지 않고(T3-43이 루트에 넣는 원문은 가리지 않은 값) 핸들러가 가림 함수를 거친 값을 넘긴다.
3. **쓰기**: 요청 스레드 밖에서 쓴다. DB 오류·지연이 답을 막지 않고, 실패는 버리고 건수만 센다(`/health`나 메트릭에서 보임).
4. **이탈·첫 글자**
   - 이탈: `/chat/stream` generator에 `except GeneratorExit`를 따로 두어 aborted로 표시하고, `finally`에서 `root.end()` 뒤에 행을 넘긴다. Starlette는 끊긴 스트림의 sync generator를 바로 닫지 않을 수 있어(다음 `next()` 또는 GC 때 닫힘) 이탈 행이 늦게 쓰일 수 있다. 테스트에서 generator를 직접 `close()`해 경로를 확인하고, 늦게 쓰이는 정도는 문서에 한계로 적는다.
   - 첫 글자: 지금 `token` 이벤트는 답이 다 만들어진 뒤 한꺼번에 나가서, 서버가 재는 첫 글자 시각이 `latency_ms`와 거의 같다. 서버가 첫 `token`을 보낸 시각을 그대로 기록하되 "현재 스트리밍 구조에서는 지연과 거의 같다"를 문서에 적는다(진짜 토큰 스트리밍이 들어오면 의미가 생김). 문서 12.2의 "화면이 재서 넘김"은 "서버가 첫 `token` 이벤트를 보낸 시각"으로 고친다.
5. **세션·하네스·입력 방식**: 요청 본문에 선택 필드 `session_id`(UUID), `input_method`(`direct`·`clarify_option`), 헤더 `X-Kosis-Internal: 1`. `ChatRequest`에 선택 필드 추가는 기존 호출과 호환된다. 하네스 표시는 루트 span에도 `kosis.internal=true`로 붙인다(문서 10.3 Prometheus 필터). 화면 프록시(`route.ts`)는 브라우저 헤더를 넘기지 않으므로 사용자가 이 표시를 달 수 없다. 지금 HTTP로 서비스를 부르는 하네스는 없어(평가는 그래프를 직접 부름) 표시를 다는 쪽은 앞으로의 HTTP 하네스다.
6. **화면 이벤트**: `POST /events` — Pydantic으로 검사, 통과하면 `ui_events`(같은 `event_id`는 무시), 떨어지면 `ingest_rejects`에 사유·건수만(원문 없음). 시각 5분 넘게 어긋나면 서버 시각으로 바꾸고 표시. `props`는 이벤트 종류별 허용 키·타입만 받는다(자유 글자 없음, 크기 상한).
7. **테이블 만들기**: `request_logs`·`ui_events`·`ingest_rejects` 마이그레이션. 번호는 PR #34·KOS-158과 겹치므로 아래 "공통"의 방식으로 둔다.

## 공통 (세 옵션 모두)
- 마이그레이션 `log_tables`를 `0001` 다음 리비전으로 만들되 파일 머리에 "PR #34·KOS-158과 머지 순서에 맞춰 `down_revision`을 고친다"를 적는다. Alembic은 리비전 ID로 잇기 때문에 머지 때 한 줄만 바꾸면 된다. 마이그레이션-모델 차이 검사(`test_migration_matches_models`)에 로그 모델을 넣는다.
- 가림 함수, `POST /events`, 요청 필드 추가, 테스트는 같다.
- 숫자는 코드가 센다. LLM 관여 없음. 골든 문항은 시드·테스트에 쓰지 않는다(지어낸 질문만).
- 측정: FastAPI `TestClient` + 가짜 그래프(답함·거절·되묻기·오류·이탈 턴을 만드는 작은 LangGraph) + SQLite/PostgreSQL로 N턴을 돌려 **저장 행 수 ÷ 턴 수**, 중복 키 0, DB를 끊었을 때 답 200·스트림 정상, 가림 표본 탐지율.

세 옵션은 **누가 턴의 끝을 판단하고, 행을 어디에 쓰는지**가 다르다. 세 옵션 모두 같은 원천(서비스 span → `row_from_turn`)을 써서 LLM 호출·토큰·실패 단계가 채워진다(처음 B안 "ChatResult만으로 쓰기"는 리뷰 지적대로 일부러 약하게 만든 비교라 뺐다).

## Option A — 핸들러가 끝을 알리고, 단일 쓰기 스레드가 DB에 쓰기
- 접근: span processor는 끝난 span을 trace id별로 **담기만** 한다. 판단은 핸들러에 둔다: `/chat`·`/chat/stream`의 `finally`에서 `root.end()` 뒤에 `collector.finish(trace_id, result, aborted=…, question=가린 값, session_id, is_internal, input_method, first_token_ms)`를 한 번 부르면, 담아 둔 span을 꺼내 `row_from_turn` → `ThreadPoolExecutor(max_workers=1).submit(insert)`. lifespan 종료 때 `shutdown(wait=True)`로 남은 쓰기를 끝낸다. 실패는 버리고 카운터. trace id가 0(추적 꺼짐)이면 쓰지 않고 따로 센다.
- 예상 성능 향상: 가짜 그래프 테스트에서 턴당 저장 행 0 → 1.0 목표(답함·거절·되묻기·오류·이탈, 이탈은 generator `close()` 기준), 중복 0, DB 끊김 시 답 200 유지. 실측으로 확인한다(추정 근거: 행을 만드는 경로가 `finally` 하나).
- 실질 반영 이점: 순서 경쟁(`note` 뒤 `on_end`)과 루트 없는 trace 정리가 필요 없다. `/tools/*`는 `finish`를 부르지 않아 자연히 빠진다. 테스트가 `get_tracer`를 메모리 provider로 바꿔 끼워도 collector를 그 provider에 붙이면 같은 경로.
- 비용·리스크: 1~1.5일. 로그 적재가 추적에 묶인다(추적이 꺼지면 0행, 대신 "추적 꺼짐" 건수로 보임). 백엔드 파일(`main.py`, `telemetry.py`) 수정 → 김병석 님 리뷰.

## Option B — span processor가 혼자 판단 (핸들러는 메모만)
- 접근: processor가 `invoke_agent` 루트의 `on_end`에서 스스로 행을 만들고 큐 → 쓰기 스레드. 핸들러는 끝나기 전에 `note(trace_id, …)`로 가린 질문·세션·이탈만 남긴다. 루트가 오지 않는 trace는 시간 제한으로 버린다.
- 예상 성능 향상: A와 같은 목표. 단 핸들러가 `note`를 `root.end()`보다 늦게 부르면 그 값 없이 행이 써진다(순서 의존).
- 실질 반영 이점: 핸들러 수정이 가장 적다(호출 한 줄). 앞으로 새 엔드포인트가 `invoke_agent` 루트만 만들면 자동 적재.
- 비용·리스크: 1.5일. 순서·시간 제한·버퍼 정리 코드가 늘고, 버퍼가 루트 없는 trace의 툴 인자 원문을 시간 제한까지 든다.

## Option C — A + 파일에 먼저 쓰고 배치로 DB 적재
- 접근: A와 같지만 쓰기 스레드가 DB 대신 **로컬 JSONL**(`logs/requests-YYYYMMDD.jsonl`, 가린 원문·허용 키만)에 append. 적재 배치(`python -m kosis_store.load_logs --date`)가 `ON CONFLICT DO NOTHING`으로 넣는다(멱등).
- 예상 성능 향상: 턴당 기록 1.0 목표, DB 장애 중 유실 0(파일에 남음). DB 반영은 배치 주기만큼 늦음.
- 실질 반영 이점: 요청 경로에서 DB를 떼어 낸다. 정제 배치(KOS-167)와 같은 하루 1회 흐름.
- 비용·리스크: 2일. **원문이 DB 밖 파일에도 남아** 90일 삭제를 파일에도 따로 보장해야 한다. 볼륨·파일 회전 관리(인프라). 운영자가 당일 로그를 바로 못 본다.

## Recommendation
**A.** 같은 원천으로 LLM·실패 단계까지 채우면서, 턴의 끝을 아는 핸들러가 한 번만 넘기니 순서 경쟁·버퍼 정리가 없다. B는 순서 의존 코드가 늘고, C는 원문 사본이 하나 더 생긴다.

## 범위 밖 (넘기는 것)

- 루트 span의 원문 속성(`kosis.turn.question` 등, T3-43)은 이 태스크에서 바꾸지 않는다. Jaeger 보관 90일 이하 또는 원문 속성 끄기는 에이전트·인프라 담당 요구 사항(문서 10.5)으로 이미 넘겼다.

## 범위 변경 (11/23, 사용자 지시)

- 화면 이벤트에 **피드백(👍/👎)** 을 넣는다(`feedback`: 값 `up`·`down`, 선택지 코드, 이유 200자). 이유는 자유 글자라 가린 뒤 `ui_events.reason` 열에 두고, 90일 삭제 대상에 넣는다. `request_id`가 꼭 있어야 한다(어느 답에 대한 피드백인지).
- 화면 이벤트에서 **`page_view`·`chart_view`·`chart_interact`를 뺀다.** 남는 종류: 클릭(`citation_click`, `copy_answer`), `stream_abort`, `feedback`.
- **일별 사용 집계 `daily_usage`** 를 만든다: 질문 수, 세션 수, 대화 수, 대화당 평균 턴 수, 클릭 종류별 수, 👍·👎 수(같은 답에 여러 번 누르면 마지막 값), 답 전 이탈 수. 하네스 트래픽 제외, KST 하루 단위, 같은 날짜를 다시 돌려도 결과가 같다(`python -m kosis_store.daily_usage --date YYYY-MM-DD`).
- 선택지 비교 없이 사용자가 정해 준 범위다. 피드백 저장 테이블(`feedback`, KOS-158)과 겹치는 점은 문서에 적는다.

## 범위 변경 2 (11/23, 사용자 지시): 전체 집계와 사용자별 집계 분리

- `daily_usage`는 **전체 사용 집계**(하루 1행)로 둔다.
- **사용자별 집계 `daily_session_usage`** 를 따로 만든다: 하루 × 사용자 1행. 질문 수, 대화 수, 대화당 평균 턴, 2턴 이상 대화, 이탈, 클릭 2종, 👍·👎, 회원 여부.
- "사용자"의 단위는 **익명 `session_id`**(브라우저가 만든 임의 UUID)로 한다. 로그 정책(POL-006)이 사용자 식별 정보를 남기지 않기로 해서 회원 계정 ID는 로그에 없다. 회원을 계정 단위로 묶으려면 정책 변경이 먼저 필요하다(문서에 적음).
- `session_id`가 없는 질문(화면이 보내지 않은 경우)은 사용자별 표에 들어가지 않고 전체 집계에만 들어간다.
- 같은 명령(`python -m kosis_store.daily_usage --date`)이 두 표를 한 트랜잭션에서 함께 다시 만든다.
- 결과: `daily_session_usage` 추가(키 `(day, session_id)`, 회원 여부 포함). 예시 데이터 3명(질문 3·1·0, 클릭만 한 사용자 포함)의 사용자별 값 30개와 전체 값 10개가 손 계산과 일치, 같은 날짜 재실행 동일, 하네스·`session_id` 없는 질문은 사용자별 표에서 제외 확인(PostgreSQL). 전체 테스트 401 통과.
