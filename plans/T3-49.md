## Idea
1. **필터 하나** `MetricFilter(start_day, end_day, user="all"|"member"|"guest", include_internal=False)`. 기간은 KST 날짜, 최대 90일(FEAT-043), 시작 ≤ 끝을 검사한다. 날짜 범위는 UTC 시각 범위로 바꿔 인덱스를 탄다(T3-36 리뷰 반영 방식 그대로).
2. **탭별 지표 = 함수 하나씩**, 모두 같은 필터를 받는다. 결과는 표 그대로(dict 목록) 돌려준다. 숫자는 SQL이 계산한다.
3. **피드백**은 `ui_events`(`event_type='feedback'`)에서 답(`request_id`)마다 마지막 값 하나만 쓴다(POL-007). 회원/비회원 필터는 `request_logs.is_member`와 `request_id`로 이어서 건다.
4. **👎 답 목록**: `feedback`(마지막 값이 down) ⋈ `request_logs` → 날짜, 가린 질문(90일 지나면 비어 있음), 쓴 표·조사명, 결과, 선택지, 이유, `request_id`(Jaeger 링크용). 최신순, 페이지(크기·위치) 조회.
5. **일별 추이**: 요약 탭의 꺾은선(질문 수, 👍 비율, 이탈률)용으로 날짜별 값을 돌려주는 함수.

## 정한 규칙 (세 옵션 모두, 리뷰 반영)
- **기간:** KST 날짜, 끝 날짜 ≤ **어제**(명세 "전날 기준", 오늘 일부 데이터 섞임 방지), 시작 날짜 ≥ 오늘 − 90일, 시작 ≤ 끝. 어기면 `ValueError`.
- **결과 비율(요약 탭):** 명세 4종 = 답함 `answered` / 거절 `refused` / 되묻기 `clarify` / 오류 `failed`+`error`. 분모는 답 전 이탈(`aborted`)을 뺀 질문 수라 네 비율 합이 100%. 이탈은 사용 패턴 탭의 **이탈률 = `aborted` ÷ 질문 수**(명세의 `stream_abort` ÷ 질문 수를 서버 판정으로 바꾼 것, 문서 12.2 결정).
- **피드백:** 항상 `request_logs`와 inner join한다. 날짜·회원/비회원·내부 여부는 모두 **질문 쪽(`request_logs`) 값**으로 정한다(그래야 전체 = 회원 + 비회원). 답마다 마지막 값은 **기간과 상관없이** `client_ts, received_at, event_id` 순서로 고른다. 그래서 늦게 온 피드백은 그 질문 날짜의 숫자를 바꿀 수 있다(같은 데이터로 다시 조회하면 같은 숫자). `daily_usage`의 피드백 수도 같은 규칙으로 맞춘다.
- **👎 답 목록:** 날짜, 가린 질문(90일 뒤 비어 있음), 쓴 표·조사명, 결과, 선택지 코드, 가린 이유(90일 뒤 비어 있음), `request_id`. 최신순 페이지 조회.
- **내부 트래픽 포함:** `is_internal`은 팀 트래픽과 평가 하네스를 함께 뜻한다. 켜면 평가 질문의 숫자(상위 표·👎 목록 등)가 섞인다(원문은 저장되지 않음). 기본은 제외.

## 공통 (세 옵션 모두)
- 지표 정의는 한 파일에만 둔다. 화면·BI는 그 결과만 읽는다.
- 측정: 지어낸 시드(골든 아님, 회원·비회원·내부·여러 날·피드백 재클릭·90일 지난 원문 포함)를 PostgreSQL에 넣고, 15개 지표 × 필터 조합(전체/회원/비회원, 내부 포함/제외, 하루/여러 날)이 손 계산과 맞는 수.
- 범위 밖: Prometheus 지표(문서 10.3), 화면 자체(BI 도구 선택·구성), 90일 삭제 실행(KOS-167).

## Option A — 원본 로그에서 바로 조회 (공통 CTE 2개 + 지표별 집계 한 줄)
- 접근: 필터를 건 `turns`(request_logs)와 `last_feedback`(ui_events 피드백 → 답마다 마지막 값, request_logs와 join) 두 CTE를 한 곳에 두고, 14개 지표는 그 위에 집계 한 줄씩 올린다. 일별 추이는 같은 함수의 `by_day=True`. 그때그때 원본을 읽는다.
- 예상 성능 향상: 필터 적용 조회 지표 0/14 → **14/14**, 손 계산 일치 목표 14/14(근거: 하루 단위 SQL 9개는 이미 손 계산과 일치, 같은 모양에 공통 조건을 씌움).
- 실질 반영 이점: 필터 조건이 한 곳(CTE)에만 있어 지표끼리 어긋나지 않는다. 여러 날 p50·p95가 정확하다. 스키마 변경 없음.
- 비용·리스크: 1일. 명세의 "집계 결과만 읽는다"와 다르다(원본을 읽음). 매 조회가 원본을 훑는다(지금 규모에선 인덱스로 충분).

## Option B — 일별 집계표만 읽기 (명세 그대로)
- 접근: 집계 배치가 결과별 수·거절 사유별·피드백 선택지별 수·회원/비회원·내부 포함 여부별 값과 일별 지연 p50·p95를 표로 채우고, 조회 함수는 집계표만 읽는다. 👎 답 목록만 원본에서.
- 예상 성능 향상: 필터 적용 14/14. 단 **여러 날 p50·p95는 일별 값으로 정확히 못 합친다**(근사). 필터 조합마다 집계 행이 늘어난다.
- 실질 반영 이점: 명세 문장과 그대로 맞고, 화면 조회가 가장 가볍고, 지난날 숫자가 배치 시점에 고정된다.
- 비용·리스크: 2일. 집계표·하위 표·마이그레이션이 커지고 지표 정의가 배치와 조회 두 곳에 생긴다. 배치가 안 돈 날은 화면이 빈다.

## Option C — 섞기: 개수는 일별 집계표, 분위수·목록은 원본
- 접근: 개수 지표(질문·결과·거절 사유·피드백·클릭·턴·이탈·상위 표)는 집계 배치가 날짜 × 회원/비회원 × 내부 여부로 채운 표에서 합산하고, 합칠 수 없는 지표(지연 p50·p95)와 👎 답 목록만 원본에서 조회한다.
- 예상 성능 향상: 필터 적용 14/14, 분위수도 정확.
- 실질 반영 이점: 개수는 명세처럼 집계 결과를 읽고 날짜별로 고정된다. 분위수는 정확하다.
- 비용·리스크: 1.5~2일. 개수 정의가 배치 쪽, 분위수 정의가 조회 쪽으로 갈려 두 경로를 테스트로 대조해야 한다. 집계표 확장 마이그레이션 필요.

(처음 C안 "A + BI용 DB 뷰"는 리뷰 지적대로 A 다음에 할 일이라 옵션에서 뺐다. BI 도구가 정해지면 A의 CTE를 뷰로 옮기면 된다.)

## Recommendation
**A.** 필터를 한 곳(CTE)에서 걸어 14개 지표가 같은 조건으로 정확히 나오고, 스키마를 바꾸지 않는다. 명세의 "집계 결과만 읽는다"는 화면 속도·숫자 고정을 위한 것인데, 지금 규모에서는 원본 조회로도 충분하고 숫자는 같은 데이터면 같다. 규모가 커지면 개수 지표부터 C처럼 집계표로 옮길 수 있다(같은 정의를 배치에서 호출).
