# T3-63 에이전트 아키텍처 전→후 비교 실험 방법 — baseline = main, 신뢰 기준과 채택 규칙

## Goal
- 완료 기준 (TASK.md 그대로): 아키텍처 실험의 전→후 비교를 **baseline = 실험 시점의 main**(커밋 고정·기록)과 **after = 실험 브랜치**로 같은 조건에서 돌린다. 결과에 잡음 하한(A/A)·짝지은 비교·유의성을 붙이고, 미리 정한 채택 규칙으로 "채택 / 보류 / 기각"을 낸다. `colab/t3_03_e2e_eval_gpu.ipynb`를 이 방식의 범용 노트북으로 바꾼다.
- Baseline: 지금 실험 방법의 신뢰도 — 정량 근거 없음. 아래 "지금 방법의 문제"가 baseline이다.

## 지금 방법의 문제 (T3-03 per10 측정에서 실제로 겪은 것)
1. **잡음을 모른다.** per10은 40대화라 1대화가 2.5%p다. T3-03의 0.650 → 0.625는 1대화 차이였는데, 같은 코드를 두 번 돌렸을 때 몇 개가 뒤집히는지(A/A) 잰 적이 없어 잡음인지 판단할 근거가 없었다.
2. **합계만 비교한다.** 성공률 두 개를 비교하면, 같은 문항에서 "전 성공·후 실패"와 "전 실패·후 성공"이 서로 상쇄된 것이 보이지 않는다. 문항 단위로 짝지어야 바뀐 문항 목록과 차이의 신뢰구간(짝 bootstrap)을 얻는다.
3. **baseline이 고정 커밋이다.** 노트북의 `BASE_REF='bf4d6bf'`는 T3-03 전용이다. 다음 실험의 baseline은 그 시점의 main이어야 하고, 어느 커밋이었는지 결과에 남아야 한다.
4. **baseline이 after의 실전 1·2로 돈다(버그).** 셀 10이 baseline 트리의 `vendor/phase1`·`vendor/phase2`를 after 트리로 symlink한다. 두 브랜치의 pin이 다르면(T3-58처럼) baseline이 after의 실전 1을 쓴다.
5. **채택 기준이 없다.** "몇 → 몇"은 남지만 언제 채택하는지 규칙이 없었다. 그래서 T3-03은 정확도 이득 없이 지연이 늘었는데도 판단을 사람마다 다르게 할 수 있었다.
6. **지연을 다른 세션끼리 비교한다.** Colab per10과 로컬 per10의 지연을 섞어 볼 위험이 있다. 원격 서버(HCX 429 재시도, Colab Qwen) 상태가 지연을 좌우하므로, 같은 세션에서 번갈아 돈 run끼리만 비교할 수 있다.
7. **골든이 바뀌었다.** e2e 기본 골든은 T3-56에서 사람이 쓴 120문항(모두 1턴, 원천 15종: compare 24·trend 21·share 21·value 11·extreme 9·거절/되묻기류 34)으로 바뀌었다. 노트북의 `failure_type` 균등 표본은 이제 동작하지 않는다(라벨 없음). 이전 per10 수치는 새 골든과 비교할 수 없다.

## 이 표본으로 무엇을 가릴 수 있나
- 판정 방법은 팀이 실전 2에서 쓰던 **질문 단위 짝 bootstrap 95% 구간**(`vendor/phase2/lab/lab_common.py` `boot()`, T2-40 채택 기준)으로 통일한다.
  - 문항마다 (after 통과 − baseline 통과) ∈ {−1, 0, +1}을 구한다.
  - 그 평균(= 통과율 차이)을 10,000회 리샘플(seed 0)해 95% 구간을 낸다.
- 정보는 바뀐 문항(discordant)에서만 나온다. 구간의 반폭은 대략 1.96·√(바뀐 문항 수)/120이다. 그래서 구간 하한이 0을 넘는 최소 순이득(이긴 수 − 진 수)은 바뀐 문항 수에 따라 커진다.

| 바뀐 문항 | 최소 순이득 | (120 대비) |
|---|---|---|
| 6~8 | 6 | 5.0%p |
| 10~16 | 8 | 6.7%p |
| 20 | 10 | 8.3%p |
| 30 | 12 | 10.0%p |
| 40 | 14 | 11.7%p |

- 이것은 "구간이 0을 벗어나는 최소 순이득"이지 검출력(진짜 개선을 잡을 확률)이 아니다. 요약: 이 골든 1회로는 **순이득 약 5~12%p 미만의 차이는 가리지 못한다.** 그보다 작은 차이는 "차이 미확인"으로 기록한다.
- 바뀐 문항이 많을수록(아키텍처를 크게 바꿀수록) 필요한 순이득이 커진다. 문항마다 오락가락하는 변경은 좋아진 문항이 많아도 채택되기 어렵다.
- 바뀐 문항이 아주 적으면(약 6개 미만) bootstrap 구간이 실제보다 좁게 나올 수 있다. 그래서 바뀐 문항 수를 구간과 함께 항상 적는다.

## Idea
모든 옵션 공통:
1. **baseline = main**: 노트북이 시작할 때 `origin/main`의 SHA를 받아 고정하고, run 이름·비교 결과에 남긴다. after는 `BRANCH` 설정 하나로 정한다. arm마다 다른 환경변수(예: `AGENT_STEPS`)를 줄 수 있다.
2. **트리마다 자기 submodule**: baseline·after 트리가 각자 `git submodule update --init`을 한다(symlink 제거, 문제 4). `data/`·`evals/datasets/`·`.env`만 공유한다.
3. **같은 세션·번갈아 실행**: baseline → after를 같은 Qwen·HCX·GPU 세션에서 돈다. A/A(baseline 한 번 더)는 **점검용**이다.
   - 같은 코드인데 통과율 차이 구간이 0을 벗어나거나, 지연 p95가 ±20% 넘게 흔들리면 "이 세션은 비교에 못 쓴다"고 표시한다.
   - A/A는 판정 조건에는 쓰지 않는다. 짝 bootstrap 구간이 문항 단위 잡음을 이미 반영하고, A/A 1회 값은 그 자체로 잡음이 크기 때문이다(리뷰 2).
   - 새 baseline(main이 바뀐 뒤 첫 실험)에서 한 번 재고, 같은 main으로 하는 실험에서는 생략할 수 있다.
4. **짝지은 비교**: 문항(sid, turn)마다 baseline·after 통과를 맞춰 다음을 낸다.
   - 바뀐 문항 목록(이긴 것·진 것)과 통과율 차이의 짝 bootstrap 95% 구간
   - 원천별 이김·짐
   - 지연은 문항별 차이(after − baseline)의 중앙값과 그 짝 bootstrap 95% 구간, 두 run 각각의 p95
   - 비용·LLM 호출
5. **채택 규칙** (결과 전에 정하고 바꾸지 않는다. 주 지표 하나 = 문항 통과)

| 단계 | 조건 | 판정 |
|---|---|---|
| ① 가드레일 | **새로 생긴 위반**(baseline에선 없던 문항에서 근거 없는 숫자·출처 누락·run_failure)이 `quality.py`의 `COUNT_TOLERANCE`(2)를 넘으면 | **기각** |
| ② 정확도 | 통과율 차이의 짝 bootstrap 95% 구간 하한 > 0 | 정확도 **개선** |
| | 구간 상한 < 0 | 정확도 **악화** → 기각 |
| | 구간이 0을 포함 | 정확도 **차이 미확인** |
| ③ 원천 쏠림 | 원천 하나에서 진 문항 ≥ 3이고 이긴 문항 0 | 개선이라도 **보류**(그 원천의 진 문항을 보고 원인 기록) |
| ④ 비용·지연 | 아래 표 | |

| ② 정확도 \ ④ 지연 p95·요청당 비용 | 둘 다 +20% 이하 | 하나라도 +20% 초과 | 둘 다 감소(−10% 이상) |
|---|---|---|---|
| 개선 | **채택** | **채택**(비용 증가를 결과에 기록) | **채택** |
| 차이 미확인 | **기각**(바꿀 이유 없음) | **기각** | **채택**(같은 정확도에 더 싸고 빠름) |
| 악화 | 기각 | 기각 | 기각 |

- "보류" 판정이나 "차이 미확인"이 나온 뒤 **같은 변경을 다시 돌려 구간이 0을 벗어날 때까지 재측정하지 않는다**(선택적 중단). 다시 잴 거면 그 실험을 새로 등록하고(반복 k·골든 확장 등 C 방식) 그 결과 하나로만 판정한다(리뷰 3).
- 최종 수치 정확도·툴 정확도는 보조 지표로 보고만 하고 판정에 쓰지 않는다(여러 지표 중 하나가 우연히 좋아 보이는 것을 막음).
- 이전 T3-03 결과는 이 규칙으로 소급 판정하지 않는다. 옛 골든·다른 세션의 수치라 비교할 수 없고, A/A도 없다(리뷰 4). 이 태스크의 Measure에서 main(T3-03 포함)과 `AGENT_STEPS=off`(ReAct 판단 끔)를 이 방법으로 다시 비교해 첫 사례로 남긴다.

## Option A — 합계 + 허용 오차 게이트 (기존 `evals/quality.py` 방식 재사용)
- 접근: 공통 1~3과 ①·④만 쓴다. 정확도는 짝짓지 않고, 합계 성공률 차이를 허용 오차(`COUNT_TOLERANCE`=2문항, A/A로 넓힘)와 비교한다. 지금 품질 게이트(ragas)가 쓰는 방식을 e2e에 그대로 가져온다. 노트북 셀 몇 개로 끝난다.
- 예상 향상 (판단의 질): "허용 오차 안의 차이는 개선 아님"이 생겨 1~2문항 차이를 오판하지 않는다. 다만 같은 수만큼 이기고 진 변경(합계 0)을 "변화 없음"으로 본다. 어떤 문항이 바뀌었는지, 차이가 우연 범위 안인지(구간)는 모른다.
- 실질 반영 이점: 결과 검증. 레포에 이미 있는 규칙과 같은 단위라 설명이 쉽다.
- 비용·리스크: 반나절. 허용 오차 2문항은 근거 없이 정한 값이라, 아키텍처를 크게 바꾼 실험(바뀐 문항이 많음)에서는 너무 느슨하다.

## Option B — 비교 모듈 `evals/compare.py` + 노트북이 그것을 부름 (균형안)
- 접근: 공통 1~5(짝지은 비교 + 짝 bootstrap 95% 구간 + 판정표)를 레포 모듈로 만든다.
  - `python -m evals.compare --base <run> --after <run> [--aa <run>]`
  - 입력: 두 run 폴더(`results.jsonl`·`ops.json`·`manifest.json`)
  - 출력: `evals/reports/compare-<base>-vs-<after>/compare.md`·`compare.json` — 짝지은 표, 바뀐 문항, 통과율 차이·지연 차이의 짝 bootstrap 95% 구간(실전 2 `boot()`와 같은 방법·설정: 10k, seed 0. numpy는 이 레포의 직접 의존성이 아니라 표준 라이브러리 random으로 구현), 원천별 표, 지연 짝 차이, 비용, 채택 판정과 근거
  - pytest로 판정 규칙·bootstrap 구간(고정 seed 결과)·짝 맞추기를 검증한다.
  - 노트북은 run을 돌린 뒤 이 모듈을 부른다. 로컬 run에도 같은 명령을 쓴다.
  - `evals/README.md`에 실험 절차와 채택 규칙을 적는다. CLAUDE.md 1장의 "골든셋 수치로 전→후를 보인 뒤 채택"에도 규칙 링크를 단다.
  - run이 서로 다른 골든·split·표본이면 비교를 거부한다(`manifest.json`의 골든 해시·표본으로 확인). 실전 1 `eval.regress`가 채점기 해시가 다르면 거부하는 것과 같은 원칙이다.
- 예상 향상 (판단의 질): 이기고 진 문항이 상쇄되는 경우를 잡는다. 효과 크기와 95% 구간, 바뀐 문항 목록이 결과에 남는다. 실전 2(T2-40)와 같은 판정 방법이라 팀 안에서 기준이 하나로 맞는다. 로컬·Colab·이전 run을 같은 규칙으로 비교하고, 비교 불가 run(골든이 다름)을 섞는 실수를 코드가 막는다. 문제 6·7처럼 실제로 겪은 실수다. 가릴 수 있는 차이는 위 표(순이득 약 7~12%p 이상)로 결과에 함께 적는다.
- 실질 반영 이점: 결과 검증. T3-10 ADR(ReAct / Plan-and-Execute / 멀티에이전트 비교)의 판정 근거를 하나의 명령으로 만든다. 발표에 "채택 규칙 + 유의성"으로 남는다.
- 비용·리스크: 1일. 기존 run 형식(`results.jsonl`의 `passed`·`unsupported_numbers`·`missing_sources`·`latency_ms`)을 읽기만 하므로 하네스 변경은 없다.

## Option C — B + arm별 반복 실행 (고성능안)
- 접근: B에 더해 e2e 층에 `--repeat k`를 추가한다(지금은 agent 층만 있음). 실행 순서는 B-A-B-A-B-A(k=3)다.
  - 문항마다 k회 중 다수결(또는 pass^k)로 통과를 정한다.
  - A/A는 baseline 반복끼리의 일치율로 잰다.
- 예상 향상 (판단의 질): 문항 단위 잡음(LLM 비결정성·서버 상태)으로 생긴 가짜 "바뀐 문항"이 다수결로 줄어, 같은 개선에서 구간이 좁아진다. 얼마나 줄지는 A/A 일치율에 달려 있어 지금은 추정할 근거가 없다(B에서 A/A를 먼저 재면 알 수 있음). 지연은 문항별 3회 중앙값이라 서버 상태 영향이 줄어든다.
- 실질 반영 이점: 작은 개선(프롬프트 수정 등)도 판정할 수 있다.
- 비용·리스크: 1.5~2일(하네스 변경, e2e 반복 결과 형식). 실행 시간이 3배다. 120문항 1회가 Colab에서 약 40~60분이라 6 run이면 4~6시간이 걸리고, Colab 세션 제한에 걸릴 수 있다. HCX 호출 비용도 3배다. 11/30 기능 동결 직전이라 마감 위험이 있다.

## Recommendation
**옵션 B.** 신뢰성 문제의 핵심(짝지은 비교와 bootstrap 95% 구간, 미리 정한 채택 규칙, 비교 불가 run 거부, A/A 세션 점검)을 레포 코드와 pytest로 고정한다. 그래서 Colab·로컬 어디서 재든 같은 판정이 나온다.
C의 반복 실행은 B의 A/A에서 같은 코드의 문항 뒤집힘이 많다고 확인될 때 필요하다. 그때 C를 새 태스크로 둔다. A는 합계만 봐서 이기고 진 문항이 상쇄되는 경우를 못 잡고, 허용 오차에 근거가 없다.
