  0으로 깎이지 않게 한다. 오류 태그를 맞힌 표/틀린 표로 나눠 집계하고, 답 없는 질문(not_answerable·clarify)은 판정 오류를 검색보다 먼저 귀속하며,
  검색 노드별 정답 순위(fuse → rerank1 → rerank2)를 요약한다. live run `20261118-104236-T3-43-live2-e2e`로 전→후, pytest
- 계기: 외부 병목 분석 문서(`e2e-trace-bottleneck-analysis.md`)를 코드·results.jsonl과 대조한 점검(2026-11-18).

     - e2e 사유 12행 모두 "정답 순위 밖"(9행은 오기).

## Idea
채점·집계 경로만 고친다. 에이전트·실전 1·2 동작, 판정(verdict)·PASS 수는 그대로. 옵션은 핵심 결함 1(예외 시 검색 결과 복원)을 **어디서 읽느냐**로 갈린다.
2~4는 세 옵션 공통:
2. `l4_e2e` summary에 `errors_by_top1 = {"right": Counter, "wrong": Counter}`, report.md·HTML 오류 카드에 맞힌/틀린 표 구분.
3. `blame()`: `kind in (not_answerable, clarify)`이고 판정 오류가 있으면 `understanding`을 검색보다 먼저. answerable·default_allowed 순서는 그대로.
4. `l4_e2e` summary에 `search_nodes = {node: {"top1": n, "topk": n, "missing": n}}`(정답 표가 있는 행, 노드 순서대로), report.md·HTML 한 줄 표.

## Option A — checkpointer 상태 (`graph.get_state`)
- 접근: `single_turns` 예외 경로에서 `graph.get_state(config).values`(마지막으로 끝난 단계의 상태)로 search를 읽는다. checkpointer 없는 그래프는 ValueError → 지금처럼 `{}`.
- 예상 성능 향상: (왜곡 제거) **앞으로의 run만**: 12행 `keys` 0 → 5, "정답 순위 밖" 오기 9 → 0, ID Recall@5 0.791 → ~0.925(= (53+9)/67).
  지난 run·현재 기준선은 그대로(trace_spans에 속성이 없어 재채점으로 못 고침) → 다음 전체 live run(약 40분, HCX + 리랭커 서버)까지 기준선이 낮게 잡힌 채.
- 실질 반영 이점: 예외 처리·결과 검증. 그래프가 가진 상태 그대로라 규칙 추정 없음.
- 비용·리스크: 2~3시간. `table_key`는 statistics가 끝나야 써져 예외 때 비어 있음(대체 표 재시도가 켜지면 이전 표가 남음, 지금 기본 끔). multi 노드 안 예외는 search가 state에 없어 복원 안 됨.

## Option B — 검색 노드 span에서 재구성, 러너·재채점 공용 함수 하나
- 접근: `restore_search(rows)` 하나를 러너(`single_turns` 끝)와 재채점 입력(`runners/stat.read_rows`)이 같이 쓴다. 조건을 좁혀 **error가 있고, gate route=found이고,
  statistics span이 있는데 keys가 빈 행**만: 마지막 순위 노드(rerank2) 앞 k개로 `keys`, 그 1위로 `used_table`. k = 같은 run 정상 행 `keys` 길이(정상 행이 없으면 복원 안 함),
  노드 후보가 더 적으면 그만큼(S-CX-MON-02·S-EDG-06은 2개). 정상 행에서 같은 규칙이 실제 keys를 재현하는지 함께 검사해, 어긋나면 복원하지 않고 경고.
  기존 live run을 `--from-run`으로 e2e 재채점 → Ragas 재채점(심판 캐시, 새 11행만 호출) → 기준선 재설정.
- 예상 성능 향상: 같은 왜곡 제거를 **오늘 run에서 바로**: ID Recall@5 0.791 → ~0.925, ID P·CP·CR도 11행 0점 제거로 상승(심판 결과로 확정). 12행 사유에 실제 순위. PASS 54 불변.
- 실질 반영 이점: 결과 검증 — 지금 기준선이 낮게 잡혀 다음 변경의 "몇 → 몇"이 부풀려지는 것을 막음. live 비용 0, 과거·미래 run에 한 규칙.
- 비용·리스크: 반나절. 규칙(rerank2 앞 k개 = 검색 후보, 정상 78/78 일치)이 실전 2 gate에 기대므로 gate가 바뀌면 틀릴 수 있음 → 위 일치 검사가 막음.

## Option C — 검색 툴 결과 span(`gen_ai.tool.call.result`)에서 후보 읽기
- 접근: 러너가 메모리 span의 `execute_tool search_tables` 결과 JSON(candidates·picked)에서 keys·used_table을 읽는다. 에이전트 계층 채점과 같은 근거(툴 span).
- 예상 성능 향상: A와 같음, 앞으로의 run만(저장된 trace_spans에는 속성이 없어 지난 run은 못 고침). multi 노드 안 예외도 툴이 끝났으면 복원.
- 실질 반영 이점: 툴 결과 그대로라 규칙 추정 없음, 그래프 내부 상태에 기대지 않음.
- 비용·리스크: 반나절. 결과 JSON 형식(실전 2 SearchOutput)에 새로 기대고, 지난 run·기준선은 A처럼 다음 live run까지 왜곡.

## Recommendation
**옵션 B.** 결함 1은 이미 기준선에 들어간 왜곡이라, 앞으로의 run만 고치는 A·C는 다음 전체 live run 전까지 기준선 비교가 계속 틀린다. B는 함수 하나로 과거·미래 run을
같이 고치고 오늘 수치로 전→후를 남긴다. 규칙 추정 위험은 정상 행 일치 검사로 막는다.
- 주의(리뷰 5): 복원해도 12행의 첫 시도 표가 `101_DT_1B8000G`(오답 표)라 `right_table=False` → 대표 단계는 여전히 retrieval. **복원 자체로 대표 단계 건수는 안 바뀐다**
  (retrieval 28 → 24는 3번 판정 순서 변경으로 4행이 understanding으로 옮기는 것). 실전 1 SchemaError는 2번 집계(틀린 표 쪽 run_failure 12)로 따로 보이고, 데이터 수정은 실전 1 범위.
