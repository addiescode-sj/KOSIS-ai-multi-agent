### 1단계 (공통, 옵션과 무관) — 이동 + 툴화, 동작 그대로
1. 아래 지도대로 파일을 옮기고 import를 고친다. supervisor(no-op)를 지운다.
2. 실전 1·2 호출을 툴로 감싼다. 노드는 툴을 `ToolCall` 형태로 `tool.invoke(call, config)` 해서 `execute_tool` span을 남긴다. 흐름은 지금과 같다: 검색 → refuse면 끝, found면 `picked[0]`로 실전 1 → 차트.

### 툴 계약 (하네스 `evals/evaluators/agent.py`에 맞춤)
하네스는 툴 결과만 읽는다. `refused()`는 결과의 `route == "refuse"` 또는 `outcome == "refused"`를 보고, `state_key()`는 `args["table_key"]`를, `stat_answer()`는 결과 최상위를 `StatAnswer`로 검증한다. 그래서 툴 계약을 다음처럼 정한다.

| 툴 | 인자 | content (span에 기록되어 채점에 쓰임) | artifact (노드만 씀) |
|---|---|---|---|
| `search_tables` | `question` | `SearchOutput` JSON (`route`, `picked`, `candidates`, `refusal_text`) | `SearchOutput` 객체 |
| `summarize_stat` | `question`, `table_key` | `StatAnswer` JSON | `StatOutput` (차트·spans 포함) |
| `make_chart` | `table_key`, `chart` (ChartSpec) | Vega-Lite dict | — |

- 세 툴 모두 `response_format="content_and_artifact"`다. `ToolCall`로 부르면 `ToolMessage(content, artifact)`가 돌아오므로, 노드는 artifact에서 차트와 spans를 꺼낸다. ReAct의 `ToolNode`도 같은 방식으로 부르므로 툴을 그대로 재사용할 수 있다.
- **`observability/tracing.py`를 한 군데 고친다.** `on_tool_end`가 `ToolMessage`를 받으면 `.content`를 기록한다. 지금처럼 메시지 전체를 기록하면 하네스가 `StatAnswer`를 검증하지 못한다. 이 수정은 T3-07 ReAct(`ToolNode`)에도 필요하다.
- `summarize_stat`에서 표 키가 tables.csv에 없어 실전 1이 `LookupError`를 내면, 툴은 코드 문장으로 `StatAnswer(outcome="refused", refusal=out_of_scope)`를 돌려준다. 그러면 하네스가 거절로 인식한다. 지금은 이 경우가 SSE `error`로 끝나므로 **동작 변경 1건**이다. `LLMKeyMissing`·`RuntimeError`(키·모델 장애)는 지금처럼 `error`로 둔다. 사전 catalog 검증 단계는 만들지 않는다. 실전 1이 던지는 `LookupError`를 잡으면 같은 효과가 나고, 검증하는 곳도 실전 1 한 곳으로 남는다(리뷰 지적).
- 1단계의 차트는 툴이 아니라 `services/chart.py` 함수를 노드에서 직접 부른다. 차트를 항상 툴로 부르면 기대 툴 목록에 없는 `make_chart`가 매 턴 `extra_call`로 잡힌다(리뷰 지적). `make_chart` 툴은 정의만 해 두고, 사용자가 차트를 요청한 경우나 LLM이 툴을 고르는 아키텍처에서 쓴다.

```text

├── config.py                ← backend/app/config.py (셸 환경 → 설정 객체)

├── retrieval/
│   ├── search.py            SearchModule 생성 + search_tables 툴
```

6장과 다르게 하는 것과 그 이유:
- **`evals/`는 최상위에 둔다.** 이 레포의 `evals/`는 계층 9개짜리 하네스이고, `python -m evals.*` 명령, CI, `tests/test_evals_*` 13개, T3-06 브랜치가 이 경로를 쓴다.
- **`retrieval/dense.py` · `sparse.py` · `fusion.py` · `reranker.py` · `catalog.py`와 `ingestion/`은 만들지 않는다.** 알고리즘은 실전 2 submodule(`kosis_rag/retrieve` · `rerank` · `kosis_rag_build`)에 있고, 그래프는 실전 2 그래프 전체를 한 번에 부른다. 다시 내보내기만 하는 빈 파일은 찾아갈 곳만 늘린다. 대신 `retrieval/README.md`에 "6장 파일 이름 → 실제 위치" 지도를 둔다.
- **`graph/retrieval/`은 2단계에서 검색 재시도 루프가 생길 때만 만든다.** 노드 하나짜리 서브그래프는 함수 하나와 같으므로 만들지 않는다(리뷰 지적).
- **`src/`는 없앤다.** PYTHONPATH가 `. vendor/phase2/src vendor/phase1 vendor/phase1/src`로 준다. 영향받는 곳: `pytest.ini`, `backend/Dockerfile`(COPY·PYTHONPATH·CMD `backend.api.chat:app`), `docker-compose.yml`, `.github/workflows`, CLAUDE.md §3·§4, `docs/current-state.md`, `scripts/stat_oracle.py`·`search_l1.py`, `evals/__init__.py`·`config.py`·`suite.py`·`runners/agent.py`, `tests/`.
- 실전 2의 `backend.app`은 지금도 이 레포 `backend`에 가려져 import되지 않는다. 실전 2는 `kosis_rag.*`만 쓰므로 영향이 없다.

## Option A — 결정적 워크플로 (코드가 경로를 정함)
- 접근: LLM 호출을 추가하지 않는다.
  ```
  START → context ─(지시어 + 직전 표 있음: 검색 생략)───────────────┐
              └─(새 질문)→ search ─(refuse)→ finalize               │
                              └─(found)→ statistics ←───────────────┘
                                          ├─(표 불일치 거절, 예산 남음)→ statistics (다음 후보 표)
                                          ├─(답함)→ chart → finalize
                                          └─(되묻기·질문 문제·예산 끝)→ finalize
  finalize → END   (outcome: answered | refused | clarify | failed)
  ```
  - `context`: 규칙 기반 Context Resolver. 지시어 목록("그 표", "이 표", "같은 표", "거기서" 등)이 있고 checkpointer에 직전 턴의 표 키가 있으면 그 표를 쓴다.
  - `statistics`: 표 불일치 거절(`no_period` · `no_item` · `class_mismatch` · `out_of_scope`)이면 `picked`, 그다음 `candidates` 순서로 다음 표를 시도한다. 예산은 `ALT_TABLE_BUDGET`(기본 1)이다. **`ALT_TABLE_BUDGET=0`이면 1단계와 같은 경로다.** 질문 자체의 문제(`causal` · `unit_mismatch` · `not_aggregatable` · `missing_value`)와 `clarify`는 다시 시도하지 않는다. 시도한 키와 이유를 `ChatResult.attempted_keys`에 남긴다.
  - `finalize`: 답 문장은 실전 1 `StatAnswer.text`나 실전 2 `refusal_text`를 그대로 쓴다. `stage2_error`가 있으면 `ChatResult.degraded = true`로 둔다(P4, 조용한 대체를 드러냄).
- 예상 성능 향상:
  - 그래프 수치 정확도(budget 0 → 1): 상한은 L1 기준 Hit@2 − Hit@1 = **0.117**이다. budget 1이면 대체 표를 1개만 시도하기 때문이다.
  - 이 상한은 L1 문항 기준이라 `calculation_golden`에 그대로 옮길 수 없다. 실제로는 "1위 표에서 표 불일치로 거절된 문항" 안에서만 재시도가 일어나므로 더 작다. **예상 +0~3%p, 근거 약함.** 1단계 baseline에서 그 거절 문항 수를 먼저 세고 예상을 고친다.
  - 지연·비용: 거절 경로에서만 실전 1 호출이 1회 늘어난다. LLM 추가 호출은 0이다.
- 실질 반영 이점: 예외 처리(대체 표, 종료 상태 4종, LookupError 거절), 질의 이해(지시어). 경로가 코드에 있어 오류 추적이 쉽다(architecture 문서 10절의 Supervisor 불필요 근거와 맞음).
- 비용·리스크: 1일.
  - **대체 표가 정의가 다른 표일 위험**(주민등록인구와 인구총조사 등). 완화: 출처가 답에 붙고, 재시도는 검색 후보 안에서만 하며, budget으로 끌 수 있다.
  - 지시어 규칙이 표현을 놓칠 수 있다. T3-04에서 보강한다.
  - **하네스 한계**: agent 계층은 summarize_stat 결과 중 하나라도 거절이면 턴을 거절로 본다. 그래서 대체 표로 답한 턴이 `false_refusal` · `extra_call`로 감점된다. 따라서 재시도 효과는 Result 3의 그래프 e2e로 재고, agent 계층은 budget 0으로만 잰다. 하네스를 "마지막 summarize_stat 결과 기준"으로 바꾸는 것은 T3-06 담당에 후속으로 넘긴다(이 태스크에서 `evals/evaluators/`는 고치지 않는다).

## Option B — ReAct 단일 에이전트 (LLM이 툴을 고름)
- 접근: `agent` 노드(`ChatClovaX` 또는 OpenAI chat model에 `bind_tools`) + `ToolNode` + `tools_condition` 루프로 만든다(`plans/agent-graph-refactor.md` 옵션 B). 툴 결과의 숫자는 LLM이 다시 쓰지 않고, 최종 문장은 마지막 `StatAnswer.text`를 쓴다.
- 예상 성능 향상: 툴·파라미터 정확도가 처음으로 의미 있는 값을 갖는다(1단계는 순서가 고정이라 항상 100%). 수치 정확도는 1단계 대비 −5~+3%p로 추정한다. 근거: LLM이 검색 질문을 바꾸거나 `table_key`를 잘못 고를 수 있어 떨어질 수 있고, 지시어는 LLM이 더 잘 풀 수 있다.
- 실질 반영 이점: 과제의 "툴 호출 에이전트" 형태에 가장 직접적이다. 멀티턴 지시어를 규칙 없이 처리한다.
- 비용·리스크: 1.5일. 턴마다 LLM 호출이 2~3회 늘어난다(지연·비용). `ChatClovaX`의 HCX-007 function calling 지원 여부를 먼저 확인해야 한다. 실행마다 결과가 달라지므로 pass^k로 재야 한다. 이 형태는 T3-07(ReAct 베이스라인)과 겹친다.

## Option C — Plan-and-Execute (LLM이 계획, 코드가 실행)
- 접근: `planner`(LLM Structured Output, `QueryTask` 목록·최대 작업 수 제한) → 작업별로 검색 → 통계를 순차 실행 → 커버리지 검사(필요한 작업마다 답이 있는가) → finalize. architecture 문서 4절의 멀티쿼리("서울이랑 부산 비교")를 처리한다. 검색 재시도 루프가 생기므로 `graph/retrieval/`(evaluator · rewrite)을 만든다.
- 예상 성능 향상: 멀티쿼리 질문의 성공률이 0 → 측정 가능해진다. 지금은 표 하나만 실전 1에 넘기므로 두 표가 필요한 질문은 구조상 실패한다. 단일 표 질문의 수치 정확도는 1단계와 같거나 조금 낮다. 근거: 계획이 단일 작업이면 경로가 1단계와 같고, 계획을 잘못 나누면 떨어진다.
- 실질 반영 이점: 과제 시나리오 중 비교 질문을 다룬다. T3-08(Plan-and-Execute 변형)의 기반이 된다.
- 비용·리스크: 3일 이상. 턴마다 planner LLM 1회와 작업 수만큼 실전 1 호출이 붙는다. 두 표 결과를 합쳐 비교하는 숫자는 실전 1이 아닌 이 레포 코드가 계산해야 하는데, 그 계산 모듈이 아직 없다(범위 커짐). 마감(기능 동결 11/30)과 T3-01~05가 겹친다.

## Recommendation
**1단계 + 옵션 A.** 사용자 요청인 "파이프라인에 따른 워크플로 기반 구조"와 연구 문서 9장("처음부터 도구 선택을 LLM에 맡기지 않는다")에 맞는다. LLM 호출이 늘지 않고, `ALT_TABLE_BUDGET=0`으로 1단계와의 회귀를 같은 코드에서 확인할 수 있다. B와 C는 1단계 툴을 그대로 써서 T3-07 · T3-08에서 같은 평가셋으로 비교한다.
