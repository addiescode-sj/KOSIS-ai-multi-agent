# T3-03 단일 에이전트 루프 — ReAct 단계 판단으로 메인 그래프 재작성

## Goal
- 완료 기준 (TASK.md 그대로): LLM이 툴 선택·순서 결정, 1턴 시나리오 동작.
  이번 요청으로 구체화: 질의 이해 → 재작성(재시도 1회) → 검색·검수 → 답변∥차트 → 검수 → 응답.
- 사용자 요구 흐름 (2026-11-23):
  1. **질의 이해**: 색인과 무관한 질문인지, 질문 종류(단일·계산·멀티표·후속), 재작성이 필요한지,
     답할 수 있는지(서비스가 다루지 않는 종류 · 조사에 없는 질문)를 판단하고 다음 셋 중 하나를 고른다.
     **되묻기** / **템플릿 즉시 답변** / **쿼리 재작성**.
     템플릿 즉시 답변이면 검색하지 않고 루프를 끝낸다. 되묻기·재작성이면 재작성 단계로 간다(되묻기는 사용자 응답을 받은 다음 턴에).
  2. **질의 재작성**: 성공 조건은 "이 질의로 RAG 색인에서 답을 만들 수 있다". Qwen 27B가 불충분하다고 보면 **최대 1회 더** 재작성한다.
  3. **검색 + 검수**: 질문에 맞는 표(여러 개 가능)를 가져왔는지 확인하고, 2차 리랭커로 "검색된 표로 답할 수 없음"을 가린다.
     답할 수 없으면 툴을 더 부르지 않고 끝낸다. 답할 수 있으면 **답변 생성과 차트를 동시에** 진행한다.
  4. **검수**: 답이 응답 템플릿(chatTemplate)을 따르는지, 시각화할 수 없는 경우를 빼고 차트가 제대로 그려졌는지 확인한다.
     그다음 최종 응답 단계로 가서 툴을 더 부르지 않고 끝낸다.
- Baseline:
  - **그래프 전·후 비교 기준 (주 지표)**: 현재 그래프로 `e2e_golden`(601시나리오·694턴)을 실서버(Qwen 리랭커 + HCX 실전 1)로 돌린 run. **아직 없음 → 구현 전에 먼저 잰다.**
    지표: outcome 일치율, false_refusal, 툴 정확도(agent 계층), ④질문 분류 110턴 정답률, 요청당 비용·p50/p95 지연.
  - 참고 (오프라인 규칙 분류, 정답 표 가정, T3-46): route 0.939 · reading 0.975 · resolved_question 0.941 · outcome 0.936.
    route 오류 대부분(rag → rewrite 14)은 규칙이 **확신하고 과분해한** 턴이다("단독주택이랑 아파트 차이"). 판단 보류 턴이 아니다.
  - 지연: T3-43 live e2e p50 21.1s · p95 36.0s (HCX + gemma). Qwen 단계 판단 1회 지연은 **측정 전**.
  - 멀티턴: T3-27 multiturn dev 대화 성공률 0.915 (mock stat).

## Idea
지금 그래프(`graph/main_graph.py`)는 다음 단계를 코드만 정한다(T3-23). 이번 태스크는 단계 경계에 **ReAct 사이클**(Thought → Action → Observation)을 넣는다.
옵션은 "LLM이 다음 단계를 얼마나 정하나"의 차이로 나눴다.

공통 원칙 (세 옵션 모두):
- **Observation은 실제 툴 결과**다(search_tables의 SearchOutput, summarize_stat의 StatAnswer). LLM이 지어내지 않는다(교재 7.5).
- **툴 계약 유지 (T3-01 마무리)**: agent 채점 툴은 `search_tables` · `summarize_stat` · `make_chart` · `combine_values` 4개 그대로.
- **숫자·답 문장은 실전 1**이 만든다. 템플릿 즉시 답변·되묻기는 코드 고정 템플릿에 슬롯만 채운다.
- **새 질문 검색은 사용자 원문으로** 한다(main_graph.py:165, LLM 영향 축소). LLM 재작성 문장은 재작성이 필요하다고 판단된 턴에서만 검색·조건 인자에 쓴다.
  재작성 문장은 원문·직전 질문에 있는 숫자·지역·낱말만 쓸 수 있다(`make_llm_reader`의 기존 검사 재사용). 그래서 기간·지역 조건을 LLM이 새로 만들지 않는다.
- **"조사에 없는 질문"은 실전 2 gate가 거절**한다(검색 뒤 근거 있는 거절). 검색 앞 템플릿은 비통계 질문(인사·기능 문의)과
  서비스가 다루지 않는 종류(예측·인과·개인 정보)만 맡는다. 검색 전 LLM 거절이 새 false_refusal을 만들지 않게 하기 위해서다.
- **기존 경로 유지**: chart_only 턴(→ chart), 멀티쿼리 턴(→ multi: 하위 질문마다 search·summarize_stat·combine_values),
  지시어·이월 턴(→ 직전 표)은 understand의 Action 값으로 그대로 들어간다. `ALT_TABLE_BUDGET`은 계속 기본 0(끔).
- **되묻기 멀티턴**: understand가 되묻기를 고르면 `pending_clarify`(원 질문 + 빠진 슬롯)를 대화 상태에 남긴다. 턴 리셋 대상에서 빼고,
  다음 턴 understand가 먼저 읽어 "원 질문 + 사용자 응답"으로 재작성한 뒤 비운다. 이 경우는 read_turn 이월보다 먼저 처리한다
  (되묻기 답 "부산"이 직전 표 이월로 잘못 읽히지 않게).
- **Qwen 연결**: 2차 리랭커와 같은 OpenAI 호환 서버(`STAGE2_BASE_URL`·`STAGE2_MODEL`)를 기본값으로 하고, `AGENT_MODEL`·`AGENT_BASE_URL`로 분리할 수 있게 한다
  (리랭커·read_turn·splitter와 같은 서버를 쓰면 경합이 생기므로 지연을 따로 잰다). JSON 한 줄로 받아 코드가 검증한다. 형식 오류가 나면 규칙 결과로 돌아간다.
- **답변∥차트**: 차트 종류는 understand가 이미 정하고(chart_request), 자동 선택은 실전 1 stat.chart, 그리기(make_chart)는 코드 ms 단위다.
  그래서 동시 실행으로 줄어드는 지연은 ~0이다. 대신 답변 분기의 재시도·이월 재검색 루프와 join barrier가 꼬일 위험이 있다.
  **기본은 answer → chart 순차**로 두고, 동시 실행 여부는 Decision에서 정한다.
- **LLM 호출 상한**(한 턴, 실전 1·2 내부 제외): read_turn 1 + splitter 1 + understand 1 + 재작성 2 (+ B·C의 판단 호출). 옵션마다 아래에 적는다.

## Option A — 관찰 기반 최소 ReAct (지금 그래프 + 앞단 판단 + 검색 실패 시 재작성 1회)
- 접근: 지금 그래프에 두 분기를 더한다.
  ① 검색 앞 `understand`: 규칙(read_turn·split_question·parse_query 슬롯·비통계/미지원 키워드)이 먼저 판단하고, 판단 보류 턴만 Qwen이 Action
  `template | clarify | rewrite | search` 중 하나를 고른다. template·clarify는 툴 없이 finalize로 간다.
  ② `after_search`가 refuse(또는 넘길 표 없음)이면 Qwen이 실패 Observation(gate 거절 이유·후보 표 이름)을 보고 질의를 **1회 재작성 → search 1회 더** 한다.
  "재작성 성공" = 다시 검색했을 때 gate가 found를 내는 것. 즉 LLM 추측이 아니라 실제 검색 결과로 판단한다.
  verify = 실전 2 2차 리랭커·gate 결과(지금 after_search), review = finalize 안의 코드 검사(출처 줄, 답 숫자 ⊂ 실전 1 사실값, 차트 data.values ⊂ 사실값).
- 예상 성능 향상: 측정 전 추정. ④질문 분류 중 비통계·미지원(거절 50 · 인과 15의 일부)을 검색 앞에서 끊어 그 턴의 검색 호출 → 0.
  검색 거절 후 재작성 1회로 false_refusal 일부 회복(T3-27 실측: "부산은?" 원문 검색 거절 → 다시 쓴 문장 검색은 found). 회복 폭은 baseline run의 refuse 턴 수로 정해진다.
  route 과분해 오류(14)는 고치지 않는다(규칙이 확신한 턴이라 Qwen까지 가지 않음).
  지연: 비통계 턴은 감소, 나머지는 understand Qwen 0~1회 + 재작성 턴만 Qwen 1회 + 검색 1회 증가.
- 실질 반영 이점: 예외 처리(비통계·미지원 질문 즉시 안내, 검색 실패 회복) · 질의 이해. 그래프 변경이 가장 작아 T3-27·T3-28 측정치를 지킨다.
- 비용·리스크: 1~1.5일. LLM 상한/턴 = read_turn 1 + splitter 1 + understand 1 + 재작성 1 = 4. 리스크: 재작성 검색이 틀린 표를 found로 고를 수 있다
  (T3-23 대체 표 재시도와 같은 위험). 재작성 문장의 낱말 제한 검사로 줄이고, 재검색 found 턴의 정답 표 일치율을 따로 센다.

## Option B — 단계별 ReAct 판단 노드 (A + 검색 전 재작성 충분성 판단 + 과분해 검토)
- 접근: A에 사용자가 말한 "Qwen이 재작성이 불충분하다고 보면 1회 더"를 그대로 넣는다. `rewrite` 노드가 재작성한 뒤 Qwen이 **검색 전에**
  "이 질의로 색인에서 답할 수 있나(지표·기간·지역이 다 있나)"를 Thought+Action(`sufficient | retry`)으로 판단하고, 불충분하면 1회 더 쓴다.
  2회 모두 불충분이면 되묻기로 끝낸다. 또 understand가 규칙의 **멀티쿼리 분해 결정**도 Qwen에게 한 번 검토받는다(route 과분해 오류가 모인 곳).
  단계마다 Thought·Action을 `trace`(이번 턴 상태, 턴마다 리셋, reducer 없이 노드가 전체 값을 반환)에 남겨 SSE·UI에 보인다.
- 예상 성능 향상: 측정 전 추정. A의 효과 + route 과분해 14건 일부 교정(같은 표 비교를 한 질문으로 되돌림, 오프라인 route 0.939 → 최대 0.96).
  사전 충분성 판단이 되묻기를 검색 앞으로 당겨 실전 1 되묻기·거절 일부가 줄어든다. 반대로 Qwen이 충분한 질문을 불충분으로 볼 때의 불필요 되묻기는 새 위험이다.
  지연: 재작성 턴마다 Qwen 판단 1~2회 추가.
- 실질 반영 이점: 사용자 요구 흐름과 단계가 1:1로 맞는다. 단계별 Thought 기록이 trace·발표 자료에 남는다. 툴 계약 유지 → T3-07·T3-10 비교에 바로 쓴다.
- 비용·리스크: 2~3일. LLM 상한/턴 = A의 4 + 재작성 1 + 충분성 판단 2 + 분해 검토 1 = 8(대부분 턴은 규칙으로 0~2). 리스크: 경량화 Qwen 판단 오류로 인한 불필요 되묻기.
  측정 지표에 "불필요 되묻기 수"를 넣는다.

## Option C — 단일 ReAct 에이전트 루프 (LLM이 툴 순서를 모두 정함)
- 접근: Qwen 하나가 Thought/Action/Action Input/Observation 텍스트 프로토콜로 루프를 돈다. 툴 8개:
  `understand_query` · `rewrite_query` · `search_tables` · `verify_tables` · `summarize_stat` · `make_chart` · `reply_template` · `ask_user`.
  코드는 가드만 둔다(summarize_stat은 검수 통과한 표 키만, 최대 8스텝, Final Answer는 실전 1 문장 그대로).
- 예상 성능 향상: 측정 전 추정. 툴 순서를 매 턴 경량화 27B가 정하므로 툴 정확도·route 변동이 크다(하락 가능). 규칙 판단은 프롬프트 예시로만 전달된다. 지연 +LLM 4~8회/턴.
- 실질 반영 이점: TASK.md 문구("LLM이 툴 선택·순서 결정")와 가장 가깝다. T3-10의 "ReAct 단일" 비교군.
- 비용·리스크: 3~4일. 판단 툴 4개가 agent 채점에서 `extra_call`이 되므로 하네스 허용 목록 수정(채점 계약 변경)이 필요하다. 비용·지연이 가장 크다. 마감 위험 중간.

## Recommendation
**옵션 B.** 사용자 요구 흐름("Qwen이 재작성 불충분을 판단해 1회 더", 단계마다 넘어갈지 추론)과 단계가 1:1로 맞는 최소안이다.
A의 관찰 기반 재작성(검색 실패 후 1회)도 B 안에 들어 있다. route 오류가 모인 곳(과분해)을 B만 건드린다.
**데이터 정확성 우선이면 A**가 더 안전하다(LLM이 검색 전 판단을 하지 않음). B로 구현하더라도 충분성 판단은 env 플래그로 끌 수 있게 해서
같은 run에서 A·B를 둘 다 잰다. C는 T3-07/T3-10 비교군으로 남긴다.
