# T3-38 멀티쿼리 부분 거절 채점 (KOS-199) · 모델 단가 (KOS-200)

## Goal
- KOS-199: "A와 B 알려줘"에서 B만 자료가 없을 때, 지금 채점기(`evals/evaluators/agent/state.py` `refused()`)는 호출 하나라도 거절이면 턴 전체를 거절로 본다.
  그래서 `refuse=false` 턴은 `false_refusal`이 되고, "하위 질문 2는 거절해야 한다"를 적을 방법이 없다. 하위 질문별 거절을 적고 채점한다.
- KOS-200: `evals/pricing.json`의 HCX-DASH-002·HCX-005·HCX-007(KRW)·Gemma 단가가 null이다. 공식 NAVER Cloud 가격 페이지에서 읽은 값만 채운다.

## Idea
- 시나리오 `TurnExpect`에 선택 필드 `refuse_parts: list[bool]`(하위 질문 순서)을 더한다. 없으면 지금 규칙 그대로(기존 파일 채점·직렬화 바이트 동일).
- 하위 질문과 툴 호출의 대응은 그래프가 실제로 남기는 순서를 따른다(`src/kosis_agent/graph/main_graph.py` `multi_node`):
  하위 질문마다 `search_tables`를 먼저 모두 부르고, 표를 찾은(`route=found`, 후보 있음) 하위 질문만 순서대로 `summarize_stat`을 부른다.
  검색이 거절한 하위 질문은 `summarize_stat`이 없다. 그래서 k번째 하위 질문의 거절 = k번째 검색이 거절했거나, 그 검색에 이어진 `summarize_stat`이 `refused`.
  검색 수가 하위 질문 수와 다르거나(나누지 않음), 찾은 검색 수와 `summarize_stat` 수가 다르면(같은 표로 되돌려 원문 한 번) 하위 질문마다 턴 전체 거절 여부를 쓴다.
- 수치: 거절해야 할 하위 질문에는 `calc_qid`가 없다. `refuse_parts`가 있으면 `calc_qids`는 답하는 하위 질문(False)에만, 그 순서대로 붙고 그 하위 질문의 `summarize_stat`으로 채점한다.
- 빌더: `calculation_golden` 답할 수 있는 문항 + `not_answerable` 문항을 "그리고"로 잇는 R 유형을 새 파일(`agent_scenarios_multiquery_dev_refusal.jsonl`)에 쓴다. 기존 B·K·N·P 파일은 그대로.
- 단가: 공식 페이지에서 읽을 수 있으면 값과 `_source`(URL·읽은 날짜), 못 읽으면 null 유지. Gemma는 null + `_note`(0 vs GPU 시간은 팀 결정). 환율 없음, 통화 섞이면 합계 없음 규칙 유지.

## Option A — 하위 질문별 거절 목록 `refuse_parts` (선택)
- 위 Idea 그대로. 오류 이름은 `missed_refusal` / `false_refusal` 그대로, 틀린 하위 질문마다 하나씩, 행에 `refused_parts`·`refusal_parts`(하위 질문 번호) 기록.
- 예상: 부분 거절 시나리오에서 지금 규칙의 `false_refusal` n건 → 0건(에이전트가 맞게 거절했을 때), 기존 파일 재채점 summary 동일.
- 비용·리스크: 반나절, LLM 0. 하위 질문 1이 실전 1에서 거절되고 2가 다른 표로 답하면 `final_calls`가 1을 대체 표 시도로 접는다(기존 규칙). R 유형은 답하는 하위 질문을 앞에 둬서 피하고 한계로 적는다.

## Option B — 턴 단위 `refuse`를 "any / all / none" 열거형으로 확장
- 하위 질문 번호 없이 "일부 거절"만 적는다. 어느 하위 질문이 거절했는지 틀려도 통과해 데이터 정확성 기준에 약하다.

## Option C — 하위 질문을 시나리오의 별도 턴으로 펼침
- 한 턴을 하위 질문 수만큼 가짜 턴으로 나눠 기존 `refuse`를 재사용. 대화 성공률·턴 통과율의 분모가 바뀌고 실행 기록(턴 = 요청 1건)과 어긋난다.
