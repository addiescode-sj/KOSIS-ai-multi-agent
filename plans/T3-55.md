# T3-55 확정 계약(api.md · log-schema.md)에 맞춘 API 보완과 프론트 연결

## Goal
- 완료 기준 (TASK.md 그대로): `docs/service/api.md`·`docs/log-schema.md`(main `33d3ce4`)를 기준으로 백엔드 계약 불일치를 고치고, 프론트를 확정 API에 연결한다. 서버 상태는 TanStack Query 훅 모듈(`usePrefetchQuery`·`useSuspenseQuery`, streaming SSR)로, API 호출은 컴포넌트 밖 모듈로, 브라우저 저장(persist)은 중앙 hook 하나로 모은다. pytest·jest·build 통과, Playwright로 화면 확인.
- 요청 (11/25, 임도유): 기준은 GitHub의 두 문서. 문서와 코드가 다른 곳은 물어보고 정한다(아래 Decision).
- Baseline (main `33d3ce4`, 11/25 감사):
  - 백엔드 계약 불일치 6건: `/events` 본문 형태, 오류 형식 `{"detail"}` 3곳, 레지스트리 밖 표 키(422 아님), 피드백 선택지 코드 2벌(`accurate_number·right_table` vs `accurate·found_table`), `failed` 답 피드백 받음(제안값은 안 받음), 메트릭의 👍/👎가 `feedback` 테이블을 읽지 않음.
  - api.md 자체가 낡은 곳 2곳(5줄 "로그인 아직 없음", 1장 표에 `PATCH·DELETE /auth/me`·`/ops/log-counts` 없음).
  - 프론트 미연결: `POST /feedback`·`POST /events` 호출과 프록시 없음, `meta.expired` 미사용(`threadLost()`가 옛 주소 `/threads/{id}`), 표 검색이 옛 주소 `/tools/search_tables`, `error.retryable` 자동 재연결 없음, `retry_of`·`input_method` 미전송, 답 복사 버튼 없음.
  - 프론트 패턴: `usePrefetchQuery` 0곳, `/chat` 목록이 클라이언트 페이지(서버 prefetch 없음), 컴포넌트 안 fetch 2곳(로그아웃·탈퇴 창), 키 팩토리 밖 키 1곳, `new QueryClient()` 직접 생성 1곳, localStorage 저장 3개가 파일마다 따로(공통 hook 없음), 비회원 목록이 localStorage(문서는 sessionStorage).
  - 테스트: 백엔드 pytest(서비스 API·로그), 프론트 jest(lib 단위)만. 화면 테스트 없음.

## 범위 밖 (이 태스크에서 하지 않음)
- 그래프(AI 파이프라인) 쪽: `retry` SSE 이벤트, `outcome` `partial`·`general`, 하위 답별 차트(api.md 9장 3·3-1, 전민기 담당). 평가 하네스(`evals/`)는 고치지 않는다.
- 운영자 메트릭 API `/admin/*`(api.md 7장 보류, Grafana 제안).
- 옛 주소(`POST /chat`·`/tools/*`·`GET /threads/{id}`) 삭제: deprecated로 남긴다(11/25 결정).

## Idea
1. **백엔드 계약 맞추기** (`backend/app/main.py`, `src/kosis_store/`, `tests/`)
   - `/events`: 본문 `{"events": [...]}`(api.md 5장). 테스트 갱신.
   - 오류 형식: `_loaded()` 503, `/dev/threads` 404, `/dev/chat` 500도 `{"error": {code, message}}`(0장). 전역 `HTTPException` 처리기로 한 곳에서.
   - 레지스트리 밖 `table_key` → 422(0장).
   - 피드백: 저장 기준은 `POST /feedback` 한 곳(5장 "피드백 저장의 기준"). `failed` 답은 422로 받지 않음(10장 제안 5). `ui_events`의 `feedback` 종류는 수신만 유지(옛 클라이언트 호환, 지표에 안 씀).
   - 피드백 원천 전환(log-schema 12.2 "둘 중 하나로 정한다" → `feedback`)은 **세 곳을 함께**: `log_metrics.py` `_LAST_FEEDBACK`(메트릭), `_REVIEW_FEEDBACK`(검수 조회, T3-52), `daily_usage.py`(`feedback_up`·`down` 집계). 응답 키는 유지하려고 `category AS choice`로 읽고, 코드값은 `accurate`·`found_table` → `accurate_number`·`right_table`로 바뀐다. 마지막 값 규칙은 `client_ts DESC`가 아니라 `request_id`당 1행 upsert(서버 도착 순, `updated_at`)로 바뀐다 → log-schema 14.2 갱신. 테스트 갱신: `tests/test_log_queries.py` fixture·기대값, `tests/test_review_queries.py`의 실행 계획 단정(`ix_ui_events_request_id` → `feedback.request_id` unique 인덱스), daily_usage 테스트.
   - 이미 `ui_events`에 쌓인 피드백 이벤트는 옮기지 않는다(백필 없음, 지표에서 빠짐). Result에 적는다.
   - 회원 대화 복원 `GET /chat/{id}`의 각 턴에 `feedback: {value, category} | null`을 붙인다(복원 화면에서 누른 값 표시).
   - OpenAPI 다시 내보내기(`scripts/export_openapi.py`), api.md 낡은 곳과 오늘 결정 반영, log-schema 12.2·14.2 피드백 원천 문구 갱신.
2. **프론트 데이터 층** (`frontend/lib/`, `frontend/app/api/`)
   - API 모듈: 지금 관례대로 도메인 폴더에 `lib/<도메인>/<이름>.ts`(fetch 함수, zod는 쓰는 곳 가까이)와 `lib/<도메인>/use-<이름>.ts`(Query 훅). 새 `lib/api/` 층은 만들지 않는다. Query 키는 `lib/query/keys.ts`에만 추가하고, 쿼리 함수는 throw하지 않고 상태 값을 돌려준다(`authFrom` 패턴, AGENTS.md). 컴포넌트는 훅만 쓴다.
   - 프록시 route 추가: `app/api/feedback`, `app/api/events` (`proxy()` 재사용).
   - 서버 prefetch + suspense: 서버 컴포넌트에서 `prefetchQuery`(await 없이) → `HydrationBoundary`, 클라이언트는 `useSuspenseQuery`. 같은 화면 안 하위 데이터는 `usePrefetchQuery`로 미리 당김. `/chat` 목록을 이 방식으로.
   - 중앙 persist hook `usePersisted(key)`(`lib/storage/`): sessionStorage·localStorage 어댑터 하나, `useSyncExternalStore` 공통 구현, 스키마 버전·zod 검사·실패 시 기본값. 비회원 대화 목록·세션은 sessionStorage(1장), 알림 설정은 localStorage. 기존 모듈의 export 이름은 유지해 호출부가 그대로 쓰게 한다.
   - 옛 localStorage 비회원 목록(`kosis.conversations.v1`·`kosis.session.v1`)은 첫 로드 때 지금 탭의 sessionStorage로 한 번 옮기고 localStorage에서 지운다(이전 대화가 갑자기 사라지지 않게).
   - 비회원 턴에 누른 피드백(`feedback: {value, category} | null`)을 저장할 수 있게 `conversations.ts` 턴 형태에 선택 필드를 추가한다.
3. **프론트 기능 연결** (`frontend/components/`, `app/api/chat/route.ts`)
   - 👍/👎 + 선택지 + 이유(3장, 👍 5개·👎 4개·이유 200자, 기타면 이유 필수), `useMutation`으로 `POST /feedback`, 낙관적 갱신. 비회원은 누른 값을 해당 턴과 함께 sessionStorage에, 회원은 복원 응답의 `feedback`으로 표시.
   - 화면 이벤트 3종 `citation_click`·`copy_answer`·`stream_abort`를 `POST /events`로 모아 보냄(백그라운드, 실패는 버리고 셈). 답 복사 버튼 추가.
   - `meta.expired` → "이전 대화가 만료되었습니다" 안내, `threadLost()` 제거. 표 검색은 `/dev/tools/search_tables`.
   - `error.retryable`이면 자동 재연결 1회(10장 제안 8) + "다시 연결하는 중" 상태, 다시 시도는 `retry_of` 전송, 되묻기 버튼은 `input_method: "clarify_option"`.
4. **검증**: pytest 전체, jest, `next build`, lint. Docker로 띄워 Playwright MCP로 새 대화 → 답 → 피드백 → 출처 클릭 → 복사 → 목록 → 삭제, 만료 안내, 회원 목록(로그인 없이 가능한 범위) 확인.

병렬: 1(백엔드), 2(데이터 층), 3(기능 연결)을 서브에이전트 3개로. 파일 담당(겹치면 담당자만 고친다):

## Option A — 최소안: 계약만 맞추고 지금 패턴에 붙이기
- 접근: 1번 전체 + 3번 기능 연결을 지금 구조(`useState`·개별 store)에 덧붙인다. 피드백은 `POST /feedback`만, 메트릭 원천 변경, 복원 응답에 피드백 없음.
- 예상 성능 향상: 계약 불일치 6 → 0, 프론트 미연결 7 → 0. 패턴 문제 7건은 그대로.
- 실질 반영 이점: 기능 완성도·예외 처리(만료·재연결). 로그가 실제로 쌓이기 시작(피드백·화면 이벤트).
- 비용·리스크: 작음. 요청한 Query 훅·persist 모듈화는 빠진다.

## Option B — 균형안: 계약 + 데이터 층 모듈화 + 기능 연결 (추천)
- 접근: Idea 1~4 전부. 피드백은 저장 한 곳(`feedback` 테이블)과 표시용 복원(회원 응답 필드·비회원 sessionStorage).
- 예상 성능 향상: 계약 불일치 6 → 0, 프론트 미연결 7 → 0, 패턴 문제 7 → 0. 화면 테스트 0 → Playwright 시나리오 1벌.
- 실질 반영 이점: 요청한 구조(streaming SSR Query 훅, API 모듈, 중앙 persist)를 그대로 충족. 피드백이 한 곳에 쌓여 지표·👎 목록·검수(T3-52)가 같은 원천을 읽는다. 데이터 이중 저장이 없다.
- 비용·리스크: 프론트 변경 범위가 커서 리뷰 부담(이선주 님 리뷰 요청). 2·3 병렬의 파일 충돌은 위 소유 규칙으로 막는다.

## Option C — 고성능안: B + 피드백 조회 API와 운영자 API
- 접근: B에 더해 `GET /feedback?request_ids=…`(비회원 24시간 포함, 어느 진입점에서도 서버에서 피드백 상태 조회), `/admin/metrics`·`/admin/feedback`(api.md 7장 형식, 팀 토큰), 옛 주소 삭제.
- 예상 성능 향상: B와 같음 + 다른 기기·다른 탭에서도 비회원 피드백 상태 복원.
- 실질 반영 이점: 진입점이 늘어도 서버 한 곳에서 읽음. 운영자 화면을 프론트로 만들 때 바로 씀.
- 비용·리스크: 7장은 보류(도구 미정), 옛 주소 삭제는 다른 코드가 깨질 수 있음. 비회원 탭 단위 정책(sessionStorage)과 "다른 탭에서도 복원"이 충돌한다.

## Recommendation
옵션 B. 피드백은 **쓰기 한 곳(`POST /feedback` → `feedback` 테이블, `request_id`당 마지막 값 1행) + 읽기는 화면이 이미 가진 진입점에 붙이기**가 맞다. 화면이 피드백 상태를 필요로 하는 곳은 "지금 보는 답"과 "다시 연 회원 대화" 두 곳뿐이다. 앞은 mutation 결과(낙관적 갱신)로, 뒤는 `GET /chat/{id}` 응답 필드로 충분해 따로 조회 API가 필요 없다(C의 조회 API는 진입점이 늘 때 추가). 비회원은 문서대로 탭 단위라 sessionStorage가 원천이다. 지표·👎 목록은 같은 `feedback` 테이블을 질문 행과 join해 읽는다.
