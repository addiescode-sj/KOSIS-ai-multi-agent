# T3-22 검색 골든셋 판정 풀 확장·재판정 (BM25 편향 보정)

## Goal
- 완료 기준 (TASK.md 그대로): unjudged@10·Hit@k·MRR 재판정 전→후, 판정 근거가 남은 풀, 풀 갱신 pytest (Linear KOS-171)
- Baseline (골든 v1 test, 답할 수 있는 60문항, `evals/reports/20261106-*-T3-06-e2e-mock-l1-*`). 하한 = 지금 채점(판정 없는 표는 오답), 상한 = 판정 없는 표를 전부 정답으로 본 값. 둘 다 저장된 순위로 코드가 계산했다.

| 검색기 | Hit@1 | Hit@5 | Hit@10 | MRR | unjudged@10 |
| --- | --- | --- | --- | --- | --- |
| hybrid+cond | 0.400 ~ 0.683 | 0.717 ~ 0.967 | 0.883 ~ 1.000 | 0.543 ~ 0.807 | 0.463 |
| staged | 0.500 ~ 0.783 | 0.800 ~ 0.950 | 0.883 ~ 1.000 | 0.630 ~ 0.853 | 0.498 |

- 구간이 넓어 지금은 hybrid와 staged의 차이도 단정할 수 없다(Hit@1 구간이 겹친다).

## Idea
T2-02 풀은 BM25 두 종류의 상위 10개 + 직접 추가한 정답(242행)이다. "정답 아님" 판정은 BM25 후보에만 있다. T2-02 동결 규칙(`vendor/phase2/plans/T2-02.md:21`)은 "이후 검색기의 판정 없는 적중을 **사람이 판정해 정답으로 확인했을 때만** 대체 key를 추가하고, label_version을 올리고, 이전 실행을 다시 채점한다"이다. 이 규칙을 처음으로 실행한다.

공통 코드 (세 옵션 모두):
1. **L1 재채점 `--from-run`**: 지금 `--from-run`은 l3·agent 전용이다. l1에 추가해 저장된 순위(`results.jsonl`의 `keys`)를 새 라벨로 다시 채점한다. 검색은 다시 돌리지 않는다. tau는 저장된 run의 manifest 값을 그대로 쓴다(dev 행이 없어 다시 고를 수 없고, 답 없음 P/R을 같은 조건으로 비교해야 하므로).
2. **구간 지표**: 리포트에 하한(지금 채점)과 상한(판정 없는 표 = 정답)을 함께 낸다.
3. **판정 출처 분리**: `judged_keys`는 사람이 본 key만 센다. LLM만 본 행은 사람 판정으로 섞지 않는다. unjudged@10은 사람 기준으로 내고, LLM 판정까지 포함한 값은 따로 낸다.

## Option A — 구간만 보고 (판정 0건)
- 접근: 공통 코드 1~3만. 라벨은 바꾸지 않고, 모든 L1 리포트에 하한~상한을 낸다.
- 예상 성능 향상: 지표 값은 그대로다(위 표). 대신 "Hit@1 0.50"이 "0.50 ~ 0.78"로 정직하게 바뀐다.
- 실질 반영 이점: 결과 검증 — 과소평가 가능성을 숫자로 드러낸다. 판정 비용 0. 이후 B·C의 기반 코드다.
- 비용·리스크: 코드 2~3시간. 구간이 넓어서 검색기 비교나 개선 판단에는 쓸 수 없다.

## Option B — 사람이 1위 29쌍만 판정 + A
- 접근: A + hybrid·staged에서 1위가 판정 없는 표인 29쌍을 사람이 직접 판정한다(시트 제공). `pool.py adjudicate`가 사람이 정답으로 표시한 행만 골든에 대체 key로 추가하고(test는 추가만, split·질문·답 없음 여부는 그대로), 바뀐 문항의 label_version을 2로 올린다. 이어서 `--from-run`으로 재채점한다.
- 예상 성능 향상: Hit@1의 구간이 한 값으로 줄어든다(staged 0.500 ~ 0.783 → 그 안의 확정값, hybrid도 같음). Hit@5·10·MRR은 구간이 조금만 좁아진다.
- 실질 반영 이점: 동결 규칙을 지키는 최소안. 가장 많이 보는 Hit@1이 확정된다.
- 비용·리스크: 코드 0.5일 + 사람 판정 약 30분. 상위 2~10위의 편향은 남는다. 다음 검색기 변경 때 다시 해야 한다.

## Option C — LLM 1차 판정 449쌍 → 사람 확정 + A (균형)
- 접근:
  1. `pool.py extend --runs <run…>`가 저장된 L1 run의 상위 k개 중 풀에 없는 (qid, key)를 새 행으로 붙인다. 답할 수 있는 문항은 상위 10개, 답 없음 문항은 상위 3개다. `found_by`에 검색기와 순위를 남긴다. 대상은 383 + 66 = 449쌍이다.
  2. Claude 서브에이전트 3개가 문항 단위로 나눠 병렬로 1차 판정한다(질문·정답 표·후보 표의 메타데이터). 결과는 `llm_slot`·`llm_note`(행마다 근거 한 줄)·`judged_by=llm` 열로만 남기고, 사람 판정 열(`slot`)은 건드리지 않는다.
  3. 사람 검수 시트: LLM이 정답으로 본 행 전부 + 오답으로 본 행 5개 중 1개. 사람이 `ok`를 채운다.
  4. `pool.py adjudicate`는 사람이 확인한 행만 골든(`retrieval_golden.jsonl`)에 추가한다(동결 규칙). LLM 판정 전체는 잠정 골든(`retrieval_golden.provisional.jsonl`)으로 따로 만든다.
  5. 재채점은 세 가지 값으로 낸다: 구간(하한~상한) / 잠정(LLM 라벨) / 확정(사람 확인). 사람 검수가 끝나기 전에는 잠정값과 구간만 있다.
  6. 답 없음 문항에서 "답이 되는 표"가 나오면 라벨을 바꾸지 않고 검수 시트에 표시만 한다.
- 예상 성능 향상: 판정 직후 구간이 잠정값 하나로 줄어든다(Hit@1·5·10·MRR 모두). 사람 검수 뒤 확정값이 나온다. 값의 방향은 하한 이상이다. 크기는 판정 전에는 근거 있게 말할 수 없다(리뷰 지적). 판정 결과에서 실측한다.
- 실질 반영 이점: 데이터 정확성 · 결과 검증 — 검색 지표가 BM25 편향 없이 임베딩·리랭커를 평가한다. LLM이 후보를 미리 정리해서 사람 판정량이 449쌍에서 "LLM 정답 + 표본"으로 준다. 재사용 — 검색기를 바꿀 때마다 `extend → LLM 1차 판정 → 사람 확정 → adjudicate → --from-run 재채점`을 그대로 돈다(T3-07~10 비교, KOS-138 pgvector 전환 비교). LLM 판정과 사람 판정의 일치율을 남겨, 앞으로 LLM 1차 판정을 얼마나 믿을지 근거가 생긴다.
- 비용·리스크: 코드 0.5~1일 + LLM 판정 병렬 1~2시간 + 사람 검수(LLM 정답 수에 비례, 예상 1~2시간). 사람 검수 전까지 확정값이 없다. dev split은 staged run이 없어 이번 범위 밖이다.

## Recommendation
**Option C.** 사용자 요청(서브에이전트 병렬 판정)과 맞고, 동결 규칙을 지키면서(사람 확인분만 골든에 반영) 상위 10개 전체의 편향을 다룬다. A는 숫자를 정직하게 만들 뿐 개선 판단에는 못 쓴다. B는 규칙을 지키는 최소안이지만 Hit@1만 확정하고 절차가 남지 않는다.
