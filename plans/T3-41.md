# T3-41 대체 정답 표 라벨 확장 + 대체 표 답의 숫자 채점

## Goal
- 완료 기준 (TASK.md 그대로): 수치 골든 중 대체 표 판정이 없는 문항(L1 미연결 80/90)에 같은 기간·지역의 골든 값이 모두 있는 표를
  코드로 찾아 대체 정답 표 라벨(근거 셀 포함)을 달고, e2e 숫자 채점이 대체 표로 맞게 답한 경우를 그 표의 셀로 채점한다(골든 값 그대로).
  재채점으로 정답 표 연결 수·PASS·Ragas LLM↔ID 일치율 전→후, pytest
- 계기 (2026-11-17, T3-19 결과 검토): LLM Context Recall 0.851 vs 코드 ID Recall 0.567. 불일치 20문항(LLM은 근거 있음, 코드는 없음)이
  전부 L1 미연결 문항.
- Baseline (`evals/reports/20261116-203254-T3-35-e2e-regrade`, HCX e2e 90문항 / `20261117-115502-T3-19-baseline`):
  - 정답 표 판정이 대체 표를 아는 문항(L1 연결) **10/90**

## 현재 구조에서 확인한 사실
1. 대체 표 판정은 `evals/runners/e2e.locate()`가 L1 검색 골든 슬롯으로만 안다 → 10/90. (Linear KOS-201 "phase1_id 짝짓기"가 같은 문제)
2. 숫자 채점(`evaluators/calculation.grade`)은 **대표 표 Parquet 셀만** 읽는다(`common.grade`가 `item.table_key` 파일을 연다).
   대체 표 셀을 인용한 답은 `unsupported_claim` + `wrong_dims`. T3-39는 "정답 표를 골랐나"에만 대체 표를 인정했다.
   agent 계층 `evaluators/agent/numbers.py`도 `item.table_key`로 채점한다(같은 문제).
3. 파생 사실(`f3 = f1 / f2 * 100`)은 fact id로 계산식을 쓰므로 셀 사실의 source_ref만 바꾸면 채점기 재사용 가능.
4. 값 데이터 `data/values/*.parquet` 2,356표 857 MB.

## Idea
**대체 정답 표 = 골든의 모든 셀 사실과 같은 값·기간·지역·분류를 가진 셀이 다 있는 표.** 숫자 일치를 코드가 확인하므로 숫자 정확성 기준은
낮아지지 않는다(틀린 숫자는 여전히 FAIL). 남는 위험은 "값은 같고 뜻이 다른 셀"이고, 규칙 ③~⑥과 모든 사실이 한 표에서 동시에 맞아야 한다는
조건으로 줄인다. 자리에 따라 두 가지로 쓴다.

- **숫자 채점 (on-the-fly)**: e2e 행의 `used_table`이 대표 표가 아니면 그 표 하나에서만 같은 규칙으로 골든 사실을 찾고, 답이 인용한 셀 중 값이 맞는
  셀을 우선해 source_ref를 바꾼 골든 사본(table_key·sha도 그 표로)으로 기존 채점기를 돌린다. 라벨 파일 없이 결정적이고, 같은 값 셀이 여럿인 경우도
  답이 인용한 셀로 풀린다. L3(오라클, used_table = 대표 표)는 경로가 바뀌지 않는다.
- **정답 표 집합 (라벨 파일)**: `locate()`의 정답 표·Ragas ID P/R처럼 "상위 k개 중 정답 표가 있나"는 답이 인용하지 않은 표도 판정해야 하므로
  전수 스캔 라벨 `evals/datasets/calculation_alternates.jsonl`(gitignored)을 쓴다. 검색기와 무관해 T3-07~10 비교에도 같은 정답 집합.

## Option A — 숫자 채점만 고침 (on-the-fly)
- 접근: 위 "숫자 채점"만. 정답 표 판정(locate)·Ragas ID 지표는 L1 슬롯 그대로.
- 예상 성능 향상: e2e PASS 31/90 → 최대 44/90(값 일치 대체 표로 답한 13문항, 다른 오류가 없으면 PASS. 재채점으로 확정). 정답 표 연결 10/90 그대로,
  ID Recall 0.567 그대로, LLM↔ID 일치 그대로.
- 실질 반영 이점: 데이터 정확성 — S-VAL-03류 거짓 FAIL 해소. 라벨 파일·스캔 없음.
- 비용·리스크: 반나절. 하지만 "정답 표를 골랐나"(검색 실패 원인 분류, `cause`)와 Ragas ID 지표는 여전히 대체 표를 모른다 → T3-19 계기(심판↔코드 차이)가 남음.

## Option B — A + 전수 스캔 대체 표 라벨 (정답 표 집합)
- 접근: A + 라벨 생성기 `evals/builders/alternates.py`(전수 스캔, 위 규칙) → `locate()` 정답 집합 = L1 슬롯 ∪ 라벨 ∪ 대표 표, ragas 계층 gold_keys도 같은 집합.
  라벨 상태: `auto`(모든 값 정수 ≥100) / `needs_review`(작은 값·비율이 섞임, 정답 집합에 안 넣고 검수 시트로). agent 계층 숫자 채점도 같은 on-the-fly 경로.
  품질 게이트 비교 키에 라벨 파일 hash 추가 → 채점 기준 변경이므로 기준선 재promote.
- 예상 성능 향상(프로토타입 실측): 정답 표 연결 10/90 → 10 + 30(auto) 문항, e2e PASS 31 → 최대 44, 검색 1위 정답 표 34 → 재채점으로 확정(대체 표로 답한 13 중 대부분),
  ID Recall@5 0.567 → 0.776, ID Precision@5 0.409 → 0.587, LLM↔ID 일치 Recall 70.1% → 85.1% · Precision 74.6% → 62.7%.
- 실질 반영 이점: 데이터 정확성·결과 검증 — 숫자 채점과 정답 표 판정이 같은 근거(값 일치 셀)를 쓰고, 검색 실패 원인(`retrieval` vs `answer`)이 바로잡힘.
  라벨이 검색기와 무관해 T3-07~10 재사용. 남은 심판↔코드 차이(Precision은 LLM이 더 엄격)가 숫자로 드러나 Ragas 지표 운용을 정할 근거가 됨.
- 비용·리스크: 1일. 스캔 19초. needs_review 라벨은 사람 검수 전까지 정답 집합에 안 들어가 일부 대체 표는 여전히 오답 처리(보수적).

## Option C — B + 매칭 완화 (기간 형식 변환·항목 어휘 대응) + 검수 시트 전부 사람 확인
- 접근: B에 더해 연간 값을 월·분기 표의 합계/연간 셀로 찾기, 골든 항목 라벨과 대체 표 항목 이름을 어휘 사전으로 대응(예: 출생건수↔출생아수),
  needs_review까지 사람이 검수해 정답 집합에 넣기.
- 예상 성능 향상: 대체 표 있는 문항 38 → 그 이상(완화로 늘어나는 수는 미측정), needs_review 반영 시 ID Recall 0.776 → 최대 0.821.
- 실질 반영 이점: 정답 집합 상한에 가까워짐.
- 비용·리스크: 2~3일 + 사람 검수. 기간 변환은 합계 규칙이 표마다 달라 오매칭 위험이 커지고, 어휘 사전은 유지 비용. 기능 동결(11/30) 전 일정에 부담.

## Recommendation
**옵션 B.** 계기가 된 심판↔코드 차이는 정답 표 집합 문제이고(불일치 20 중 14가 값 일치 대체 표), A는 그걸 남긴다. B는 프로토타입으로 효과가 실측돼 있고
