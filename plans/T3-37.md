# T3-37 차트 채점 — 자동 선택 골든 · Vega-Lite 데이터 대조 (KOS-197)

## Goal
- 완료 기준 (Linear KOS-197): ① 계산 골든 문항 `type`에서 기대 차트 종류를 끌어내 종류 말이 없는 C·M 시나리오("그래프로 보여줘", "그려줘")를 만드는 빌더 옵션 ② make_chart 결과 Vega-Lite `data.values`의 숫자가 같은 턴(차트만 다시 그리는 턴이면 대화의 마지막) `summarize_stat` 사실 값의 부분집합인지 검사, 아니면 턴 오류 `chart_data_mismatch` (`evals/evaluators/agent/chart.py`, `grade_turn`에 연결) ③ 차트 턴 통과율·자동 선택 일치율을 `aggregate()`/`by_task`와 agent 리포트 표에 낸다. 기존 시나리오는 그대로, 기존 파일 재채점 결과는 이전과 같아야 한다, `--oracle` 1.000, pytest
- Baseline: 에이전트 계층은 차트를 make_chart 인자 `chart_type`으로만 채점한다. 종류 말이 없는 차트 턴은 채점 대상이 아니고(시나리오 0개), Vega-Lite 데이터와 실전 1 사실 값의 대조는 없다

## Idea
조사한 사실:
1. 실제 턴 기록(`execute_tool make_chart`의 `gen_ai.tool.call.result`)에는 Vega-Lite가 **없다**. 툴 content는 `{table_key, chart_type, kind, drawn, note}`이고 Vega-Lite 전체는 artifact로만 노드에 간다(`src/kosis_agent/services/chart.py`, tracing은 content를 기록). 대신 인자 `chart`에 실전 1 ChartSpec 전체(점마다 `value`·`fact_id`)가 들어 있고, 결과 `kind`가 실제로 그린 실전 1 종류다. 그래서 채점기는 결과에 `vega_lite`가 있으면 그것을, 없으면 툴과 같은 변환(`kosis_chat.chart.vega.to_vega`, ChartSpec + 결과 `kind`)으로 spec을 다시 만들어 `data.values`를 읽는다. 에이전트 코드(src/kosis_agent)는 고치지 않는다.
2. `data.values`에서 대조할 숫자는 x·y·theta 채널의 quantitative 필드(실전 1은 `값`)만이다. 원형의 `비중`(툴팁)·`순서`(order)는 사실 값이 아니다.
3. 저장된 실행 5개(T3-27 cmp-dev-rules · hybrid-HCX-005 · live-hcx · numbers-hcx · relyear-dev-rules, 차트 147개)에서 차트 점 값 ⊄ 사실 값인 차트는 0개였다(실전 1은 맥락 행도 사실로 낸다). 그래서 정확 일치(부동소수 오차만 허용) 규칙으로 기존 실행의 판정이 바뀌지 않는다.
4. 실전 1 `QuestionType` = value · trend · compare · share · extreme. 실제 종류 선택 규칙은 `src/kosis_agent/services/chart.py`가 아니라 실전 1 `kosis_chat/chart/builders.py`에 있다(chart.py는 종류 말이 없으면 실전 1 종류 그대로): value = 막대 하나(또는 기간 순 막대 timeline) · trend = 꺾은선 · compare = 막대 · share = 원형 · extreme = 정렬 막대(또는 timeline). 대상×기간 격자면 grouped_bar / multi_line. T3-02 규칙(시간 변화 = 꺾은선, 항목 비교 = 막대, 구성 = 원형)과 같다.
   → 매핑 `value→bar, trend→line, compare→bar, share→pie, extreme→bar`. 그린 종류는 계열로 묶는다: bar·timeline·grouped_bar → bar, line·multi_line → line, pie → pie.
5. 기존 C·M 출처(L1 한 슬롯 문항 중 계산 문항이 있는 것)는 10개뿐이고 value 7 · trend 2 · compare 1(share·extreme 0)이다. 그래서 자동 선택 시나리오는 계산 골든 문항에서 바로 만든다(E·X처럼 `first_turn`). 유형마다 번갈아 뽑아 C·M 각 15개, 표가 MAX_ROWS를 넘는 문항은 뺀다.

## Option A — 이슈 그대로: 턴 기대 `auto_chart` + 차트 채점 모듈 + 별도 시나리오 파일
- 접근: `TurnExpect.auto_chart`(bar | line | pie, 종류 말이 없는 차트 턴에서 그려야 할 계열) 추가. `builders/multiturn.py --auto-chart`가 `agent_scenarios_multiturn_chart_auto(_structure).jsonl`(sid `MT-C-A001`·`MT-M-A001`)만 쓴다(기존 3+1개 파일은 건드리지 않음). `evaluators/agent/chart.py`: 데이터 대조(`chart_data_mismatch`), 자동 선택 일치(`wrong_chart_type`, make_chart를 불렀는데 계열이 다를 때). `aggregate`·`by_task`에 차트 턴 통과율·차트 데이터 일치율·자동 선택 일치율, 리포트 표·HTML 타일
- 예상 성능 향상: 지표 추가라 시스템 수치는 그대로. 자동 선택 턴 0 → 30개가 채점된다. 기존 시나리오 재채점은 모든 기존 지표가 같고(사실 3) 새 지표만 생긴다
- 실질 반영 이점: 데이터 정확성 — 차트에 사실이 아닌 숫자가 그려지면 잡힌다(LLM이 만든 숫자 = 버그 원칙을 차트까지). 자동 선택 규칙(T3-02)이 바뀔 때 "몇 → 몇"을 남길 기준점
- 비용·리스크: 반나절, LLM 비용 0(mock 실전 1 구조 실행). mock 실전 1이 질문 유형을 잘못 읽으면 자동 선택 일치율이 낮게 나오지만 그건 측정 결과로 기록한다

## Option B — make_chart 툴 content에 Vega-Lite를 싣고 그것만 채점
- 접근: `src/kosis_agent/services/chart.py`의 content에 `vega_lite`를 넣어 span에 기록, 채점기는 결과만 읽는다
- 예상 성능 향상: A와 같은 지표
- 실질 반영 이점: 채점이 실제로 그린 spec을 그대로 읽는다
- 비용·리스크: 에이전트 동작(툴 content·LLM에 보이는 결과·span 크기) 변경이라 평가 태스크 범위 밖. 과거 실행은 재채점할 수 없다

## Option C — ChartSpec 점 값만 대조 (Vega-Lite 재구성 없음)
- 접근: `args.chart.series[].points[].value`를 사실 값과 대조하고, 자동 선택은 A와 같게
- 예상 성능 향상: A와 같은 수치(점 값 = `값` 필드)
- 실질 반영 이점: 코드가 더 짧다
- 비용·리스크: 이슈의 "Vega-Lite spec의 data" 검사가 아니다. `vega_lite`가 미리 채워진 spec(실전 1 계약상 가능)이나 다른 그리기 경로는 놓친다
