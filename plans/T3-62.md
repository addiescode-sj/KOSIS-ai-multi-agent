# T3-62 화면 인터랙션 — 스크롤 연동 애니메이션과 핵심 수치 카운터 (Framer Motion)

## Goal
- 완료 기준 (TASK.md): Framer Motion(`motion` 패키지)으로 ① 스크롤 진행에 따라 움직이는 효과, ② 답 카드 "핵심 수치"가 0에서 실제 값까지 올라가는 카운터를 넣는다. 카운터 끝에 보이는 값은 서버 값 문자열과 한 글자도 다르지 않고(단위·자릿수·쉼표 유지), `prefers-reduced-motion: reduce`이면 처음부터 최종 값이다. `npx tsc --noEmit`·`npx eslint .`·`npx jest`·`npm run build` 통과, 브라우저(Playwright)로 두 애니메이션 확인.
- 요청 (11/27, 임도유): 참고 자료는 FESI 7기 노션 "CSS Animation" — 기본 애니메이션 4종(페이드 인/아웃, 슬라이드, 스케일, 회전). 이 중 페이드·슬라이드를 스크롤 등장에, 스케일은 진행 막대(scaleX)에 쓴다. 회전은 이미 로딩 아이콘(`animate-spin`)에 있어 새로 쓰지 않는다.
- 프론트 담당은 Addie Lee라 PR 리뷰를 받는다. 변경은 표시 층(`components/`)과 순수 계산 모듈 하나로 한정하고, 데이터 흐름·API·스키마는 건드리지 않는다.
- Baseline (origin/main `38e32c0`, 이 worktree):
  - 애니메이션 라이브러리 없음. 움직임은 `tw-animate-css`·Tailwind `animate-spin`·`transition-colors`뿐. 스크롤 연동 효과 0, 숫자 카운터 0.

  - `prefers-reduced-motion` 처리 0곳.
  - tsc 통과, eslint 통과, jest 23개 파일 101개 통과, `next build` 통과. 클라이언트 JS(`.next/static/chunks/*.js` gzip 합) **517,272 B**.

## Idea
1. **카운터의 숫자 규칙은 순수 함수로** (`lib/motion/count-up.ts`, jest)
   - `countFrame(fact, progress)`: `progress >= 1`이면 `formatValue(fact)`를 그대로 돌려준다(끝값 = 서버 값 문자열, 따로 다시 만들지 않음). 중간 프레임은 `value × ease(progress)`를 끝값과 **같은 소수 자릿수**로 `ko-KR` 포맷 → 글자 폭이 흔들리지 않는다. 음수(증감률 −3.2%)는 0 → −3.2로 내려간다.
   - 숫자는 서버가 준 `fact.value`·`fact.round`만 쓴다. 화면이 새 숫자를 만들지 않는다(중간 프레임은 보이는 연출일 뿐이고 끝 프레임은 서버 문자열).
   - 중간 프레임 자릿수: `round`가 있으면 그 값, 없으면(`round` null, 원 셀 값) **끝값 문자열의 소수 자릿수**를 그대로 쓴다. 끝 프레임은 어느 경우나 `formatValue` 문자열.
   - `Headline` 타입(`types/answer.ts`)과 `headline()`(`lib/chat/answer.ts`)에 `raw: number`, `round: number | null`을 더한다(기존 `value` 문자열은 그대로 → 복사 버튼(`copyText(result)`, 데이터 기준)·다른 호출부 영향 없음). `answer.test.ts`의 `toEqual` 기대값 갱신.
2. **카운터 컴포넌트** (`components/motion/count-up.tsx`, `"use client"`)
   - **이번 화면에서 방금 스트리밍으로 받은 턴만** 센다(리뷰 반영). `AssistantMessage`가 `running`이던 적이 있는지 ref로 기억해 `live` prop으로 내려보낸다. 복원된 대화(`/chat/[id]`)·저장된 턴은 처음부터 최종 값 → 긴 대화를 스크롤해도 재생되지 않고, 서버 렌더와 클라이언트 첫 렌더가 같은 문자열이라 하이드레이션 불일치가 없다.
   - live 턴은 마운트 뒤 `animate(0, 1, { duration: 0.9, ease: "easeOut" })`로 진행값을 돌려 `countFrame`을 찍는다. 끝나면 `value` 문자열 자체를 렌더.
   - 폭 고정: 최종 문자열을 보이지 않는 sizer로 두고 그 위에 움직이는 숫자를 겹친다 + `tabular-nums`. 숫자가 올라가는 동안 단위·차트 칸이 흔들리지 않는다.
   - `useReducedMotion()`이 참이면 애니메이션 없이 바로 `value`.
   - 화면 낭독기는 최종 값만 읽는다: 움직이는 숫자는 `aria-hidden`·`select-none`, sizer 자리의 최종 값이 실제 텍스트(드래그 복사에도 최종 값만 잡힘).
   - 단위(`head.unit`)는 지금처럼 숫자 옆 별도 span — 카운터 밖이라 그대로 유지.
3. **스크롤 연동** (`components/motion/`)
   - `ScrollProgress`: `useScroll()`의 `scrollYProgress` → `useSpring` → 상단 고정 막대 `scaleX`(노션의 스케일). `AppShell` 헤더 위에 한 줄, 모든 고객 화면 공통. 줄일 동작 설정이면 spring 없이 그대로(막대 자체는 위치 표시라 남김).
   - 홈 소개 영역(`chat.tsx`의 `Home`): 기능 카드 3개에 `useScroll({ target, offset: ["start end", "end end"] })` → `useTransform`으로 opacity 0→1, y 24→0(노션의 페이드 + 슬라이드). 오프셋을 "카드 아래쪽이 화면 아래에 닿을 때 1"로 잡아 **처음부터 다 보이는 카드는 처음부터 완전히 보인다**(스크롤할 수 없는 큰 화면에서 반투명으로 남는 문제 방지).
   - 답 카드 등장: 결과 카드는 `data-result`가 도착할 때 한 번 마운트된다(그 전엔 `Generating`). 이 카드를 `motion.div`로 감싸 페이드 + 슬라이드(노션 fadeIn·slideIn). 카운터와 같은 `live` 기준이라 복원된 카드는 `initial={false}`로 효과 없음.
   - 스크롤 컨테이너는 window다(AppShell은 overflow 컨테이너가 아니고 사이드바·헤더만 sticky) → `useScroll()` 기본값. Home → 대화 전환 때 AppShell이 다시 마운트되어 진행 막대가 0부터 다시 시작하는 것은 새 화면이라 맞는 동작.
   - 전역 `<MotionConfig reducedMotion="user">`(`app/providers.tsx`) — `motion.*` 컴포넌트의 transform 애니메이션이 OS 설정을 따른다. 스크롤 연동 값(`useTransform`)은 MotionConfig가 막지 않으므로 훅 안에서 `useReducedMotion()`이면 고정값을 쓴다.
4. **검증**: jest(`count-up.test.ts`: 끝값 = `formatValue` 문자열, 자릿수 고정, 음수, 0, 큰 수·소수 round), tsc·eslint·build, 번들 크기 전→후, Playwright: 홈 스크롤 → 진행 막대 scaleX·카드 opacity 변화 값 읽기, 답 카드 숫자가 중간값을 거쳐 서버 문자열로 끝나는지(가짜 답은 `lib/chat/fixtures.ts` 또는 로컬 dev 서버 + Docker 백엔드), `reducedMotion: "reduce"` 에뮬레이션에서 첫 프레임 = 최종 값.
   - 실행 중인 Docker 스택(3000·8000)은 건드리지 않는다. 이 worktree에서 `npm run dev -- -p 3100`, `/api/*`는 지금처럼 백엔드 8000으로 프록시.

## Option A — 최소안: 카운터 + 상단 진행 막대만
- 접근: Idea 1·2 + `ScrollProgress`만. 홈·답 카드 등장 효과 없음. `motion`의 `animate`·`useScroll`·`useSpring`만 import(`motion.*` 컴포넌트는 막대 하나).
- 예상 수치: 스크롤 연동 효과 0 → 1(진행 막대), 카운터 0 → 1, 끝값 일치 jest 0 → 6건, reduced-motion 처리 0 → 2곳. 클라이언트 JS 증가는 측정 전 추정 +10~15 KB gz(`animate`·`useScroll` 경로만).
- 실질 이점: 숫자 정확성 규칙(끝값 = 서버 문자열)을 테스트로 고정하면서 변경이 가장 작아 리뷰가 쉽다.
- 비용·리스크: 낮음. 다만 "홈 소개 영역·답 카드 등장"이라는 요청 예시가 빠져 화면 변화가 작다.

## Option B — 균형안: A + 홈 소개 영역 스크롤 연동 + 답 카드 등장 + 전역 reduced-motion (추천)
- 접근: Idea 1~3 전부. `motion.*` 컴포넌트를 그대로 import(`motion/react`).
- 예상 수치: 스크롤 연동 효과 0 → 2(진행 막대, 홈 기능 카드), 스크롤 등장 0 → 1(답 카드), 카운터 0 → 1, 끝값 일치 jest 0 → 6건, reduced-motion 처리 0 → 전역 1 + 훅 3곳. 클라이언트 JS 증가는 측정 전 추정 +30~40 KB gz(`motion.*` 컴포넌트 포함).
- 실질 이점: 요청 예시(홈 소개·답 카드·진행 막대·카운터)를 모두 덮고, 노션 자료의 페이드·슬라이드·스케일을 실제 화면에 쓴다. 컴포넌트 3개(`ScrollProgress`·`ScrollReveal`·`CountUp`)가 `components/motion/`에 모여 다른 화면(검색 결과·설정)에도 바로 쓸 수 있다.
- 비용·리스크: 중간. 번들 증가(측정해서 Result에 남김). 복원 대화에서 효과가 다시 재생되지 않도록 `live` 구분 필요 — Playwright로 새 답 1건(재생)·복원 대화(재생 안 함) 확인. reduced-motion 처리는 jest(node 환경)로 검증할 수 없어 Playwright 에뮬레이션으로만 확인한다.

## Option C — 고성능안: B + LazyMotion 번들 줄이기 + DOM 컴포넌트 테스트
- 접근: B와 같은 화면. `motion.*` 대신 `<LazyMotion features={domAnimation} strict>` + `m.*`로 처음 로드 크기를 줄이고, `jest-environment-jsdom`·`@testing-library/react`를 들여와 `CountUp`의 reduced-motion·끝값을 DOM에서 테스트한다.
- 예상 수치: B의 화면 수치 + 클라이언트 JS 증가 추정 +15~20 KB gz(B보다 작음, 측정 전), DOM 테스트 0 → 3건.
- 실질 이점: 번들 증가를 절반 가까이 줄이고, 컴포넌트 동작까지 테스트로 고정.
- 비용·리스크: 높음. devDependency 2~3개 추가와 jest 설정 변경(지금 `lib/**` node 환경만 — AGENTS.md·jest.config 방침 변경)이라 리뷰 범위가 커진다. `strict` 모드에서 `motion.*`를 쓰면 런타임 오류라 이후 기여자에게 규칙이 하나 생긴다.

## Recommendation
- **B**. 요청 범위를 모두 덮으면서 변경이 표시 층에 머문다. 숫자 정확성(끝값 = 서버 문자열)은 순수 함수 jest로 A·B·C 모두 같은 수준으로 고정되므로, C의 DOM 테스트·LazyMotion은 번들 측정값을 보고 리뷰에서 필요하면 후속으로 한다.

## Review
독립 리뷰(서브에이전트, 11/27) 반영:
1. "스트리밍 중 카드 깜빡임" 전제가 틀림 — 결과 카드는 `data-result` 도착 때 한 번 마운트된다. 실제 위험은 **복원 대화에서 카드마다 효과 재생**과 **서버 렌더(0) ↔ 클라이언트(최종 값) 불일치** → `live` 턴만 재생, 그 외 첫 렌더 = 최종 문자열로 수정.
2. 숫자 폭 흔들림 → 최종 값 sizer + `tabular-nums`.
3. `round` null 규칙 → 끝값 문자열의 소수 자릿수를 중간 프레임에 사용.
4. `Headline` 타입 위치(`types/answer.ts`)와 `answer.test.ts` 기대값 갱신을 명시.
5. 번들 수치는 측정 전 추정으로 표시, 실제 값은 Result에.
6. 드래그 복사 시 중간 숫자 → 움직이는 숫자는 `aria-hidden`·`select-none`, 최종 값이 실제 텍스트.
7. C는 B 위에 얹는 개선이라 독립 대안으로는 약하다는 지적 — 같은 화면을 다른 로드·테스트 방식으로 만드는 안으로 남기되 추천은 B 유지.

## Decision

구현 중 고친 것 (Playwright에서 발견):
1. `live`를 "마운트 때 running"으로 잡으면 답이 한 번에 도착할 때 카운터가 안 돎 → "이 화면을 열 때 없던 턴"(`Chat`의 `initial.messages` 기준)으로 변경.
2. 스크롤할 수 없는 화면에서 진행 막대가 꽉 찬 채로 보임 → `scrollY`가 0이면 막대 숨김.
3. reduced-motion에서 홈 카드가 서버 HTML의 `opacity:0`에 남음(하이드레이션이 인라인 스타일을 고치지 않음) → 항상 motion value로 넘기고, reduced-motion 판단은 하이드레이션 뒤에 적용.
