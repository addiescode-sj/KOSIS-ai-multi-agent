# T3-28 멀티쿼리 — 다른 표가 필요한 한 턴 여러 질문 (Linear KOS-181, KOS-177 하위)

## Goal
- 완료 기준 (TASK.md 그대로): 서로 다른 표가 필요한 한 턴 여러 질문("2024년 출생아 수와 사망자 수", "혼인 건수랑 이혼 건수 비교")을 하위 질문으로 나눠 표마다 검색·실전 1로 답하고, 하위 답을 합친다(표 사이 계산이 필요하면 코드가 계산, LLM 숫자 없음). 골든 문항을 이어 붙인 멀티쿼리 dev 시나리오로 대화 성공률·하위 질문별 툴·표·수치 정확도를 전→후로 잰다. 한 턴 질문 회귀 0.
- Baseline: **baseline 없음.** 멀티쿼리 시나리오가 아직 없다. 이 태스크에서 만드는 시나리오로 T3-27 그래프(현재)를 먼저 재서 "전" 값으로 쓴다. 지금 그래프는 한 턴에 검색 1번·표 1개라서 하위 질문 2개 중 1개만 답한다 → 대화 성공률 ~0 예상.

## 범위 (KOS-177 "남은 것" 중 이 태스크가 맡는 것)
- **멀티쿼리** = 한 턴 안에 **서로 다른 표**가 필요한 질문 둘 이상. T3-27이 "T3-08로 넘김"이라고 적은 항목이다. KOS-181이 따로 생겨서 여기서 한다.
  - 같은 표 안의 비교("서울이랑 경기도 2인 가구 비교", S-CMP-04)는 실전 1 `compare`가 이미 답한다 → **나누지 않는다.** 나누면 오히려 회귀다(한 턴 패리티 90/90으로 확인).
  - "찾아서·계산해서·그려줘"(한 턴 여러 *요청*)는 T3-27에서 끝났다(M 유형 1.000).
- **두 표 결과를 합친 계산** (KOS-177 "남은 것" 3번째): 하위 답이 각각 숫자 하나이고 사용자가 차이·합·비율을 물으면 코드가 계산한다.
- 범위 밖: 하위 질문이 서로의 결과에 기대는 연쇄 질문("출생아가 가장 많은 시도의 혼인 건수는?") → T3-08 Plan-and-Execute.

## Idea

### 공통 1: 멀티쿼리 dev 시나리오 (`evals/builders/multiquery.py`)
수치 골든 90문항을 **표가 다른 두 문항**끼리 이어 붙여 한 턴으로 만든다. 정답은 두 골든 문항의 정답 그대로라 사람이 새로 만들 정답이 없다.
- 이음 표현 3~4개, 시드 고정: "{Qa} 그리고 {Qb}", "{Qa}, {Qb}", "{Qa} 또 {Qb}" 등. 원문을 그대로 붙이므로 골든 조회 검색(T3-27 `GoldenLookupSearch`)이 하위 질문마다 맞는 표를 준다. 합친 원문을 통째로 검색하면 긴 쪽 하나만 찾는다 → 나누지 못한 그래프는 하위 질문 하나를 놓친다.
- 원천: 답할 수 있는 골든 문항 전부(유형 무관, 채점은 각 문항의 L3 채점 그대로). 표가 다른 쌍만, 시드 고정 ~30개.
- **표 사이 계산 예시(K)**: 단위가 같은 값 문항 쌍에 "…, 둘의 차이는?" / "합은?"을 붙인다. 정답은 두 골든 값으로 코드가 만든다(빌더). 원천은 사실 1개짜리 값 문항 9개(7개 표)뿐이고, 표가 다르고 단위가 같은("명") 쌍은 **5개**다(S-VAL-03·07 × S-EDG-16·21, S-EDG-16×21). **지표가 아니라 동작 확인용 예시**로만 보고한다.
- **나누면 안 되는 대조군(N)**: 같은 표 비교 골든(S-CMP-*, S-CX-GAP-*, S-CX-GRW-* 등 "A와 B" 문항)을 그대로 넣는다. 기대: 분해 없이 summarize_stat 1번. "와/랑"에 속는지(과분해율) 잰다.
- 출력: `evals/datasets/agent_scenarios_multiquery_dev.jsonl`(+`_structure`), 합성 정답 `calculation_golden_multiquery.jsonl` (gitignored, 빌더만 커밋).

**빌더 세트의 한계 (리뷰 2·3 반영)**: 골든 조회 검색은 "골든 원문이 질문 안에 그대로 있는가"로 표를 준다. 그래서 빌더가 붙인 이음말("그리고"·","·"또")에서 자르기만 하면 어떤 옵션이든 구조 지표가 ~1.0이 된다. 빌더 세트는 **"분해가 연결돼 동작하는가 + 대조군을 나누지 않는가"**만 확인하고, 옵션 간 차이는 재지 못한다. LLM이 하위 질문을 바꿔 쓰면 원문 일치가 깨져 엉뚱한 표가 나오므로, mock 측정에서 LLM 안은 실제보다 나쁘게 보인다.

**옵션 비교용 세트 (일반화)**: 사용자가 따로 쓴 멀티쿼리 표현 10~20개(조건 공유 "2024년 출생아 수와 사망자 수", "와/랑" 이음, 대조군 포함). 골든 조회로는 표를 줄 수 없으므로 문항마다 **하위 질문별 정답 표 키를 사람이 적고**(tables.csv에서, L1 정답 집합처럼 여러 개 허용), **실시간 검색**(T3-27에서 쓴 Chroma·체크포인트)으로 돌린다. 채점은 분해 정확도(하위 질문 수·조건)·하위 질문별 표 정확도·과분해율. 수치는 정답이 없어 이 세트에서는 재지 않는다(답한 숫자에 근거 없는 숫자가 없는지만 본다).

### 공통 2: 채점 확장 (`evals/schemas.TurnExpect`, `evals/evaluators/agent.py`)
- 지금은 턴당 `calc_qid` 하나 = 마지막 summarize_stat만 채점한다. 선택 필드 `calc_qids: list[str]`를 추가해 **summarize_stat 호출 순서대로** 각각 L3 채점한다(추가만, 기존 시나리오 그대로).
- 계산 결과는 문장 숫자 대조가 아니라 **구조화 필드**로 채점한다(리뷰 4): `ChatResult.combined = {op, value, unit, inputs: [표 키·셀 키]}`를 기대값 `combine`과 비교. 하위 답 숫자를 베낀 경우와 구분된다.
- 지표: 대화 성공률, 분해 정확도(하위 질문 수 일치), 하위 질문별 표·툴·인자·수치 정확도, N 대조군 과분해율, 요청당 지연. 측정은 T3-27과 같이 2단계: 구조(mock 실전 1) → 수치(HCX, 사용자 확인 후).

### 공통 3: 그래프 (`src/kosis_agent/graph/`)
- 새 모듈 `graph/multiquery.py`: `split_question(question, parse) -> list[str]` (하위 질문 목록, 1개면 분해 안 함) + `combine(answers, op) -> Combined | None` (코드 계산).
- `main_graph.py`: context 다음에 하위 질문이 2개 이상이면 **하위 질문마다 기존 search → statistics 경로**를 돈다(새 검색 알고리즘·새 실전 1 호출 방식 없음, 툴 span 그대로 = 하네스가 호출별로 채점). 이번 턴 상태에 `sub_questions`, `sub_results` 추가.
- **같은 표 되돌림**: 하위 질문들이 검색에서 같은 표를 찾으면 나누지 않고 원문 한 번으로 실전 1에 묻는다(같은 표 비교는 실전 1 `compare`가 답함). 코드가 검색 결과를 보고 정한다. 모든 옵션에 공통.
- 답 문장: 하위 답(실전 1이 검증한 `StatAnswer.text`)을 순서대로 잇는다 → 출처가 표마다 남는다. 계산이 있으면 코드 고정 문장 "{A}와 {B}의 차이는 {값}{단위}예요." (숫자는 코드가 하위 답의 사실 값에서 계산, 사실이 하나가 아니거나 단위가 다르면 계산하지 않고 그 사실을 말함).
- 하위 질문 하나가 거절되면 나머지는 답하고 거절 이유를 그 하위 질문에 붙인다(지어내지 않음). outcome은 모두 답함 = answered, 일부 = answered + `partial`, 모두 거절 = refused.
- 대화 상태: 다음 턴 "그 표"는 **마지막 하위 질문의 표**로 둔다(단순 규칙, 한계는 Result에). `ChatResult`에 선택 필드 `sub_results`·`combined` 추가(옛 프런트는 무시).
- 멀티턴과의 관계: 분해는 context가 "새 질문"으로 판단한 턴에서만 한다. 이월·지시어·차트 턴은 지금 경로 그대로.

## 옵션 — 하위 질문을 어떻게 나누나 (리뷰 1 반영: 매 턴 LLM 플래너안은 T3-08과 겹쳐 빼고, LLM 0 지표 규칙안을 넣음)

## Option A — 구분자 규칙 (LLM 0)
- 접근: "?"·"그리고"·"또"·"," 로 자른 조각이 각각 완전한 질문(실전 2 `parse_query`가 지표 낱말을 읽음)이면 나눈다. "와/랑/하고"로는 나누지 않는다. 조건 공유는 하지 않는다.
- 예상 성능 향상: 빌더 세트 대화 성공률 ~0 → ~1.0(빌더 이음말과 같은 규칙이라 상한, 차이를 못 잼). 사용자 표현 세트에서는 "X와 Y" · 조건 공유 표현을 못 나눔 → 분해 정확도 낮음(세트 구성에 따라 대략 절반 이하로 추정, 측정 전 근거 약함). 과분해 0.
- 실질 반영 이점: 데이터 정확성·예외 처리(부분 거절)·멀티쿼리 경로 자체. 지연·비용 추가 0(검색은 하위 질문 수만큼).
- 비용·리스크: 1일. 가장 흔한 "출생아 수와 사망자 수" 형태를 놓친다.

## Option B — 지표 기반 규칙 (LLM 0, 추천)
- 접근: A + ① "와/과/랑/이랑/하고"로도 자르되, **조각들의 `ParsedQuery.measures`가 서로 다를 때만** 나눈다(확인: "2024년 출생아 수와 사망자 수" → `['출생','사망']` 나눔, "2025년 2인 가구 수, 서울이랑 경기도 비교" → `['2인가구']` 하나라 안 나눔). ② 뒤 조각에 연도·지역이 없으면 앞 조각의 연도·지역 표현을 코드가 채운다("2024년 사망자 수"). ③ 지표 낱말이 없는 조각("태어난 아이")이 있으면 나누지 않는다(판단 보류 = 지금 동작). 나머지는 같은 표 되돌림이 받친다.
- 예상 성능 향상: 빌더 세트 ~0 → ~1.0(A와 같음), 사용자 표현 세트 분해 정확도 A보다 높음(근거: 위 실측 두 예처럼 "와/랑" 이음 대부분이 measures로 갈림). 과분해: measures가 둘 이상 읽히는 같은 표 문항(예: "인구와 가구")은 같은 표 되돌림으로 막음. 숫자 추정치는 사용자 세트를 재기 전에는 쓰지 않는다.
- 실질 반영 이점: A + 질의 이해. 실전 2 parse 규칙을 그대로 재사용, LLM 비용·지연 0. `split_question`이 T3-07·08 비교의 기준선이 된다.
- 비용·리스크: 1.5일. measures 사전에 없는 지표("태어난 아이"류, T3-27에서 골든 13/90)는 못 나눈다 → 사용자 세트에서 그 비율을 잰다.

## Option C — B + 판단 보류 턴만 LLM 분해, 코드 검증
- 접근: B가 판단 보류한 턴(구분자는 있는데 지표 낱말이 안 읽힌 조각)만 LLM에 하위 질문 목록을 묻는다. T3-27 `LLMReader`는 (직전, 이번 질문) 전용이라 **새 프롬프트·JSON 스키마·검증기가 필요**하다(재사용은 HCX JSON 한 줄 호출 방식 정도). 검증: 하위 질문의 숫자·시도·낱말이 원문에 있어야 함, 벗어나면 버림. 표 키·숫자는 LLM이 정하지 않는다.
- 예상 성능 향상: 사용자 세트 분해 정확도 B보다 조금 높을 수 있음(보류 턴 비율만큼이 상한). 빌더 세트에서는 LLM이 바꿔 쓴 하위 질문이 골든 조회와 어긋나 오히려 낮게 나올 수 있다(측정 함정).
- 실질 반영 이점: 표현 일반화. 발표에 "규칙 → LLM → 코드 검증" 일관 설계.
- 비용·리스크: 2~2.5일, 보류 턴 LLM 1회(~1 s), 새 검증기 테스트 부담.

## Recommendation
